# 3D原本バッファと空コンテキストの保持（C4）

## 変更

3D原本はBlobにせず、検証済みArrayBufferを原本キャッシュ内で所有する。
完全なバッファは転送で所有権を取り、呼び出し元のビューを切り離してから検証する。
部分ビューだけは対象範囲をコピーする。受け手に返すのは凍結した不透明な参照で、
原本を読む一般向けアクセサーは設けない。検証と参照の登録を一体にし、呼び出し元のバッファ、
Blob、複製したメタデータから検証済みの印を借用できないようにした。

`inspectAssetResources`を従来の`inspectAsset`と共有し、GLB/VRM構造・MIME・容量などの
検証条件を維持する。レンダラーのGPU見積もり上限も維持する。原本キャッシュの96MiBには
所有バッファの`byteLength`を計上し、2D素材は従来どおりBlobの`size`を計上する。
2Dの描画、保存形式、取り込み側の検証経路は変更しない。

最後のモデル削除時には解析結果・geometry・texture・material・skeletonを解放し、
空のWebGLコンテキストだけを30秒保持する。再追加時に破棄タイマーを解除する。
非表示、Scene終了、コンテキスト喪失では即座に破棄する。
表示中にコンテキストを失った場合は、残っているモデルを新しいコンテキストへ再転送して復帰する。
削除したGLTF/VRMの解析結果は保持せず、再追加のたびに解析する。
診断専用の`keepContext`指定は既存の比較用として残すが、非表示・終了・喪失では同様に破棄する。

## 解析ライブラリの確認

使用中のThree.js 0.186.1では、GLTFLoaderのGLB拡張がBINを`data.slice(...)`で取り出し、
`loadBufferView`がさらに範囲をコピーする。sparse accessorの書き込みも複製した属性へ行う。
VRMUtilsの頂点整理は解析後のBufferGeometryを、VRM 0の向き補正はSceneの回転を変更する。
原本を編集する経路は確認されなかったため、パーサーへ渡す前の追加コピーは入れない。
参照: [GLTFLoader r186](https://github.com/mrdoob/three.js/blob/r186/examples/jsm/loaders/GLTFLoader.js)。

実ブラウザーでGLBとVRM 1.0の小さな自作fixtureを、通常のRenderer・VRMLoaderPlugin・
後処理・プレイヤー作成・最初のポーズと描画まで通す。前後および再解析後の原本SHA-256が
完全一致することを`tests/model-source.spec.ts`で検証する。

## 計測条件

2026-10-21、変更前`a81e63b`、変更後`c2c003d`。
[C3の条件](asset-read-transfer.md)を使い、両方を今回新しく測った。
Windows、Chrome for Testing 153.0.8010.12、Intel UHD Graphics / ANGLE Direct3D11、
1920×1080指定の専用ウィンドウ、実YouTubeの同じwatchページ、診断ビルドでの通常Renderer。
OS・ドライバーのキャッシュは消去していない。普段のプロファイルと通常版distは使わない。

VRMは57,185,776bytes（54.5366MiB）の私有原本、VRM 0.x。
PNGは30,000,000bytes、3000×2499 RGBAの実画素を持つ固定データ。
各素材を5回再読み込みし、その都度同じタブで削除・再追加する。小さな画像を残してSceneを維持する。
原本・アバター画像はコミットしない。

取得は原本の検証完了まで。再読み込みの表示時間は取得開始から、再表示は再追加指示から数える。
完了はモデルの描画・canvasコピー・2 RAF、画像のdecode・2 RAFであり、物理画面への提示時刻ではない。
YouTube本体のロードと素材の保存時間は含めない。

全40試行、区間、変更後の実VRMの資源数、反復試験の全20サンプルを
[計測JSON](benchmarks/asset-source-context-2026-10-21.json)に記録した。

今回のVRM表示中央値は再読み込みで約42%、再表示で約18%短縮した。
ただし非同期区間はタスク実行待ちを含み、特に変更前のBlob読み取りと初回描画には大きな外れ値がある。
各区間の中央値は同じ試行とは限らず、足して全体にはならない。
Blob往復の消滅は確認できたが、表示時間の差すべてをこの変更だけの効果とは断定しない。
解析の高速化は確認できず、PNGも改善したとはいえない。
VRM再読み込みの中央値はC3の目標1.5秒を引き続き超えている。

## 資源の解放と確認範囲

`tests/model-context.spec.ts`では、本番の30秒設定を変えずに時計だけを制御する。
保持中5回、期限切れ後5回の追加・削除をGLB/VRMそれぞれで繰り返す。
29,999msで保持、30,000msで破棄、再追加で同一canvasを再利用することを確認する。
実WebGL・実パーサーを使い、`renderer.info.memory`のgeometry/texture数とprogram数を記録する。

| 対象                           | 表示中 geometry / texture / program | 削除後（保持中） | 期限切れ後のcontext |
| ------------------------------ | ----------------------------------: | ---------------: | ------------------: |
| GLB自作fixture（10回）         |                      毎回 1 / 2 / 2 |   毎回 0 / 0 / 0 |                   0 |
| VRM 1.0自作fixture（10回）     |                      毎回 1 / 3 / 1 |   毎回 0 / 0 / 0 |                   0 |
| 54.5MiB VRM 0.x（5組の再表示） |                      毎回 5 / 8 / 6 |   毎回 0 / 0 / 0 |          計測対象外 |

継続的な増加は確認されなかった。これらはThree.jsの資源数で、物理VRAMの使用量ではない。
非表示・再表示、Scene終了、実際の`WEBGL_lose_context`による喪失、削除・Undoも確認する。
自動化環境では実タブ切り替えや最小化でも`document.hidden`が変わらなかったため、
非表示のテストはvisibility入力を固定し、実Rendererの破棄・復帰を確認する方式にした。
ネイティブのタブ非表示イベントの自動確認は未達であり、確認範囲を区別する。
フォーカス模擬によるvisibilityへの影響は
[Chromeの説明](https://developer.chrome.com/docs/devtools/rendering/apply-effects#emulate_a_focused_page)にもある。

検証済み印の偽造拒否、呼び出し元ビューとの分離、部分ビュー、原本キャッシュの混在課金、
既存のMIME・破損・容量・認証・再承認・中断・チャンク予備経路をテストする。
型チェック、lint、全unitとChromeの関連テストを実行する。
診断用resident/binary/chunks比較も、新しい原本参照型に合わせて実描画の一致を確認する。

解析結果のキャッシュ、シェーダー検証の無効化、UI・DesignDocument保存形式の変更は行わない。
新たな範囲外の不具合は確認していない。
