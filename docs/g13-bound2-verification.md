# G1.3 ②の2回目の修正の検証

## 判定

**読み取り時の上限の修正は確認できたが、実描画の保護に残件があり、限定検証全体は不合格。**

前回の501.2ms・505.7msの再現は時計制御・実時間とも通った。部品の増減と不規則な2,304回の読み取りでも、古い位置を上限外で返す例はなかった。元の `g13-sparse-visual` も通り、更新後の操作部品全体はネイティブ表示と一致した。

一方、同じ作品で次の描画入力を1.4秒まで空けると、動いた操作部品が既に描かれた黒い絵に隠れ続けた。`capture` の呼び出しが来たときの古さと、次の呼び出しまで画面に残る絵の保護は別だった。この隠れは修正前にもあり、今回新しく入った退行ではない。②の修正だけで画面上の保護の時間上限まで守れる、とは判定できない。

## 読み取り時の上限

### 前回の再現

`TRUST_MS` は200ms＋6組×34ms＝404ms。初めに全体を読み、最初の組を確認した直後にWAAPIで部品を150px動かす。DOM mutationは0。次の追いつき確認で、修正後はその組をもう一度比較した。

| 時計   | 修正前                                                        | 修正後                                                        |
| ------ | ------------------------------------------------------------- | ------------------------------------------------------------- |
| 制御   | 900msの読み取りで、最後の確認から500ms前のleft=70を返す       | 799msで読み直し、left=220を返す                               |
| 実時間 | 約884.2msの読み取りで、最後の確認から496.2ms前のleft=70を返す | 約780.5msの追いつきでleft=220。その後約890.3msの読み取りも220 |

前回からテストの操作と期待を緩めていない。修正後の500ms経過時に `targetRead=false` でも、それより前に新しい位置へ更新済みなら違反ではない。最後に確認した古い位置を返し続ける場合だけを不合格にしている。

### 不規則な間隔と部品の増減

既存unitの時刻管理のsimulateを使わず、本物のDOMにsourceを読み込んだ。sourceが返す矩形を部品自身の矩形と比較し、部品を実際に読んだ時刻を別に記録した。間隔には1・7・8・9・16・33・34・50・199・200・201・403・404・405・699・1,301msを使い、固定seedで96条件を再生した。

同じsourceで部品数を8段階に増減させた。追加した全ての部品が、テストからfreshを頼まずに候補として発見され、surface数は20→24→25→26→50→139→259→22へ変わった。その後、各段階で先頭・中央・末尾の部品を動かした。画面上で操作部品が動いていないことを実装の時刻表だけから判断していない。

修正後は2,304回中、信頼して返した古い位置の上限違反0、96条件とも移動を発見した。同じoracleを修正前にかけると18回違反し、最大654msの古さを検出した。`pending=layout` の古いsnapshotは描画を保留するため、信頼した読み取りとは分けて記録した。

### タブの非表示と復帰

Playwrightの通常接続はフォーカスを模擬するので、タブを切り替えても `document.hidden=false` のままだった。URLでのtabs検索も、この拡張にはURLを読む権限がなく使えなかった。これらの準備の失敗を製品の失敗として数えていない。

最後は使い捨てのChromeをheadlessで起動し、公開API `connectOverCDP({ noDefaults: true })` で接続した。通常fixtureと同じ拡張と模擬ページを使い、同じwindowId内の別タブを実際に選んだ。visibilityの記録が `[true,false]` になることを確かめ、裏で部品を150px動かし、900ms以上後に戻した。最後の通常テストと同じ実行ファイルの確認では、最初の確認から1,025.8ms後の復帰後の最初の `capture({coalesce:true})` がleft=220を返した。ブラウザーは153.0.8010.12。getterの差し替えや合成のvisibilityイベントではない。通常の利用者のChromeやプロファイルは使っていない。

## 実際の描画

### 元のsparse条件

元の `g13-sparse-visual` は成功した。描画をポインターにだけ追従させ、300msで最初の組を読み、部品を動かし、520ms・620msにポインター入力を送る。修正後はその後の穴が新しい位置へ移った。独立に加えた全画素の比較でも、部品の70×40px全体について、作者の層を隠したネイティブ表示との差は **0/2,800画素**。同じ比較の修正前は失敗した。

画像はDOMを変えない `Page.captureScreenshot` で撮り、開いて確認した。[更新後](screenshots/g13-bound2-verification/sparse-final-after.png) ではSecondの文字と部品全体を読める。

### 長く入力しない条件

**G1の残件：操作面が隠れる × 条件がそろうと発生 → その段階で直す分類。依頼に従い修正していない。**

元の作品・部品・移動方法のまま、次のポインター入力を520msから1,400msへ、620msから1,500msへ遅らせた。記録は1,900msまで延ばした。300ms付近の確認後、部品がmutationなしで動く。新しい入力が来ない間、元の穴のまま絵が表示される。

通常ビルド2回で、元の条件では成功する追加specが失敗した。2回目は移動334.6ms、最後に中心が隠れていたのは1,419ms。移動からでも1,084.4msで、404ms＋1フレームを超える。1,000ms付近にCDPで撮った画像では部品が黒い絵に完全に隠れ、部品全体の **2,800/2,800画素** がネイティブ表示と違った。1,400msの新しい入力後は穴が更新され、最後の画像は **0/2,800画素** の差になった。[入力前](screenshots/g13-bound2-verification/idle-covered-after.png) / [入力後](screenshots/g13-bound2-verification/idle-final-after.png)。

記録用ビルドでも同じ隠れと画素差を確認した。答え合わせは相対312.6msに最初の組を読み、次は1,416.6msまで走っていない。そこで移動を見つけ、1,417.6msに全体を読んだ。記録上の空白は1,104ms。この間の画像と毎フレームの表示記録も保存した。修正前でも同じ長い待ちの条件は失敗した。

原因は、今回の上限判定が `source.capture` の呼び出し時に行われること。`answer-check` は期限超過時に全組を読むが、その期限で自分から呼び出しを予約しない。guardのsampleは描画フレームで呼ばれ、そこでpendingな変化・停止・接近の解除などを予約する。静かな部分確認の期限だけで次の確認を呼ぶ処理は、この差分には追加されていない。新しい読み取りで上限を守れても、古い切り抜きを使った既存の絵は、その読み取りまで残る。

直し方の案は、作品の再描画とは別に保護の再確認を期限内に予約し、動きを検出したときは既存の絵の切り抜きを更新するか保留すること。常時の全体読み取りに戻す必要があるとは判断していない。設計に関わるので、今回コードを直していない。本物のYouTubeでこの組み合わせが起きる頻度は未確認。ここで実証したのは視覚的な隠れで、入力の奪取とは断定していない。

## 変更と引き継ぎ

- 変更は報告、証拠、再現用コードだけ。製品は依頼どおり直していない。
- `manifest.json`、schema、migrations、validationに差分なし。私用VRM名の全履歴のstatも該当なし。DB・APIや作品データの変更はない。
- 今回は②の限定検証。全画面・シアター・明暗・ログイン操作、Undo/Redo・保存/破棄の実サイト全通りや、新しい悪意ある作品データの独立確認は回していない。CIや既存報告をこれらの独立再確認とは数えない。
- 翔太の手動確認：ポインターにだけ反応する絵を表示し、ページ側で操作部品が動いたあと、ポインターを止めて待つ。部品が見え続けるか、動かした瞬間だけ穴が直るかを確認する。Alt+Shift+Qで描画を外し、本来の部品が見えることも確かめる。自動の模擬ページ再現は保存した手順で実行できる。
- 次の担当へ：組ごとの時刻管理と全組catch-upは維持する。次に詰めるのは、入力がない間に既存の絵をいつ再確認するか。読み取りの合格と画面上の保護を分けて検証する。①③④を戻さず、今回失敗した長い待ちの実描画を先に通す。
