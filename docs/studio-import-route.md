# Studio取り込み経路の統一と転送実験

2026-10-20、依頼Cの検証記録。

## 変更

Studioからの取り込みは、サイズに関係なく既存の`importAssets`でService Workerへ保存し、
YouTube Hostには`import-assets`で素材IDだけを渡す。Studio Portの旧`import`とHostのBase64復元処理を削除した。
ページ内編集画面からのFile取り込みは変更していない。

ファイル数・転送量・保存量・形式・テクスチャ・ハッシュ・所有者の検証は既存関数を使う。
HostではIndexedDBの正式なメタデータを取得し、Coreが作品全体の参照と上限を照合する。
描画に必要な原本の取得経路は従来どおりであり、YouTubeの描画側から原本バッファがなくなる変更ではない。

切断、対象タブ変更、Studio終了時はAbortControllerで取り込みを中止し、一時`studio-upload-*` leaseを即時解放する。
既に送信した保存処理と解放処理はWorkerの変更キューで直列化される。
応答が後から届いた場合にも`finally`で解放する。Coreの履歴・保存・復旧用leaseは従来どおり保持する。

## navigator.serviceWorker.postMessageの実験

**転送できた。正式な経路には採用していない。**

`.work/studio-import-transfer`だけに実験用の受信コードを組み込み、Studioの
`navigator.serviceWorker.getRegistration().active.postMessage`でArrayBufferとMessagePortを転送した。
送信直後に元ArrayBufferの`byteLength === 0`となり、受信した実原本のハッシュが一致した。
detachは所有権移転の確認であり、ブラウザ内部でのコピーがないことまでは示さない。

Worker側は送信元Clientを確認し、既存の所有者検証・変更キュー・`importBatch`をそのまま使った。
毎回検証済みreceiptをクリアし、ハッシュと`inspectAsset`を各1回、VRMのテクスチャ検証を1回実行したことを数えた。
不正な先頭バイトは構造検証で拒否された。PNGテクスチャのIDATを壊したVRMも、
ハッシュ・構造検証の後のテクスチャ検証で拒否された。

同一Studio・Worker内で各5回。Fileの読み取り後、postMessage直前からStudioの同じ単調時計で測った。
受信ACKにはWorkerのClient照合を含む。完了には検証・IndexedDBへの保存・返信を含み、描画は含めない。

| 素材           | 受信ACK・中央値 | 受信ACK・最大 | 検証保存完了・中央値 | 検証保存完了・最大 |
| -------------- | --------------: | ------------: | -------------------: | -----------------: |
| PNG 1MB        |           3.5ms |         4.1ms |               10.1ms |             13.4ms |
| VRM 54.5366MiB |         241.2ms |       345.3ms |            1,037.3ms |          1,330.6ms |

Workerの停止は、テスト用Chromeの該当Worker targetだけをCDP `Target.closeTarget`で終了させた。
停止テストの考え方は[Chrome公式ガイド](https://developer.chrome.com/docs/extensions/how-to/test/test-serviceworker-termination-with-puppeteer)を参照した。

- **停止後の送信**: 取得済みのServiceWorker参照からpostMessageすると新しいWorkerが起動した。
  Workerごとの識別値が変わり、全検証を通過。VRMの検証保存完了まで1,477.9msだった。
- **処理途中の停止**: 全検証とIDB保存後、返信直前に意図的に止めた。
  保存済みメタデータは再起動後にも取得できたが、返信は届かず、実験の3秒deadlineで検出した。
  転送済みバッファはdetach済みで再利用できず、処理も自動再開されなかった。
- **元Fileから再送**: 新しいArrayBufferを読み直して転送し、全検証・同一ハッシュIDの保存に成功。
  1,370.4ms。中断した要求と再送の一時leaseは既存のrelease処理で解放した。

実験用の受信コード、計測ハーネス、未丸めのJSON結果は`.work`内だけに置いた。
通常のbackground、Manifest、Studioプロトコルには実験の入口を追加していない。

## 回帰確認と範囲

手元でlint、型チェック3構成、専用`.work`出力へのビルド、unit 182件が成功した。
`studio.spec.ts`、`side-panel.spec.ts`、`vrm-editor.spec.ts`のe2e 21件も成功。
33MiBの既存実GPUオプトインも有効にして確認した。

実Chromeで、StudioからWorkerへの直接アップロードと、Portのメッセージに素材IDしか含まれないことを確認した。
保存・Undo/Redo・復元は既存のCoreを使う。保存済みのアップロード応答をStudio内で保留し、
手動切断と対象タブ変更のそれぞれで、応答を解放する前に一時leaseが消えることを確認する回帰テストを追加した。
旧`import`は、有効なPNGを渡しても未対応操作として拒否される。

作品スキーマ、ページ内取り込み、通常版dist、mainは変更していない。
範囲外として、`src/browser/storage-adapter.ts`の素材参照数上限に`8`の直書きが残ることを確認した。今回の変更対象にはしていない。
