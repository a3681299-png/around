# G1.3：スクロール中も絵を出し続ける（調べと設計）

依頼（翔太、2026-11-03）：スクロール中も絵を出し続け、そのための仕事を基準内に収める。G1 の守る力は弱めない。今回はコードを変えず、調べた結果と設計だけを書く。

対象：`codex/creator-editor-spike` の `a94d231`（製品コードは G1.2 の最後 `4d3f39b` と同じ）。G1.2 の経緯と閉じた理由は [docs/g12-plan.md](g12-plan.md) の末尾、出発点の数値は [docs/g12-verification.md](g12-verification.md)。

## 結論（先に）

- **スクロール中に絵が消える原因は、HOLD を外していないことではなく、ページ全体の一様なスクロールを「操作部品が動いた」と数えていること。** スクロールのたびに、操作部品の矩形（画面座標）が変わって geometry の世代が上がる。止めた表示は「世代が 350ms 変わらない」まで戻らないので、約90ms間隔のホイールでは、最後のホイールの約0.5秒後まで戻らない（下の a）
- 画面に固定の層（screen 面）の切り抜きは、ページと一緒に動く部品を**縦の帯全体**で抜いている。ページの面（page 面）の切り抜きは文書の座標で描いている。どちらも、一様なスクロールでは**切り抜きが変わらない**作りになっている。だから、「ページ全体のスクロールで動いただけ」を、文書の座標で比べて「変化なし」と扱えば、守る力を弱めずに絵を出し続けられる見込みがある。切り抜きをスクロール量だけ動かすことは、page 面では文書の座標のまま描くことで済み、screen 面では動かす必要がない
- 隠れている間の仕事（b）と、動き続ける層の仕事（c）は、プロファイルを行単位で分けて場所が分かった。`applyLayout` の自己時間の約半分は**毎フレーム同じ値のスタイルを書き直していること**（node と controls で約160ms）。残りは、層ごとの `layers.find`（約60ms）、安全の記録の JSON 化（約26ms）、書いたあとに読む `overlaySlot` の computed style（約100ms、`fixedContainingBlock` の多く）。`rank2`・`above` は 200ms ごとの部品の読み直し（`capture`）の中で、変更前にも同じだけある
- 比べ方（d）：変更前でも止まらない条件（ポインターがリンクから遠い）を**正式な基準**にし、Codex の32層の条件を計測の場面として `scripts/g11` に入れる。ポインターがリンクの近くの条件は、変更前の仕事が 0 なので、差ではなく上限で見る
- `signal-timeline-live` に、ホイールでのスクロール中に GIF が見えていること（`visibility`）の判定を足す（e）。今のコードでは失敗するはずなので、0回目に足して、失敗することを先に確かめる
- 作業は4回（0〜3）。0回目は記録用のビルドで原因を確かめる回で、製品の動きは変えない

## a. SHIFTED・HOLD は、スクロールのどの変化で起きているか

### 検証の記録から分かること

`docs/benchmarks/g12-verification/visual-current.json` の `wheel`（rAF ごとの表示と `data-ww-safety`）を、最初のホイールからの時刻で並べた。

| 最初のホイールからの時刻 | scrollY | 表示   | 止めた理由                      |
| ------------------------ | ------- | ------ | ------------------------------- |
| −52ms                    | 0       | 見える | なし                            |
| −4ms                     | 90      | 隠れる | HOLD（部品が動いている間）      |
| 87ms                     | 90      | 隠れる | SHIFTED（部品の位置が変わった） |
| 2,704ms                  | 0       | 見える | なし                            |

ホイールは 0〜2,187ms に24回（間隔の中央値 約90ms）。**最初のホイールで HOLD、次の読み直しで SHIFTED に変わり、最後のホイールから約517ms 後に戻る。** その間に「見える」は1回もない。

### コードでの経路（`src/host/operation-guard.ts`・`src/host/operation-source.ts`）

1. **HOLD**：スクロールのイベントで、source が `geometryDirty` を立てて通知する（`operation-source.ts` の `changed`）。guard は通知を受けると `boundaryDirty` を立て、`invalidate(true)` で描く前に隠す。次の `sample` の `capture({ coalesce: true })` は、前の読み取りから 200ms（`COALESCE_MS`）以内なら古い snapshot を返し、`deferredFor() > 0` なので `stopped = HOLD`
2. **SHIFTED**：窓が明けて読み直すと、`boundaryKey` が前と違えば `pause(SHIFTED)`。`boundaryKey` は、ページと一緒に動く部品の `top`・`height` を除いているが、**`scrollBox`（中のスクロール領域・sticky の箱）は画面座標のまま入っている**。ページと一緒に動くスクロール領域の中の部品なら、一様なスクロールで `scrollBox.top` が変わる。もう1つの入口は `commit` の `source.validate(surfaces)` で、世代が変わっていれば同じ `SHIFTED` になる。どちらの入口だったかは、今の記録では区別できない
3. **戻らない理由**：`sample` は `surfaces.generation.geometry` が変わるたびに `stableAt = time` にし、止めた表示を戻すのは `time - stableAt >= 350` のときだけ。世代は `shape`（画面座標）を含む署名から決まるので、**一様なスクロールでも読み直すたびに世代が上がる**。約90ms間隔のホイールでは、200ms ごとの読み直しのたびに 350ms の待ちが最初からになる

まとめると、HOLD も SHIFTED も「ページ全体が一様に動いた」と「部品の並びが変わった」を区別していない。前者は、切り抜きの作りから見て、絵を隠す必要がない変化である（下の「守る力が弱まらないこと」）。

### まだ確かめていないこと（0回目で確かめる）

- SHIFTED を起こした `boundaryKey` の差分が、`scrollBox` なのか、見える部品の集合（遅れて読み込まれた行）なのか、`left`・`width` なのか。入口が `sample` か `commit` か
- YouTube がスクロールのたびに、source が見ている属性（`class`・`style`・`hidden` など）を部品やその祖先で書き換えているか。書き換えていれば、スクロールだけを区別しても HOLD は残る。そのときは、どの要素のどの属性かを記録し、対策を分けて考える

- mutation なしで文書の座標が変わる部品が YouTube にあるか（D7）。窓が明けた読み直しで、スクロールの通知だけだったのに文書の座標の署名が変わった部品を、要素と祖先の `content-visibility`・`animation-timeline`・`position: sticky` 付きで記録する

確かめ方：記録用のビルドフラグ（`WW_GUARD_TRACE` に足す。ソースの文字列の置き換えはしない）で、①世代が上がった理由（スクロールだけ／見える集合／矩形の変化、要素の id 付き）、②`boundaryKey` の差分の項目、③`pause(SHIFTED)` の入口、④HOLD の窓を開けた通知の種類（scroll・mutation・resize・focus）を `data-ww-guard-*` に残す。本物の YouTube で、Codex の条件（動く2層、約90ms間隔のホイール 24 回）を2回。

### 設計の案：一様なスクロールを「変化なし」として扱う

- source の snapshot に、**文書の座標で比べる世代**（`generation.layout`）を足す。署名は、ページと一緒に動く部品の `shape`・`protectedEnvelope` と、ページと一緒に動くスクロール領域の `scrollBox` を `scrollX`・`scrollY` だけずらしてから作る。sticky の縦の帯（±1e7）、画面に固定の部品（`scrolls: false`）は今のまま
- 今の `generation.geometry`（画面座標）は残す。描画が使う矩形は今と同じ画面座標
- guard の `boundaryKey` と `stableAt` は `generation.layout` で見る。一様なスクロールでは、SHIFTED にならず、待ちも最初からにならない
- **スクロールだけの通知では HOLD にしない。** source は「前の読み取りから、スクロールのイベントだけがあった」ことを覚えておく（mutation・resize・focus・fonts のどれか1つでも来たら、今と同じ扱い）。スクロールだけなら、窓の間は古い snapshot を**スクロール量だけずらした** snapshot として返し、`deferredFor()` は 0 にする。窓が明けたら今と同じく読み直して、`generation.layout` で答え合わせする（ずらした結果と読み直した結果が違えば、その時点で今と同じ SHIFTED）
- 中のスクロール領域（`nearestScroller`）がスクロールしたときのイベントは、ページ全体のスクロールではないので、今と同じ扱いにする（`event.target` が document のときだけ「スクロールだけ」）
- 入力のときの照合は今と同じく、毎回、新しく全体を読む（`validate(snapshot, event)`）。比べる世代を `layout` にするかは決めてもらう（下の D3）

### 守る力が弱まらないこと

| 保護                       | 一様なスクロールのとき                                                                                                                                                                                   |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| screen 面の切り抜き        | ページと一緒に動く部品は、画面の上端から下端までの縦の帯で抜いている（`sweptRegions`）。帯は `left`・`width` だけで決まり、スクロールで変わらない。compositor が先にスクロールしても、部品は帯の中にある |
| page 面の切り抜き          | 文書の座標で描いていて、面ごとページと一緒に動く。部品との位置関係はスクロールで変わらない                                                                                                               |
| 中のスクロール領域・sticky | page 面では `scrollBox` 全体（sticky は縦の帯全体）で抜いている。ページ全体のスクロールでは、文書の座標で変わらない。領域の中のスクロールは「スクロールだけ」と扱わない                                  |
| 入力のときの照合           | 今と同じく、入力のたびに新しく読み、押した点の要素を `elementFromPoint` で確かめる                                                                                                                       |
| 作品が入力を受けない作り   | 変えない                                                                                                                                                                                                 |

この表の前提は「スクロールで、文書の座標での部品の位置が変わらない」こと。スクロールに合わせてスクリプトで動く部品（スクロールで隠れるヘッダーなど）は mutation か、窓が明けたときの答え合わせで見つかり、今と同じ扱いになる。`content-visibility` や CSS のスクロール連動アニメーションのように、mutation なしで位置が変わるものは、200ms ごとの答え合わせまでの間、ずれうる（下の「危ないところ」）。

## b. 絵が隠れている間に、配置の計算と描画をしない

### 今の動き

隠れていても、world の評価（`world-session.ts` の `paint`）と `applyLayout` は毎フレーム動いている。動く層があると `needsFrame` が立ち、rAF が続くため。検証の4組では、スクロール中の rAF の呼び出しが 162〜170回 → 689〜771回。変更前に少なかったのは、ポインターがリンクの近くにあって全部の層を止めていた（`safeInteraction`）ため、動く層がなかったからである。

### 設計の案

- guard が「全部の層を隠している」（`stopped` があり、`stoppedIds` がない）ことを、`sample` の戻り値で world-session に渡す
- 全部を隠している間、world-session は `sample` だけ呼び、評価・`apply`・3D の評価をしない。rAF も次を頼まない。止めた表示が戻るきっかけは、guard の 360ms のタイマーと、source の通知の `invalidate`（どちらも今ある）。戻ったフレームで評価を再開する
- 時刻の扱いは、タブが隠れているとき（`environment.hidden`）と同じにする。3D は `suspended`・`dt = 0`、追従は前の状態から続ける。シグナルの規則は、戻ったフレームの値で評価する
- 一部の層だけを隠している（`stoppedIds`、ラッチした層）ときは、その層の DOM の書き込みだけを省く。評価は続ける（他の層が見えているため）
- 録画中・プレビュー中・devtools を開いている間は、評価を止めない（録画の時刻を飛ばさない）

a が入ると、隠れている時間そのものが短くなる。b は、a のあとに残る HOLD・SHIFTED（部品の並びが本当に変わったとき）と、ラッチした停止のための手当てになる。

## d. 性能の比べ方の定義

### 何がおかしかったか

## e. `signal-timeline-live` に「見えていること」を足す

今の判定は、スクロールの位置ごとに GIF の `style.opacity` が規則の値になるのを待つだけで、枠（`[data-image-id]`）の `visibility` は失敗したときの記録にしか使っていない。検証の3回では、ポインター区間の各20標本が **20/20 hidden** のまま通っていた。

足す判定（判定を強める方向の変更。既存の判定は1つも緩めない）：

1. 今の `verifyScroll` の待ちを、「不透明度が規則の値」**かつ**「枠の `visibility` が `hidden` でない」**かつ**「`data-ww-safety` の `stopped` が空」が同時に成り立つまで、に変える

### 3. `signal-timeline-live` の判定を強めた（e）

- 止まった位置ごとの待ちを「不透明度が規則の値」**かつ**「枠（`[data-image-id]`）の `visibility` が `hidden` でない」**かつ**「`data-ww-safety` の `stopped` が空」にした。media 要素そのものは、不透明度 0 のときに描画側が隠す（停止ではない）ので、見るのは枠の inline style と停止の記録
- 新しい区間「wheel scroll」：D9 の点にポインターを置いたまま、ホイールを下へ 12 回・上へ 12 回（約90ms間隔）。rAF ごとに枠の表示と停止を記録し、**理由の付かない隠れが 0 回**であることを判定する。記録用ビルドでは、部品が本当に増減・移動した読み直しの直後の停止から解除までを「理由付き」として別に数える（D5(b)）。ポインターから 72px 以内の部品の矩形も記録する
- 今のコードでの結果：**通常ビルド・記録用ビルドとも、狙いどおり新しい区間で失敗した**（隠れた rAF：通常 168/168、記録用 160/165。理由付きは 0）。止まった位置ごとの判定は両方とも通った（止まって 350ms たつと戻るため）。記録は `docs/benchmarks/g13-round0/trace/signal-live-*.json`

D9 との違い（判断）：D9 は「重なる層を隠す」。この計画では、隠す期間を「200ms の窓の間」ではなく「次のフレームまで」にする。mutation を受け取った時点で部品の矩形を確かめ、変わっていなければ、その部品は周りを動かしていない（D9 の絞る条件そのもの）ので、窓の終わりまで隠し続ける理由がない。変わっていれば、今と同じくその場で全部隠す（属性で部品そのものが動いた場合も、今より弱くならない）。再生中のシークバーのように毎フレーム属性が変わる部品の上で、層が出たり消えたりし続けるのを避けるため。矩形の読み取りは mutation のたびに起きるので、仕事の増え方は2回目の計測で見る。

足すテスト（先に書く。模擬ページの e2e、`tests/operation-safety.spec.ts`）：

- 一様なスクロールでは `generation.layout` と `boundaryKey` が変わらず、窓の間の snapshot はスクロール量だけずれ、`deferredFor()` は 0。窓が明けた読み直しでも `layout` は同じ
- 続けてスクロールしても、guard は止めず（`stopped` が空）、描いた層を隠さない
- 中のスクロール領域のスクロール、要素の追加、部品の要素の `style` で位置が変わったときは、今と同じく全部隠す（強める方向の確認）
- 部品の中の属性の変化（ホバーの class）は、その部品に重なる層だけを隠し、離れた層は隠さない。次のフレームで戻る
- スクロールの直後の押下は MOVED にならず、部品に届く。覆われた部品への押下は今と同じく止める
- 描画まで通した e2e：画面に固定の層が、ホイールでスクロールしている間ずっと見えていて、各フレームで、層の下を通る操作部品（別に読んだ snapshot で「切り抜きで抜く・覆ってはいけない・見える」もの）の中心が、切り抜きの描ける範囲に入っていない（`elementFromPoint` は拡張の層が入力を受けないので常に部品を返し、切り抜きの確かめにならないため、こちらにした）

### 止める報告（G1.3 の挑戦3回を使い切った）

#### 分かったこと

1. **スクロール中に絵が消える原因は取れた。** 原因は、ページ全体の一様なスクロールを「部品が動いた」と数えていたこと。文書の座標で比べ、ずらした読み取りを使うことで、遠い場面でほぼ 100%、近い場面で約 90% のフレームに絵が出るようになった（`4d3f39b` は 1〜3%）
2. **仕事は `4d3f39b` と同じ量に収まった。** 6組で、全部の場面の差が基準内（中央値 +0.10 以内、p95 +0.45 以内）。絵を出し続けるようになった分の増加は、描画の書き込みを減らす直し（c1〜c3）とずらした読み取りの軽量化、答え合わせの分割で相殺した
3. **D10 の p95 だけが届かない。** スクロールの場面の p95 は、同じビルドの定常より 1.45〜1.6ms 大きい。`4d3f39b`（絵はほぼ全部隠れている）でも +1.35〜1.5ms で、同じく届かない。答え合わせを1秒にしても変わらない
4. 近い場面で残る隠れの主な原因は、シークバーのホバー（矩形が実際に変わる）。①の差し替えは模擬ページでは働くが、YouTube のシークバーでは働いていない（理由は確かめていない）
5. `signal-timeline-live` の新しい判定は、ホイールの区間の隠れが 168/168 → 18/159 まで減ったが、0 にはなっていない

#### 原因の見立て（D10 の p95）

D10 の上限は、スクロールの場面と定常の場面の差を見ている。この作品では、スクロールの場面だけ 31 層の不透明度がスクロールに合わせて毎フレーム変わる（定常は1層が動くだけ）。そのため、スクロールの場面では world の評価と描画の書き込みが毎フレーム 32 層ぶん起きる。この差は、絵を隠していた `4d3f39b` でも同じだけある（隠していても評価と配置の計算はしていた）。答え合わせの間隔を変えても p95 が動かないことも、この見立てと合う。ただし、p95 のフレームで何が重いかを、プロファイルで切り分けてはいない（回数の上限のため）。
