# Studio の作業中のコピーと作品の保存

## 再現

Studio は作品を `storage.local` に保存し、作業中のコピーは対象タブ別に `storage.session` へ遅延書き込みしていた。作品の保存直後に Studio を閉じたり YouTube を再読み込みしたりすると、新しい保存済み作品と保存前のチェックポイントが併存する。YouTube 側にまだ編集セッションがあればそのセッションが優先されるが、再読み込み後の新しいセッションは保存済み作品を読んでから古いチェックポイントを適用していた。この時点で保存データ自体は新しく、古い内容はプレビューに出る。そこで保存すると、古い内容が保存される。

修正前の回帰テストでは、画像の取り込み後に保持したチェックポイントと、その後名前を変えて保存した作品を用意し、保存前のチェックポイントが残る順序を再現した。開き直した Studio に保存済みの名前が出ず、テストが落ちた。別タブで同じサイトの作品を保存した場合も、旧版は選択肢を出さずに作業中のコピーを復元し、テストが落ちた。時計の時刻や作品フォーマットの `schemaVersion` から、どちらの編集が先かは分からない。

## 復旧の規則

| 状態                                                                   | 開き直し時の扱い                                                                                         |
| ---------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| 同じ編集セッションの保存以前と確認できる                               | 保存済み作品を開く。現存するレイヤーの選択などは引き継げる。古い作品と Undo 履歴は適用しない             |
| コピーに未保存の差分がなく、保存時の基準が変わった                     | 保存済み作品を開く                                                                                       |
| 未保存の差分があり、コピーの基準と現在の保存済み作品が一致する         | コピー、選択、Undo 履歴を復元する                                                                        |
| 未保存の差分があり、別タブの保存と競合するか旧形式で基準を証明できない | 保存済み作品を表示し、作者が「保存済みの作品を使う」か「作業中のコピーを復元」を選ぶまでコピーを保持する |

作品を保存する書き込みに、編集セッション ID と保存時点の版を添える。復旧側は同じセッションの版だけを比較する。編集中に別タブから保存通知が届いても、作業中のコピーが出発点とした保存値を記録し続ける。接続が切れていた間に保存値が変わった場合は、同じ YouTube ページのメモリ上にドラフトが残っていても選択を出す。サイドパネルと別窓が接続したまま引き継ぐときは、両者が同じ編集セッションを使う。

競合中にウィンドウを閉じても候補を残す。「保存済みの作品を使う」を選んだら、保存済みの内容を基準とするクリーンなチェックポイントに置き換える。「作業中のコピーを復元」は未保存プレビューを開く。作品への書き込みは、復元後に作者が「保存」を押したときに行う。通常の明示的な編集終了では、その終了以前のチェックポイントを削除できる。サイドパネルと別窓のチェックポイント書き込みを対象タブ別に直列化し、遅い書き込みや削除が別の画面で記録された新しい版を消さないようにした。

保存の版は Studio 専用の別キーに置く。作品データとバックアップの形式、アセット検証、Chrome の権限は既存の経路を使う。定常時の描画・入力処理の性能は計測対象外とした。

## 確認結果

| 確認                             | 結果                                                                                                                                                                                  |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 型チェック・lint                 | 通過                                                                                                                                                                                  |
| unit                             | 601件通過、2件スキップ                                                                                                                                                                |
| 保存と復旧の繰り返し             | 既存のレイヤー編集2件・タイムライン1件と、新しい Studio 回帰3件を各10回実行。60件通過                                                                                                 |
| Windows e2e、1 worker、G1 両方式 | 454件中360件通過、89件スキップ、5件失敗。レイヤー編集12件、タイムラインの保存と再読込、Studio 13件、ネイティブサイドパネル10件は通過                                                  |
| 本物の YouTube                   | 未ログイン、表示あり・画面外で、名前を変えて保存、Studio を閉じて開き直す操作を3回ずつ2回実行。うち各2回で YouTube も再読み込み。毎回最後に保存した名前を確認し、開き直した画面も確認 |

全件実行で失敗したのは `editor-entry.spec.ts` の3件、`skin-verification.spec.ts` と `ui0d-emergency.spec.ts` の各1件。すべて Windows のネイティブキー送信後に期待した動作を観測できず、Studio 修正前（`086ef4a`）でも同じ5件が失敗した。キー送信の原因は未特定。既存の編集3件は同じ修正前の単発比較で通った。保存前のコピーを確実に残す新しい回帰テストでは、修正前の誤復旧を再現した。

全件の検出時に、前の塊で追加した Playground の JSON import が Node 24 で読み込めなかった。import 属性を別コミットで追加し、Playground の生成マネキンを使う e2e 6件が通過した。このブランチは push 時の CI 対象外。Windows のログと画面はローカルの `.work/studio-recovery-review` に置いた。

## Claude Code の独立確認

- 保存の直前に作業中のコピーが残っている状態で、保存直後に Studio を閉じて YouTube を再読み込みする。保存済みの内容が開き、復旧の選択が不要なこと。
- 2つの YouTube タブを使い、片方に未保存の変更を残してもう片方から保存する。復旧の選択を閉じて開き直しても候補が残り、両方の選択で作品の保存状態が期待どおりになること。
- サイドパネルと別窓を切り替え、すぐに編集を続ける。履歴と素材が引き継がれ、閉じた側の遅い書き込みで新しい作業が戻らないこと。
