# UI1 独立検証（2026-10-27）

UI1 は、この検証では全項目の合格にできない。petal のピンクの塊と読めない登録ボタンを再現した。9スライス用の素材でも動画カードの枠はサムネイルに覆われ、コメント入口では左端の文字が枠に重なる。変更前後の交互計測は、起動直後の p95 が +1.10ms で基準を超えた。

検証対象は `3e18edc`〜`97797dc`、比較元は `29b8d5b`。`git pull --ff-only origin codex/creator-editor-spike` は Already up to date。HEAD の `857ae43` はスキルの追加として対象から外した。実サイトはすべて未ログインの新規プロファイルを使った。

## ピンクの塊と文字の原因

証拠は [petal の再現](screenshots/ui1/verification/real-youtube-petal-reproduction.png)、[各部品と計測のJSON](benchmarks/ui1-verification-windows.json)。DevTools Protocol から拡張の isolated world を識別してCPUを読み、部品の `getComputedStyle()` とDOMRectは実ページで採取した。ソースの値だけから原因を決めていない。

`tests/fixtures/motion/petal.png` は **64×48px**。非透明な範囲は **x=4〜16、y=16〜31**（右下を除くbboxでは `[4,16,17,32]`）。画像全体が枠用の絵ではない。報告と同じ `slices={top:12,right:16,bottom:12,left:16}`、`scalePct=100` で再現した。

中央の32×24pxにも **左端の1列だけ** ピンクが入っている（元画像のx=16、RGBAは240/32/112/255）。この1列は `fill` で引き伸ばされる。実測幅1337.25pxの説明欄なら `(1337.25−32)÷32 = 40.789px`、高さ104pxなら `(104−24)×16÷24 = 53.333px` のピンクになる。左スライス内の絵とつながり、説明欄では幅約53px、高さ約53pxの塊になる。ボタンの幅では横方向の伸びが小さいため、小さな四角に見える。切り位置と素材の1列のはみ出しが、両方の見た目を作っていた。

| 項目                                    | 実測・計算済みスタイル                                     | 見た目への影響                                                                |
| --------------------------------------- | ---------------------------------------------------------- | ----------------------------------------------------------------------------- |
| `border-image-source`                   | `url("blob:https://www.youtube.com/<UUID>")`               | 画像は正しく読めている                                                        |
| `border-image-slice`                    | `12 16 fill`（4辺表記では12/16/12/16）                     | ピンクの大半は左の領域に入り、上・下・右の枠になる絵はほぼない                |
| `border-image-width`                    | `12px 16px`                                                | 左の小さな図形が縦方向に伸びる。説明欄では左端の塊が大きくなる                |
| `border-image-outset` / `repeat`        | `0` / `stretch`                                            | 枠は要素内に描かれ、左スライスが本物の文字の下まで来る                        |
| `background-color` / `background-image` | transparent / none                                         | 登録ボタンの元の黒い背景を消す                                                |
| 登録ボタンの元の色                      | 背景 `rgb(15,15,15)`、文字 `rgb(241,241,241)`              | 文字色は不変。透明な素材の下が白いページになり、白文字を読めなくする          |
| ネイティブのborder                      | ボタン0px/none、検索欄は上1・右0・下1・左1px               | ゼロborderでもborder-imageは描かれる。検索欄のnative borderを変更していない   |
| ネイティブのpadding                     | 登録ボタン左右16px、検索欄左16/右4px、説明欄0px            | 描く枠の幅に合わせて文字の余白は増えない。説明欄左端の絵と文字が重なる        |
| compact                                 | 対象部品に色fallbackを付けても、表示中の再現部品の印はnull | このピンクの塊はcompactの誤発動ではない。色fallbackなら source は none になる |

検証素材は [frame-light.png](../tests/fixtures/skins/frame-light.png) と [frame-dark.png](../tests/fixtures/skins/frame-dark.png)。96×96px、切り位置24px、角4個・辺4本を別色にした。倍率25%なら描く幅は6pxになる。倍率100%では上下の合計48pxが高さ32〜40pxを超え、ブラウザーが枠を比例縮小し、中央が消える。太い素材を小さいボタンへそのまま使うときの別の制限である。[CSSの描画規則](https://www.w3.org/TR/css-backgrounds-3/#border-image-width) に沿う。

ボタンにはYouTubeの `contribYtLightShapeStaticWashLightSolid` が残っている。実測は `background:rgba(255,255,255,0.15)`、`filter:blur(10px)`。枠の色に白が混ざるのはこの本物の描画による。検証用の画素判定では、この白との合成だけを許し、白一色・異なる色・隠れた枠は拒否する陽性/陰性対照を置いた。元の部品やこの効果を消してテストを通すことはしていない。

動画カードでは、素材を正してもサムネイルが左辺の上に描かれる。[動画カードの画像](screenshots/ui1/verification/video-card-frame-light.png) を参照。カードの背景へ描く現在の方式で、すべての子要素より枠が上に出る保証はない。padding追加はレイアウト不変の契約を破るので入れていない。枠用の描画面をアダプターが明示するか、要素の外側への描画を扱うかは、周囲への重なりとG1を含めて設計し直す必要がある。

コメント入口も [画像](screenshots/ui1/verification/comment-input-frame-light.png) の左端で `Add a comment…` の文字と6pxの枠が重なる。nativeの左paddingは0px、下paddingは4px、bottom borderは1px。十分に大きい要素でも、枠のための余白があるとは限らない。最終の8領域の画素判定は7部品が成功し、動画カードとコメント入口は失敗として残した。文字を隠したり、余白を追加して通したりしていない。

[明るい素材](screenshots/ui1/verification/subscribe-text-light.png) と [暗い素材](screenshots/ui1/verification/subscribe-text-dark.png) を実際に開いて確認した。中央の絵は文字の下に来る。白と黒、どちらかの素材ならすべての部品を読める、という設計にはできない。

提案は次のとおり。**今回は実装していない。**

- 編集画面で、通常・hover・選択中と明暗モードごとに実際の文字の下の背景を調べ、「読みにくいかもしれません」を出す。平均輝度だけで判定せず、文字の範囲の明るい箇所・暗い箇所も見る。
- 中央の絵を薄くするなら、nativeの背景を残して、その上の中央だけに不透明度を設ける。`border-image fill` は枠と中央の不透明度を分けられないので、方式と作品データの判断が必要。単一の不透明度上限だけで可読性を保証したとは言わない。
- 初期取り込み時に画像の寸法・非透明範囲、描く枠の上下/左右の合計、実際の最小部品サイズを見せる。petal のような画像と9スライス向けの素材を区別できるようにする。

`border-image` はnativeの `border-radius` で切れない。実ページでは登録ボタン20px、検索欄は左側40px指定、チップ8pxでも色付きの四角い角が見えた。

`.work/ui1-inspect.mjs` とチップを独立確認する `.work/ui1-chip-mask.mjs` だけで、nativeの寸法と各角の半径からSVGの白い角丸形を作り、ローカルBlobを `mask-image` として一時的に当てた。[登録ボタン](screenshots/ui1/verification/subscribe-button-mask-experiment.png)、[検索欄](screenshots/ui1/verification/search-box-mask-experiment.png)、[チップ](screenshots/ui1/verification/filter-chip-mask-experiment.png)。3部品のDOMRect、画面内5点の `elementFromPoint`、実Tab順が一致した。

角丸の描画には使える。ただしmaskは子要素もまとめて処理し、スタッキングコンテキストを作る。[Maskingの規則](https://www.w3.org/TR/css-masking-1/#the-mask-image)。全サイズ追従、楕円・割合の半径、フォーカスリングの見え方、G1との合成の全組み合わせは検証していない。製品に入れる前に別途検証が要る。`clip-path` は当たり判定を変えるので、この試作では使っていない。

## 性能

Windows 11 (`win32 10.0.26200`)、i7-13650HX、Node 24.16.0、Chromium 143.0.7499.4、1920×1080、deviceScaleFactor 1。URLは `https://www.youtube.com/results?search_query=lofi+hip+hop`。起動は遷移から6秒、定常は8秒待ってからスクロールする6秒、SPAは動画を開いてから6秒。広告や公開サイトの変化も含め、生データを捨てていない。拡張なしは測っていない。

通常と毎rAFに2msのビジーループを加えた計測版で先に校正した。中央値は **0.00→2.00ms**、p95も **0.00→2.00ms**。拡張のisolated worldのコールバックを拾っていた。0.00は全区間のCPUゼロという意味ではない。起動時や変化があるフレームへCPUが集中している。

元の道具には setInterval・Chromeイベント・一部のPromise/マイクロタスク等の取りこぼし、ネストした同期コールバックの二重計上、最初と最後のフレーム境界外のCPUを捨てる問題があった。これらを直し、コールバック種別の件数と合計の一致を記録した。読み込み直後も最初の区間へ含めた。非同期関数全体の経過時間をCPUへ足す測り方はしていない。

## 翔太が手動で確かめること

検証用の通常相当ビルドは、リポジトリ直下から `.work/creator-editor/.work/ui1-verify-final`。Chromeの拡張の読み込み先をこのディレクトリへ切り替え、ログインしたYouTubeを再読込して行う。計測カウンターは入っていない。

- ログインしたYouTubeで、既に登録しているチャンネルの動画を開く。登録前と登録済みの絵を別の色にし、強制表示を外してもnativeの登録状態に追従するか。通知のベルやドロップダウンを誤って同じ部品に含めないかも見る。
- 既に高評価している動画と、既に低評価している動画で、通常とselectedの絵を別色にする。強制表示を外し、nativeの `aria-pressed` と絵が一致するか、ボタンの文字・数値・クリック位置が変わらないか。
- コメントの入力欄をクリックして展開し、短い下書きを入力して消す。投稿しない。展開後の本物の入力欄に新しい印と着せ替えが付き、古い入口の印が残らないか、Tab/Shift+Tabと入力が使えるか。
- 上の状態でページを移動して戻り、シアターと全画面にも出入りする。nativeのメニュー、登録済みの状態、下書きの扱いが着せ替えで変わらないか。
- 明るい中央と暗い中央を切り替え、通常・hover・focus・selectedごとの本物の文字を明暗両モードで読む。最後に Alt+Shift+Q で着せ替えと一時プレビューが消え、nativeの見た目に戻ることを確認する。

利用者が実際に保存した過去のJSONはリポジトリにないため、そのデータの互換性は未確認のまま。
