## 古い位置の上限

通常版と同じく記録用の `AROUND_GUARD_TRACE` を外して source をブラウザーへ読み込み、実時間で2回確認した。source の読み取りそのものを観測して、対象の最後の `getBoundingClientRect` の時刻を取った。CSS アニメーションを1msの終端で pause し、DOM mutation を起こさずに対象を150px動かした。時計を制御した試しでも同じ経路を先に確認している。

| 実時間の回 | 最後に対象を確認した時刻 | 古い位置を返した時刻 | その確認からの経過 | snapshot / 実際の left | DOM mutation |
| ---------- | -----------------------: | -------------------: | -----------------: | ---------------------- | -----------: |
| 1          |                  390.9ms |              892.1ms |        **501.2ms** | 70 / 220px             |            0 |
| 2          |                  381.1ms |              886.8ms |        **505.7ms** | 70 / 220px             |            0 |

修正の定数で一周は6組×34ms、`TRUST_MS=200+204=404ms`。いずれもこれを超えた位置を返す。次の読み取り（1000.5 / 1013.3ms）で対象を読み直して220pxを返した。各時刻はプローブ開始からの相対値。フレームを待つ仕様を理由にした丸めの範囲ではなく、静かな読み取りの入口で確認を省く経路が原因。

手順は、全体を読む→約380msで最初の組を確認→その組の部品を動かす→約780msで残りの組を追いつき確認→約880msに再び読む、である。`sweep(now, catchUp)` は `sweepGroup` から残りだけを読む。一周が終わると `checkedAt=now` にするため、最初の組を読んでいなくても全体が今確認できた扱いになる。次は `now-checkedAt <= 200` に入り、その組の古い矩形を返す。`targetRead=false` と実際の矩形を同時に記録した。[再現コード](benchmarks/g13-fix-verification/repro/g13-fix-bound.spec.ts) / [全結果](benchmarks/g13-fix-verification/focused.json)。

今回確定したのは source の上限違反であり、この追加条件で本物の YouTube の操作部品が隠れるところまでは実証していない。長い読み取り間隔が必要な条件付きの不具合として扱う。影響は古い切り抜きの元になる位置を返すこと。操作面が隠れるなら頻度によらずその段階で直す対象だが、この追加再現の実描画への影響・発生頻度は未確認。依頼の②を満たしたとは判定できない。

直し方の案は、catch-up 時には古い組も含めて再確認するか、全体の確認時刻を各組の最も古い確認時刻で管理すること。部分的な確認を一周終了時の現在時刻へまとめて更新しない。製品コードは変更していない。
