# UI0-a：浮かぶエディターをデザインシステムに合わせる

ページの上に浮かぶエディター（`src/editor/panel.ts` の Shadow DOM。ポップアップの「エディターを開く」で出るもの）の見た目を、`docs/around-studio-design-system/` に合わせた。ボタンの文言・DOM の形・操作は変えていない（例外は下の「README と違う判断」の 1 か所の文言）。

## 変更点と理由

### 書体

- ネットワークから書体を読まない。同梱もしない。Chrome の権限は増やしていない。
- UI は `'BIZ UDPGothic', 'Hiragino Sans', 'Yu Gothic UI', 'Meiryo UI', 'Noto Sans JP', system-ui, sans-serif`。等幅は `'IBM Plex Mono', ui-monospace, 'SFMono-Regular', 'Cascadia Mono', Consolas, monospace`（Plex Mono は入っている PC でだけ使われる）。
- 実際に描かれた書体を CDP（`CSS.getPlatformFontsForNode`）で確かめた：見出しは `BIZ UDPGothic Bold`（`isCustomFont: false`＝PC に入っている書体）、英字の見出しは `Cascadia Mono`。

### Studio 系を旧スタイルのままにした理由

`panel.css` は浮かぶエディターだけでなく、Studio の作業台（`studio/workbench.ts`：Studio のウィンドウ・サイドパネル・ページ内 Studio・ページのツールバー）の土台にもなっていた。書き直した `panel.css` をそのまま共有すると、ページ内 Studio で `.editor-body` の新しい背景がキャンバスを覆い、YouTube が見えなくなった（`docs/screenshots/ui0a/` には直したあとの画像だけを置いた）。Studio は UI0-a の範囲外なので、作業台では変更前のスタイル（`src/studio/editor-base.css`・`editor-skin-base.css`）を使い、変更前と同じ見た目であることをページ内 Studio のスクリーンショットで確かめた。

## コントラスト

エディターの中の、見えていて有効な文字（見出し・ボタン・ラベル・ヒント・タブ・状態・保存のチップなど）の文字色と背景色の比。開いた直後・画像 2 枚・プロパティ・着せ替えの 4 場面で測った。

| テーマ | 最小   | どこ                                                                           | 変更前の最小                    |
| ------ | ------ | ------------------------------------------------------------------------------ | ------------------------------- |
| ダーク | 6.22:1 | `ink-muted`（WORLD CREATOR、ヒント、dense ボタン）                             | 7.07:1（ただし 9〜11px の文字） |
| ライト | 5.13:1 | `ink-muted` の「×」（ガイドを閉じる、`surface-sunk` の上）と選ばれていないタブ | 7.07:1                          |

主ボタン（`on-cobalt` on `cobalt`）はダーク 7.35:1、ライト 7.07:1。すべて 4.5:1 以上。変更前より比は下がったが、文字は 9〜11px から 12〜13px に上がった。

## 計測

交互計測はしていない。ページの上で動く処理（content script の動き・`src/sites/`・`src/world/`・`src/host/`・描画）を変えていないため。変えたのはエディターの Shadow DOM の中の CSS と、どの CSS を入れるかの分岐だけ。content script のファイルは CSS の文字列が増えて 3,044,345 → 3,078,896 バイト（+34.5KB、+1.1%）。

### 途中で見つけた不具合

- 文字を 12〜13px・行の高さ 20 に上げ、ボタンを 32 にしたことで、1100×760 でレイヤー一覧の高さが 0 になり、行がフッターの下に隠れて押せなくなった（e2e 4 件の失敗。操作が破綻する種類）。ヘッダーを 2 行にまとめ、保存のチップをヘッダーへ移してツールバーを 1 行にし、帯の余白を 12 → 8 に詰め、レイヤー行の上下の余白をなくした。一覧の高さは 65px（変更前 68px）、行の高さは 42px（変更前 48px）で、変更前と同じく 1.5 行ほど見える。
- 押されたツールにマウスが乗っていると、hover の色が cobalt を上書きしていた。押された状態を優先するようにした。
- 左に寄せたときの位置の e2e は、14 → 20 を README に合わせた変更として期待値を直した。

## 未確認の点・気になっている点

- Studio のウィンドウとサイドパネルは撮影していない。旧スタイルの複製を使うので変わらないはずで、ページ内 Studio は変更前後で同じことを画像で確かめた。
- 狭い画面（幅 740 以下）と低い画面（高さ 630 以下）の見た目は撮っていない（e2e の 430×650 の確認は通っている）。
- `prefers-reduced-motion` で動かないことは CSS で止めているだけで、実機で確かめていない。
- 1100×760 ではレイヤー一覧が 1.5 行分しかない（変更前と同程度）。13/20 の文字のままさらに広げるには、ガイドや選択の帯の構成を変える必要がある（UI0-b）。
- 着せ替えのスライス画面（絵を取り込んだあと）は撮っていない。`skin-editor` の e2e（線のドラッグ）は通っている。
- ライトは OS・ブラウザの設定に従う。YouTube をダークで見ていても、OS がライトならエディターはライトになる。

- ページの上の印：`around-mark`・`around-tag`・`around-unsupported`・`around-protect`（`controller.ts` の紫の点線 #695089 の置き換え）
- `around-scrub`（数値欄の軸の文字。いまは「X」「Y」が UI の書体）、`around-segs`、`around-notice`・`around-chip--limited`（制限中）
- 「−」「×」の文字の記号をアイコンにする。アイコンを 14px の作図の決まりで描き直す
- DOM に `around-*` のクラスを付けて、部品として共有する（いまは既存のクラスに決まりを当てただけ）
- パネルの幅 340（`workspace.ts` の幅の操作）
- Studio の作業台（ウィンドウ・サイドパネル・ページ内 Studio）を移し、`src/studio/editor-base.css`・`editor-skin-base.css` を消す
- エラーの意味の割り当て（保存失敗を何色・何の形で出すか）、YouTube のテーマとの連動

## 次の担当への引き継ぎ

- `panel.css` は浮かぶエディター専用になった。Studio の見た目を直すときは `src/studio/editor-base.css` か `workbench.css` を見る。`panel.ts` の `workbench` の分岐を忘れると、片方だけ直したつもりになる。
- 保存のチップ（`.dirty`）は `.toolbar` の中にあるが、`main` を基準に `top: 32px` でヘッダーの 2 行目へ置いている。ヘッダーの 1 行目の高さ（32）を変えるときは一緒に直す。
- 縦の余白は 1100×760 でレイヤー一覧が押せるぎりぎり。行や帯を足すときは `editor-ux.spec.ts` の「group reasons …」を回す（一覧が狭いと最初に落ちる）。（追記：このあとの「低い画面の修正」で、一覧は最低 2 行分を持ち、足りない分は外側がスクロールするようにした。行や帯を足すときは「a low window …」も回す）

## 追加の確認：低い画面でレイヤー一覧が押せるか（2026-10-29）

## 低い画面の修正（案 A）

原因：一覧（`.layers`）は `min-height: 0` で、上の「素材の追加」と「操作ガイド」は縮まない。そのため高さ 631〜736 では、ガイドが出たまま一覧が行 1 つ分より低くつぶれ、一番下の行がフッターの下に隠れて押せなかった。高さ 630 以下はガイドを隠す既存の決まりで助かっていた。UI0-a の前からある不具合なので、UI0-a のスタイルとは別のコミットにした。

### 進め方

1. 先に `editor-ux.spec.ts` へ「1366×657 で、ガイドを出したまま、レイヤー 3 つの一番下の行を押して選べる」テストを足した。人と同じ操作（ガイドの上でホイール → 一覧の上でホイール → 行の中心をクリック）で確かめる。修正前のコード（`92e113b` をビルドしたもの）では、一覧が画面に入らずに失敗することを確かめてから直した。
2. 「32 layers keep one list scroll」が守っているものを読んだ。`docs/editor-ux.md` の「各作業領域にスクロールを一つだけ設け、保存と履歴は固定する」に対応し、テストは次の 3 つを確かめている：32 行が一覧の中のスクロールだけで最後まで見られる、`.editor-body` は動かない（`scrollTop` が 0）、「元に戻す」と「保存」が画面に残る。A でもこの 3 つは変わらない。外側の入れ物（`.layers-pane`）がスクロールするのは、一覧が 2 行分を割るほど低い画面のときだけで、そのときも履歴と保存は外にあって動かない。このテストはガイドを閉じた 1100×760 で動き、外側はスクロールしない。テストは変えていない。
3. ホイールは JS で扱っていない。ブラウザの標準のスクロールの連鎖（一覧の端 → 外側）だけ。

### 気になっている点

- 657・700 では、開いた直後は一覧が見えていない（外側を下へ回すと出てくる）。「押せない」ことはなくなったが、「一覧があることに気づく」のは UI0-a の前より遅い。ガイドを閉じれば一覧は最初から見える。ガイドの出し方（たたむ、一覧の下に置く）は UI0-b で考えたい。
- 一覧がはみ出していない（行が少ない）ときに一覧の上でホイールを回すと、YouTube のページが動く。ブラウザがはみ出しのない入れ物を連鎖に入れないためで、UI0-a の前から同じ（修正前のビルドの 900 の高さで、ページが 2205px 動いた）。今回は直していない。
- スクロール状態のクエリがない Chrome 120〜132 では、一覧の端から外側へは連鎖しない（ページへも漏れない）。その場合、外側はガイドや素材の追加の上でホイールを回して動かす。この版の Chrome では確かめていない。

### CI の失敗と修正（`f328bd7` の e2e shard 1/4）

- 落ちたテスト：`editor-ux.spec.ts` の「workspace width, docking, collapse, tabs and menu keys …」。行の「…」でメニューを開き、↓ と Esc のあとで「1個選択中」のはずが「0個選択中」だった。
- 手元で `--repeat-each=10`：`f328bd7` のビルドで 10 回中 8 回失敗、`92e113b`（修正前）のビルドで 10 回とも成功。ときどきではなく、案 A の変更で起きる。Linux・xvfb・書体の違いではない（Windows でも同じく落ちる）。
- 原因：1100×760 で「並べる」などのあと、外側（`.layers-pane`）が 39px スクロールできる状態になり、一番下の行の「…」が 4px 隠れていた。Playwright はクリックの前にボタンを画面へ入れるため外側を 26 → 30 へスクロールする。スクロールの通知は次のフレームで届くので、クリックで開いたメニューを、ワークスペースの「スクロールしたらメニューを閉じる」処理（`workspace.ts`）がすぐに閉じていた。メニューがない状態の Esc は「選択解除」なので、選択が 0 になった。案 A の前は外側がスクロールしなかったので起きなかった。
- 人の操作でも同じ競合が起こりうる（右クリックの直前にホイールを回したときなど）。テストは変えず、製品側を直した：メニューを開いた時点の各スクロール位置を覚え、その位置から動いたスクロールのときだけメニューを閉じる。開く前のスクロールの遅れた通知では閉じない。
- 確かめたこと：同じテストを `--repeat-each=10` で 10 回成功。「a low window …」に「メニューは開いたまま残り、開いたあとに一覧をスクロールすると閉じる」を足し、`--repeat-each=5` で 5 回成功。
