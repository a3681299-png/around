# ミルドの独立検証（Windows）

2026-11-07。対象は `codex/mirdo-character` の `b3db85e`、比較は分岐元 `c69d9bb`。塊4の再検証後に実施した。製品とテストは変更せず、試験用の計測と動画収録は検証環境に限った。 [実装報告](https://github.com/a3681299-png/web-world-themes/blob/b3db85e/docs/characters/mirdo.md) · [塊4の再検証](../chunk4-reverification-windows.md)

**判定は不合格。** 実サイトでミルドの取り込み、下の縁での着座、座る・立つ動作を確認した。起動直後の長い処理と動画の落ち、検索 SPA の長い処理と CPU 合計が、同版の振れを超えた。定常は A/B の増加が基準内だったが、同版の振れが p95 の許容差を超えたため、デスクトップでの合否は保留。

## 取り込み、動き、素材

- 新しいキャラの自律は on。既存データは指定済みの on/off を保ち、項目のない過去データは off。取り込みでプレーヤーが見つかると既定は右下（x 0.90、y 0.74、150×190）。プレーヤーがない場合、または作者が落とす点を指定した場合は画面基準。unit とエディターの e2e で確認した。
- 保存形式の版と Chrome 権限に差分なし。元パッケージ、変換した VRM、全19本の VRMA の21ファイルを Git オブジェクトとハッシュで照合し、一致0件。ブランチ差分に画像、モデル、動画、アーカイブは追加されていない。
- `models.ts` の待機選択は、縁から離れて休む・到着したときに、使える `idle` 役割のループを配列の先頭から選ぶ。腰の上下方向から一度だけの `sit` 役を判定し、座る・立つの入り口に使う。逃げる場合は立ち上がりを省く。歩行中は進行方向へ回り、休止時は正面へ戻る。待機ループを持たない作品では座りループへフォールバックし、下の縁から138 px離れた最初のフレームで座る重み1を観測した。ミルドのように待機ループを持つ構成と分けて扱う。

元の変換済み VRM と19本で崩れ判定を再実行し、14本合格・5本除外だった。提供された合格フォルダーの14本と一致した。実装報告の「15本」はこの素材一式では再現しなかった。

| 対象                               | 自動判定と画像                                                                                                              |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Walk_Loop／Walk_Formal_Loop        | すべり約17%／16%で除外（線は15%）。コマを並べた画像では大きな体の崩れは見えず、接地中の足のずれは静止画だけでは判別できない |

実サイトで14本を取り込むのに3.19秒。既定の右下配置、自律 on、休む・うとうと＝Sitting_Idle_Loop、逃げる・戻る＝Jog_Fwd_Loop、近づくは割り当てなしを確認した。待機用の最初のループは Crouch_Idle_Loop で、縁から離れた待機ではしゃがんだ姿勢になった。

既存の `character-import-live.spec.ts` は、待機を確認する時点でまだ `return` のため1件失敗した。この回は画面に YouTube Music の案内が出ていた。逃走と戻りはどちらも Jog_Fwd_Loop で、帰着後に Sitting_Enter → Sitting_Idle_Loop を確認。実サイトで採った3,397コマ（rAF 中央値6.1 ms、p95 30.2 ms）のうち、落ち着いて座った588コマの箱中心と下端の最大差は0.016 px、箱と座り重みの飛びは0、ポインター直上の426コマの HOLD は0だった。

別プロファイルの追試では案内の閉じる操作後に待機・着座を確認し、バーが出た前後とも同じクリップ、座り重み1、同じ位置（箱中心と下端の差0.016 px）だった。進捗バー上のヒットは YouTube の要素で、画像でもバーが手前だった。バーが隠れても浮きは見えず、下端から外へ出た脚はプレーヤーの境界で切れる。この追試では主画面165 Hz、撮影後に採った短い区間の rAF 中央値は12.1 msだった。

## ワールド記録

- `c69d9bb` で作成した formatVersion 3 の画像作品の記録を `b3db85e` で再生し、144フレームと最終状態が完全一致した。
- `seats`、`seat`、`seatWeight`、`transition` は省略可。新版の座り遷移中の状態と入力を個別に JSON から読み直し、4項目を保持した。不正な辺・部品 ID・型を3件とも拒否した。テイクは引き続きアダプター由来の `seats` を保存しない。
- キャラ付き VRM の開発用ワールド録画は、両版とも開始時点で「デザインの形式が不正です。」を返した。記録のシーンを DesignDocument v10 として検査する既存の経路で、キャラ付きレイヤーを受け取れない。このためミルドを含む開発用ワールド記録全体の往復は未確認。下記のレビュー動画はブラウザーの描画を録画したもの。

## 165 Hz での座りと速度

同一の座り・立ち・歩行・走行を評価器に60 Hzと165 Hzの時刻列で渡した。停止状態と移動状態を含む20秒を採った。

| 時刻列 | 座り重みの最大変化／コマ | 歩行 px/s | 走行 px/s | 歩行／走行の再生倍率 |
| ------ | -----------------------: | --------: | --------: | -------------------: |
| 60 Hz  |                    0.052 |     48.00 |    160.20 |                 1.50 |
| 165 Hz |                    0.019 |     47.85 |    160.05 |                 1.50 |

座り重みは0〜1を通り、移動中の跳ねは0。左へ進む際の yaw は約−90°へ収束した。0.4秒の立ち上がりと0.5秒の着座を双方で観測した。歩行と走行の0.15 px/sの差は、座標が0.01 px刻みに丸められた時系列から計算した値。

## 性能

Ryzen 5 5600X、Radeon RX 6800（ANGLE／D3D11）、Windows 11 Pro 26H2、Chromium 153.0.8010.12。表示あり・画面外、1920×1080、DPR 1、主画面60 Hz。ミルドと同じ14本の割り当てを一つの検証専用の未ログインプロファイルで読み、拡張 ID と設定を保って各版で Chromium を起動し直した。

1ブロックは旧版2回と新版1回。奇数は A0→A1→B、偶数は B→A1→A0 とし、同じブロックから A1−A0（同版対照）と B−A0（変更前後）を取った。起動は実動画への遷移から6秒、定常は6秒待ってカーソルをプレーヤーに毎秒出し入れする6秒、検索 SPA はマネキンの代わりにミルドが50 pxを超えて逃走したことを見てから `lofi` を送信する6秒。

CDP は拡張 URL の V8 自己時間（500 μs 間隔）を主指標にした。同じ窓で g11 の拡張 rAF コールバック経過時間も採った。g11 校正の2 ms追加は中央値 +2.00 ms。長い処理はページの50 ms以上の件数。動画の落ちは `getVideoPlaybackQuality()` の差分で、検索後は旧動画が外れるまで採った。広告、動画・モデル未描画、時計の照合や6秒窓が成立しない回は除外し、同じブロックの不足場面を取り直した。予備計測で旧文書の時計を拾ったため、現文書の `performance.now()` と CDP の時刻を突き合わせて採り直した。背景 CPU は起動前の参考値で、除外には使っていない。

各場面で同版対照8組と変更前後8組。表は B−A0、括弧内は A1−A0 の範囲。起動と検索は増加側の上限を超えた組を数えた。

| 場面     |                 CDP 拡張 CPU 6秒合計 (ms) | ページの50 ms以上の処理（件） |          動画の落ち（枚） |
| -------- | ----------------------------------------: | ----------------------------: | ------------------------: |
| 起動     | −168.8〜+144.1（−184.4〜+157.8）、超過0/8 |    −4〜+7（−10〜+4）、超過2/8 | −1〜+2（−1〜+1）、超過1/8 |
| 検索 SPA |    −14.2〜+102.1（−83.5〜+34.4）、超過3/8 |     +2〜+6（−2〜+3）、超過3/8 |           0（0）、超過0/8 |

起動の CDP 合計の組差中央値は +1.5 ms、検索は +13.1 ms。検索では8組すべてで長い処理が2〜6件増えた。参考の g11 合計は、起動で1/8、検索で4/8が同じ方式の A/A 上限を超えた。起動時の再生開始の差も大きく、落ちを数えた総フレームの組差は −26〜+59枚だった。

| 定常の指標               | A/B の組差範囲 | 同版の組差範囲 |
| ------------------------ | -------------: | -------------: |
| CDP 中央値 (ms/フレーム) | −0.138〜+0.010 | −0.123〜+0.033 |
| CDP p95 (ms/フレーム)    | −2.569〜+0.972 | −2.614〜+0.236 |
| g11 中央値 (ms/フレーム) |   −0.40〜+0.20 |   −0.60〜+0.10 |
| g11 p95 (ms/フレーム)    |   −1.60〜+1.00 |   −1.40〜+0.30 |

A/B の全組は中央値 +0.5 ms、p95 +1 ms以内。長い処理と動画落ちはすべて組差0だった。A/A の p95 の振れは CDP で2.614 ms、g11 で1.40 msと定常の許容差1 msを超えたため、AGENTS.md の PC 条件に従い、定常の判定にはノート PC での取り直しが必要。

GPU の参考値には描画のタイマークエリを使用した。起動の GPU p95 は全8組で増え、定常・検索では増減が混在した。タイマークエリが取得できた窓のサンプルと、CPU プロファイルの自己時間上位を要約に含めた。 [計測の全組・除外理由](../benchmarks/mirdo-verification-windows-2026-11-07.json)
