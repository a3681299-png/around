# WWT 製品設計：キャラが住むYouTube

Nov 3, 2026 · @翔太

## 核

**いつものYouTubeに、あなたのキャラが住む。** UIが変わらなくても、日常のページにキャラが暮らしているだけで、見た瞬間に「何これ」となる。UIの着せ替え（部品に画像や色を当てて見た目を作り替える機能）は、2026-11-06 に一旦外した。UI は着せ替えるのではなく、3D の世界の一部（ガラスの板・光が当たる面・キャラが触れる場所）として扱う。着せ替えは、需要が分かれば戻せる形で凍結している（下の「UIの着せ替えを外す」）。

デスクトップペット（しめじ・伺か・Bongo Catなど）との違いは、WWTが**ページの中身を分かっている**こと。これが、デスクトップアプリではなく拡張機能で作る理由になる。

- **部品が分かる**：動画カードに座る、プレーヤーの縁を歩く、再生ボタンの近くではよける
- **動画が分かる**：曲に合わせて踊る、動画が止まったら振り向く
- **操作を壊さない**：キャラがどこにいても、YouTubeのボタンは押せる（G1）

デスクトップのほかのアプリには、DOMのような中身の手がかりがない。上の3つは、Webページだからできる。

## キャラの形式

キャラは3DのVRM、動作は名前の決まった標準セット（.vrma）。人型の骨の名前が決まっているので、同じ動作がどのモデルにも使える。

- **モデル**：VRM（人型）。WWTはもうVRMとGLBを読める
- **動作**：VRM Animation（.vrma）。標準のセットは、**自由に配れる動作だけ**で作る（2026-11-07 決定）。土台は CC0 の動作セット（[Quaternius の Universal Animation Library](https://quaternius.itch.io/universal-animation-library)、120 以上、商用・配布とも自由）と翔太が作る動作・姿勢。使う前に、ダウンロードした版に付いているライセンスの文を確かめ、出どころを記録する。Mixamo の動作は、生のファイルを配ることが禁止されていて、モデルに組み込んだ .glb も誰でも取り出せるので、標準のセットにも Playground にも入れない（翔太の手元の作品と、描いた結果だけを見せる動画には使える）
- **足りない動作**：近いもので代わりに出す（「走る」がなければ「歩く」を速く）。最初は待つ・歩く・座るの3つから始められる

標準の動作の名前（案）

| 名前  | 動作     | 代わり                     |
| ----- | -------- | -------------------------- |
| idle  | 待つ     | —（必須）                  |
| walk  | 歩く     | —（必須）                  |
| sit   | 座る     | —（必須）                  |
| run   | 走る     | walk を速く                |
| jump  | 跳ぶ     | なし（段差を歩いて下りる） |
| sleep | 寝る     | sit                        |
| peek  | 覗き込む | idle                       |
| happy | 喜ぶ     | idle                       |
| dodge | よける   | walk                       |
| dance | 踊る     | idle                       |

**モデルの権利**：販売されているモデルは、利用規約で再配布が禁止されていることが多い。作品を配るときは、作品にモデルを含めず、「モデルは各自が入れる」形にする。動作（.vrma）と性格・行動の設定だけを配る。

最初のキャラは「Trusie トルーシェ」（もち山金魚さん）。宣伝のために使うことは、作者から了承を得ている。製品に埋め込んで売ることはしない。リポジトリにはコミットしない（`WW_VRM_FILE` で指定）。

### 読み込むだけで、感情に応じて動く（2026-11-06 決定）

**原則**：作者がキャラと動作を読み込んだら、何も設定しなくても、キャラが感情に応じて自律して動く。作者は自動の結果を見て、気に入らない所だけ直す。動作を1本ずつ行動に割り当てる作業は、作者に求めない。

- **まとめて読み込む**：VRM は決まりの上でアニメーションを中に持てないので、モデル（.vrm）と動作（.vrma）を1回の読み込みでまとめて選ぶ（フォルダごと選べる）。FBX・GLB はファイルの中のアニメーションをそのまま使う（R7）。どの入口も、読み込んだあとは同じ仕組みを通る
- **当てて、直して、試す（2026-11-07 決定）**：体型が普通でないとき（デフォルメ体型など）でも、標準の動作をまとめて切らない。1本ずつそのキャラに当てて自動で補正し（腰の高さ、足の接地を IK で、足の長さに合わせた歩幅、腕を開いて体に入らないように）、見えない所で一度再生して崩れ（手が体に入る、足が浮く・すべる、床に沈む）を自動で測る。通った動作だけを、そのキャラの動作として残す。作者には「使える動作 14本・崩れたので外した 6本」のように結果だけを見せる。最初の試験台はミルド（頭身 3.6）
- **必ず暮らし始める**：無い動作は代わり（走る → 速く歩く）、それも無ければ計算の動き（呼吸・揺れ・視線・跳ねる・瞬間移動）で埋める。取り込んだ直後は、プレーヤー基準の見える置き場所に出す
- **動作を自動で見分ける**：動作の名前（Idle・Walking・Sitting・Jumping など、よく使われる名前）と、動作そのものの測定（腰が進む距離 → 移動、腰が下がって止まる → 座る、腰が上に跳ねる → 跳ぶ、ほとんど動かずくり返す → 待機、動きが大きく弾む → 喜び）を組み合わせて、役割と感じ（楽しい・怖い・眠いなど）を決める。使う区間（ループする所）と速さも自動で探す。名前と測定が食い違うときは測定を優先し、確かさが低いものは「身ぶり」として控えめに使う
- **感情につなぐ**：自律は、今の内部状態（退屈・警戒・眠気）を、喜び・怖さ・好奇心まで広げ、感情の状態に合う感じの動作を選ぶ。合う動作がないときは、計算の動き（呼吸・揺れ・視線）で埋める
- **コンテストでは**：Playground のキャラは翔太が選んだミルドだけにする。見る人が自分のモデルを入れる入口は作らない（2026-11-07）。取り込みの自動の仕組みは、ミルドで確かめながら作り、コンテストのあとに誰のキャラにも効く形へ広げる
- **作者は直すだけ**：エディターに自動の結果（どの動作をどの行動・感じに当てたか、確かさ）を見せ、作者は入れ替え・外す・区間の調整だけをする
- **操作性**：読み込みから、キャラが YouTube の上で動き出すまでを、作者の操作なしでつなぐ。カーソルを動かしてもキャラがちらつかないこと（塊4の重なりの方式）を前提にする
- **順番**：VRM のまとめた読み込みと、自動の見分け・割り当ては、デモのトルーシェ（Mixamo の36本）に効くのでコンテストの前に入れる。感情の幅を広げる部分は、11/26 の自律の自然さの確認と合わせて進める。FBX・GLB のファイルの中のアニメーションは R7

### 取り込める形式：VRM と FBX

**エンジンの中では、骨の対応・表情・揺れもの・材質を「中の形」として持つ。** VRM はそのまま中の形になり、FBX は取り込むときに変換する。動きの仕組みは1つで済ませ、R3 で骨の扱いを VRM に縛られない形で作る。VRChat のアバターの多くは FBX と unitypackage で配布されているので、FBX の取り込みは買う理由になる。

| FBX に足りないもの | 取り込みでやること                                                                                   |
| ------------------ | ---------------------------------------------------------------------------------------------------- |
| 骨の対応           | よくある名前の辞書（VRChat・Unity・VRoid・Mixamo）で自動で対応付け、骨の図で確かめて直せる画面を出す |
| 材質               | テクスチャを読み込んでトゥーン調の材質にする（lilToon の見た目そのままは無理）                       |
| 表情               | VRChat の口の形とまばたきは名前で対応付ける。喜怒哀楽は、あれば選んでもらい、なければ表情なしで動く  |
| 揺れもの           | 「Hair」「Skirt」などの名前の骨に、簡単な揺れを自動で付ける（あとで調整できる）                      |

unitypackage の中身（FBX とテクスチャ）を直接取り出せれば、「BOOTH で買ったファイルをそのまま落とすだけ」にできる。取り込むときに、「アバターの規約で、ほかのアプリでの使用が許されているか確かめてください」と案内を出す。順番は、VRM で動きが綺麗に動くのを確かめてから（R7）。

### 動きの3段階：体型に左右されるかで線を引く

アバターは頭身も足の長さもばらばらで、同じ歩く動作を当てても崩れる。線は「体型に左右される動きか」で引く。

| 段階                | 対象         | 動き                                                                                                        |
| ------------------- | ------------ | ----------------------------------------------------------------------------------------------------------- |
| 1. 読み込むだけ     | どの人型でも | 視線と顔の向き、まばたき、呼吸、揺れもの、表情、横に揺れる、跳ねる、震える、瞬間移動、計算で作る座り方      |
| 2. 標準の動作・姿勢 | 普通の体型   | 翔太が作る標準の .vrma と姿勢に、自動の補正（腰の高さ、足の接地、足の長さに合わせた速さ、腕の開き）をかける |
| 3. 作者の動作       | 作者が作る   | トルーシェのように、そのキャラ専用に作った動作                                                              |

- **体型を測って自動で決める**：読み込んだときに、頭の大きさと身長の比、足と腕の長さを測る。標準の動作が崩れる体型なら段階1の動きに切り替え、使う人にそのことを表示する。手で変えることもできる
- **歩かずに移る**：遠い所へは瞬間移動（ノイズが走って消え、別の部品に現れる）、近い所へは跳ねて移る。移る先はランダムではなく、きっかけ（カーソル、新しいコメント、動画の停止、怖いもの）で選ぶ。部品の上を横切らないので G1 とも合う
- **姿勢の反映**：翔太が作る姿勢は、1コマの .vrma（人型の骨ごとの角度）と、「どこが何に触れるか」の印（お尻は縁、両手はひざ、足は床など）。使う人のキャラには同じ角度を当て、触れる所はエンジンが IK で合わせ、体にめり込む所は少し押し出す。届かない所はあきらめるか、より単純な姿勢に切り替える
- **座り方は下に何があるかで分ける**：操作部品に重なった絵は切り抜かれるので、動画カードやボタンの上では体育座り・横座り・寝転ぶ（縁より下に何も出さない）。プレーヤーの上の縁（下は動画）やページの余白では、足を下ろしてぶらぶらさせる

## 動きの設計の段階

誰もがタイムラインを作るわけではないので、手間の違う段階を用意する。上の段階ほど簡単で、下の段階ほど作者の思いどおりになる。どの段階も重ねて使える（性格で暮らしつつ、サビだけ踊る、など）。

| 段階                  | 作者がやること                                                               | キャラの動き                                               | エンジン           |
| --------------------- | ---------------------------------------------------------------------------- | ---------------------------------------------------------- | ------------------ |
| 0. 性格を選ぶ（後で） | 「怖がり」「飽きっぽい」などを選ぶだけ。中身は感情の上がり方・下がり方の数値 | 同じ動作セットでも、感情の動き方が変わって暮らし方が変わる | 新しく作る         |
| 1. 場所と動作         | 部品やページの場所に「ここでは座る」を指定する                               | 指定した場所の間を、歩く・走る・跳ぶを自動で選んで移動する | 新しく作る         |
| 2. きっかけと反応     | 「動画が止まったら振り向く」「サビで踊る」を並べる                           | シグナル（再生・停止・音・スクロール・マウス）に反応する   | シグナルがある     |
| 3. 演技で記録         | ページの上でキャラをドラッグして動かし、そのまま記録する                     | 記録した動きをそのまま再生する                             | テイクの記録がある |
| 4. タイムライン       | 時間の上で細かく作る                                                         | 作者の思いどおり                                           | タイムラインがある |

新しく作るのは1と、感情の仕組み（R4）が中心。性格（0）は、標準の動作セットに感情ごとの動作がそろってから（R6のあと）、感情の癖として定義し直す。動作が少ないうちに性格を変えても、見た目がほとんど変わらないため。実際に動くものを見てから決める。2・3・4は今ある仕組みを、キャラにつなぐ。

**間の自動補完**：場所AからBへの移動は、距離と高さの差から動作を選ぶ。近ければ歩く、遠ければ走る、段差があれば跳ぶ。ページの部品の上の縁を「床」として扱い、床から床へ移る。

## 部品の「できること」

ページの部品が、「ここではこれができる」を最初から持っている。作者が場所を置かなくても、キャラは近くの部品から次の行動を選べる（ゲーム「シムズ」の、冷蔵庫が「食べる」を持つのと同じ考え方）。YouTubeの配置が変わっても、キャラは部品についていく。部品を見分けるのは、今あるサイトアダプター（`src/sites/`）の仕事。

最初の一覧（案）

| 部品               | できること                             | 使う動作         |
| ------------------ | -------------------------------------- | ---------------- |
| 動画カード         | 上に座る、寝転ぶ、サムネイルを覗き込む | sit・sleep・peek |
| プレーヤーの上の縁 | 腰かけて動画を一緒に見る               | sit              |
| ページの下の端     | 歩く床                                 | walk・run        |
| 検索欄             | 入力中の文字を覗き込む                 | peek             |
| 高評価ボタン       | 押されると喜ぶ                         | happy            |
| コメント欄         | 新しいコメントを読みに行く             | walk・peek       |

- 作者は部品ごとに「この部品では必ずこれ」を上書きできる（段階1）
- 部品だけでなく、ページの任意の場所にも「できること」を置ける
- YouTube以外のサイトでも、アダプターを足せば同じ形で広げられる

## リアルタイム編集の原則

どの段階も、本物のYouTubeの上で、その場で結果が見える。「編集」と「再生」を分けない。

- 場所を置いた瞬間に、キャラがそこへ歩いていく
- きっかけを足した瞬間に、反応が変わる。その場できっかけを起こして試せる（動画を止めてみる、など）
- 性格を切り替えた瞬間に、暮らし方が変わる
- 今ページのクリックが何をするのかを、常にページの上に出す（キャラを動かすのか、場所を置くのか、YouTubeを操作するのか）。今のエディターで分かりにくかった一番の点

エディター（サイドパネル）の最初の画面は「キャラを住まわせる」にする。レイヤー・タイムラインは、その後ろに置く。

## 拡張と制作アプリの役割

拡張は見る人の道具で、制作アプリとのつなぎ役。編集はすべて制作アプリでする。拡張だけでは編集できない（2026-11-04、翔太の決定）。今の編集の画面（サイドパネル・別ウィンドウの Studio）は、制作アプリができるまで開発用として残す。

- **拡張のアイコンを押すと開く窓**：案内・困ったとき・応援（FANBOX やクラファンへのリンク）・設定の書き出しと読み込み・プライバシー。ボタンはどれも「押すと1つの決まった動作」（制作アプリとつなぐ、作品を止める、作品を切り替える など）
- **YouTube の中のアイコンとスライダー**：プレーヤーの操作バーにアイコンを置き、押すとスライダーが出る。変えられるのは、作者が作品の中で「見る人が変えてよい」と決めた項目だけ（キャラの大きさ、光の強さ、音への反応の強さ など）。見る人の値は作品データではなく見る人の設定に保存し、作品を更新しても消えない。置き場所はサイトのアダプターが持ち、見つからなければ置かない。YouTube のボタンをずらしたり隠したりしない（G1）
- **制作アプリ**：翔太が普段使う Chrome とつなぐ（方式B）。アプリの中にブラウザを開く方式や、アプリが別の Chrome を起動する方式は、Google のログインで詰まる可能性が高く、ログインしていない YouTube は「よそのYouTube」になるので採らない。作者が編集する画面と、見る人が体験する画面がずれないことを優先する
- **クラッシュ報告など外へ送る仕組み**は、入れるならプライバシーの方針と、すべて切れる選択肢を最初から用意する

### 方式Bの仕組み

- **要素の位置・シグナル・編集データ**：nativeMessaging（JSON。アプリから拡張へは1件 1MB まで）。インストーラーが接続の設定も入れる。拡張の ID はウェブストアの ID に固定する
- **タブの映像**：拡張のオフスクリーンドキュメントで tabCapture し、WebRTC でアプリへ送る。接続の手続きは nativeMessaging でする。tabCapture は使う人が拡張を押したタブにしか許されないので、「このタブを制作アプリとつなぐ」を1つのボタンにする
- **映像の上のクリック**：アプリは「映像のこの位置」を送り、要素 ID への変換は拡張のコンテンツスクリプトが今の画面で行う。映像は少し前の画面なので、アプリの手元の情報で決めるとスクロール中にずれる。拡大率・画面の倍率も拡張がまとめて扱う
- **ページを動かす操作**：スクロールや再生・一時停止は、コンテンツスクリプトからページの API で動かす。マウスを乗せたときの見た目は WWT の側で「乗せた状態」を再現して見せる。メニューを開くような本物の操作は、使う人が Chrome で直接する。debugger の権限は使わない（警告が強い）
- **制作アプリの中身**：Electron が素直（WebRTC が入っていて、TypeScript のまま書ける）
- **権限**：nativeMessaging を足す。権限なしの方法（アプリが PC の中にサーバーを立て、拡張が WebSocket でつなぐ）には、どの Web サイトからも話しかけられる・ポートがぶつかる・ファイアウォールの警告が出る、という弱点がある。nativeMessaging は決めた拡張とアプリの間でしかつながらないので、こちらを選ぶ。ウェブストアでの見え方は、試作のときに確かめて書き足す
- **作品データの検証は拡張の側に残す**：制作アプリから届くデータも、今と同じ安全の検証を通す（アプリにはほかの人の作品も入るため）
- **最初の試作で確かめること**：Chrome がアプリの後ろに隠れたとき・最小化したときも映像を取り続けられるか、映像の遅れ、CPU の負担、映像の上のクリックが正しい要素に変わるか

### ほかのサイト・ほかのブラウザに耐える3本の線

最終的には YouTube 以外のサイトと、Chrome 以外のブラウザに広げる。今はほかに向けて作らず、境界だけを守る。

1. **アプリと拡張のやり取りに、YouTube と Chrome の言葉を入れない**：セマンティックレイヤーの言葉（カード・ボタン・見出し・動画の枠 など）だけで話す。通信に版番号をつけ、古い版とも話せるようにする
2. **サイトごとの違いは `src/sites/` のアダプターに閉じ込める**：設定のアイコンもアダプターが持つ「置き場所」の1つ。置き場所がないサイトでは、操作面にかからない隅に小さく出すか、ツールバーのアイコンだけにする
3. **ブラウザごとの違いは `src/browser/` に閉じ込める**：Chrome にしかない機能（サイドパネル・オフスクリーンドキュメント・tabCapture）を、コードのあちこちで直接呼ばない。manifest もブラウザごとにビルドで作り分ける。検証のときに、Chrome 固有の呼び出しがこの外に出ていないかを確かめる

映像の取り方はブラウザによって違う（Chrome・Edge は tabCapture、Firefox は拡張から映像を流し続ける機能がない、Safari は制限が多い）ので、差し替えられる形にする。どのブラウザでも使える最後の手段は、制作アプリが OS の機能でブラウザの窓を直接映すこと。クリックを要素に変える処理は、この場合も拡張がする。

### 今からやっておくこと

R3 以降、編集の画面に手を入れるときは、編集の操作を「画面」ではなく「作品データへの命令」として切り分ける。制作アプリに移すときに、命令をそのまま使える。R8 の前に「調べて計画」で小さな試作を作り、上の「最初の試作で確かめること」を測ってから本番に入る。

## G1とキャラ

操作を壊さないこと（G1）が、そのままキャラの「よける」動きになる。カードの上に座っているキャラにマウスを近づけると、ひょいとよける。守るための仕組みが、性格のように見える。

- **G1.2が土台**：今のG1は、操作部品に近づくとページ全体の効果を止める。キャラが歩き回るなら、止める範囲を「近づいた部品に重なるものだけ」に絞る必要がある
- **止めるのではなく、よける**：キャラは絵と違って動けるので、重なりそうになったら、消える代わりに dodge で横へ移る。よけきれないときは、今までどおり消える（守る力は弱めない）
- **動いているキャラの当たり判定**：キャラはクリックを受けない（本物のボタンが押せる）。触って反応するやり取りを入れるときは、G1の設計と一緒に決める
- **性能**：3Dのキャラが常に動くので、「描画と性能」の3つの物差し（拡張のCPU時間・GPUの描画時間・動画のフレーム落ち）の基準を、キャラがいる状態でも守る。見えていないとき（タブが裏、画面外）は止める

着せ替えに「絵として置く」モードを足す案は、取りやめる。キャラを飾りたい人は、キャラを住まわせればよい。

### UIの着せ替えを外す（2026-11-06 決定）

**理由**：着せ替えは G1 と読みやすさを守る分、自由度が低く、ほかの拡張との差も出にくい。YouTube の UI が変わるたびに壊れやすい。WWT にしかない価値は「キャラがいつもの YouTube の奥の部屋に住んでいること」なので、3D とキャラを優先する。

**外すもの**：UI の部品の見た目を作り替える機能（部品に画像・色・形を当てる編集と、その描画）。エディター・拡張の窓・Playground・制作アプリの入口から消し、既定のビルドでは描かない。

**残すもの**（着せ替えではなく、3D の世界の一部）：読みやすさのガラスの板、画面全体のフレーム、部屋と動画の光が UI に当たること、キャラが UI の縁に座る・触れること、空間に置く画像・動画のレイヤー、シグナル・テイク・タイムライン。

**戻せるようにする約束**：

- コードは消さず、開発用のビルドのフラグで戻せる形にする（既定は外す）
- 作品データの形・移行・検証は変えない。版は上げない。古い作品の着せ替えの部分は、読み込み・保存・書き出し・バックアップで捨てずに持ち続ける（描かないだけ）
- 着せ替えの unit テストは残す。e2e は、フラグを立てたビルドで回せる形にして、既定の全件からは外す
- 戻す手順（フラグ・テスト・関係するファイル）を docs に書く
- 「外すもの」と「残すもの」の境目がはっきりしない機能は、消す前に一覧にして翔太が決める

**戻す目安**：デモや Playground の公開後に、見た人・使った人から UI の見た目を変えたいという声が繰り返し出たとき。

## 空間の設計思想（2026-11-06 決定）

Web ページの後ろに背景を置くのではなく、**ブラウザの奥に生活空間があり、その手前に Web の UI が浮かんでいる**世界にする。UI と 3D 空間が一つの世界として共存し、キャラはその境界を行き来する。UI の操作性と読みやすさは犠牲にしない。これを、空間・描画・キャラの制御の基本方針にする。

### 空間の構造

- 奥に、生活感のある高品質な 3D の部屋がある。見る人は見回さない。カメラと投影は、作品とシグナルが動かす（寄る・ずれる・距離感が変わる。将来は G2 の特殊な投影）。部屋は本物の3Dの形として、その場で描く（2026-11-06）
- ブラウザの UI は、部屋の手前に浮かぶガラスの板として見せる。操作は今までどおり本物の DOM のまま
- 文字やボタンの下には、半透明の保護の板やぼかしを置く。読む・押す部品ほど濃くし、部屋の景色と操作性を両立させる（「読みやすさの板」をこの考え方に広げる）
- **板の見た目：グラスモーフィズム＋リキッドグラス（2026-11-06 決定）**。半透明で後ろの部屋をすりガラスのようにぼかす（グラスモーフィズム）のに加えて、板の縁で後ろの部屋が曲がる屈折、部屋のランプ・窓・動画の光に合わせて縁に走るハイライト、後ろの部屋の色を少し拾った色味を足す（リキッドグラス）。どれも WWT が部屋を描くときの計算で作り、YouTube の DOM には触らない（板の位置は UI の領域情報から取る。ぼかしも同じ計算で作れるなら backdrop-filter は使わない）。読みやすさが優先：屈折は縁だけで、文字のある中央は静かにする。曲げるのは後ろの部屋だけで、文字は曲げない。板の濃さは部屋の明るさの決まりを優先する。ハイライトの動きは控えめにし、reduced-motion では止める。光の明滅は1秒3回まで。Playground の豪華版では、HTML-in-Canvas で板を本物の3Dにし、傾いた板の屈折まで出す。実装は R5（UI の奥の層・読みやすさの板）で行う
- **板と部屋・キャラのつながり（2026-11-06 決定）**。どれも WWT が部屋を描く側の計算で作り、YouTube の DOM には触らない。読みやすさと G1 の決まりが優先
  - **板が部屋に影と光を落とす**（コンテストに入れる）：ランプや窓の光が板を通り、床や壁にうっすら四角い影と、色の付いた光を落とす。動画が明るい場面では、プレーヤーの形の光が部屋に差し込む
  - **キャラが板に触れた跡**（コンテストに入れる）：キャラが板の向こうから手のひらを当てると跡がつき、息をかけると曇って少しずつ消え、曇った所に指で小さく落書きする。跡は板の縁と余白だけで、文字の上には付けない。数秒で消える
  - **夜は板に部屋が映り込む**（間に合えばコンテストに入れる）：部屋が暗いとき、夜の窓ガラスのように板にうっすら部屋とキャラが映る。時間帯の混ぜ方に乗せる。文字が読みにくくならないよう、縁の近くだけ・薄くする
  - **読むときだけ板が濃くなる**（試して決める）：部品の重要度で決まる濃さに、カーソルの近さで少し足す。濃さの下限は今の決まりのまま下げない。動きが増えるので、効果は小さくし、reduced-motion では使わない
- 世界の奥行きは3つに分けて扱う：**部屋（UI の奥）**・**UI の板**・**UI の手前**。キャラと動く物は、どの奥行きにいるかを持つ

### DOM を基準にした空間（2026-11-06 決定）

**DOM は動かさず、3D の側が DOM に合わせる。** これが空間の本筋で、どのサイトでもどのブラウザでも使える。HTML-in-Canvas は、自分たちのページで UI そのものを傾けたいときの上乗せ。

- 3D の側で「UI の板」の奥行きに平面を1枚決め、その平面で 3D の1単位が画面の1ピクセルに重なるようにする。DOM の部品の四角形は、そのまま平面の上の四角形になる
- カメラが寄る・ずれるときも、UI の平面はカメラに付いて画面に留まり、部屋だけが後ろで動く
- 部品ごとに、目に見えない**身代わり**を 3D に置く。身代わりは「UI の領域情報」から作り、大事な部品（操作・読む）だけにして、近いものはまとめる。更新はアダプターが渡す「変わった部分」だけ

| できること                   | 中身                                                                                                                                   |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| UI が部屋に影を落とす        | 身代わりが窓の光を遮り、床にプレーヤーやカードの影が落ちる。時間帯で向きが変わる                                                       |
| UI がガラスの板に見える      | 部品の四角形に合わせて、板の厚み・縁の光・映り込み・すりガラスのぼかしを DOM の真後ろに描く。文字とボタンは本物の DOM のまま手前にある |
| キャラが UI の後ろに回り込む | 身代わりが奥行きを持つ。G1 は今の重なり順と切り抜きで守る                                                                              |
| キャラが UI に触れる         | 手の IK の目標を部品の縁にする。本物のクリックに反応するだけで、クリックの代わりはしない                                               |
| UI の変化に世界が反応する    | サイドバーが開く・シアターモード・スクロールで、影・光・キャラの居場所が付いてくる                                                     |
| UI の近くの移動              | 身代わりがそのまま経路の障害物になる                                                                                                   |

- **できないこと**：UI そのものを曲げたり、シェーダーで光らせたりはしない。部屋の光の色を薄い層で UI に乗せるのは、読みやすさを落とさない範囲だけ
- **1フレームのずれ**：スクロールや配置の変化が 3D に届くまでに1フレーム遅れることがある。影や縁の光の遅れは「見た目」で許容。操作の守りはこの仕組みに任せない
- **今ある物とのつながり**：重なりの方式（塚4）、UI の領域情報、部屋の光の層をつなぐ「身代わりの層」を1つ足すだけ。R5「世界の層」の中心に置く

### キャラ

- 奥の部屋を歩き回れる。部屋と UI の手前を行き来でき、UI の前後を横切ったり、家具の裏に隠れたりする
- **UI の奥にいるとき**：キャラは部屋の層で描かれ、UI はいつもキャラの手前にある。操作部品が隠れないことを、ブラウザの重なり順が保証する（G1 のいちばん確かな形。重なりの中に入れる試作 docs/layering-plan.md と同じ考え方）
- **UI の手前にいるとき**：今の G1 の守り（操作部品の切り抜き）がそのまま効く。手前で操作部品を横切る道は選ばず、横切るのは奥か、操作部品のない所
- 家具の裏に隠れるなど、部屋の中の前後は、部屋の奥行きの情報で決める
- 将来は、DOM の部品の位置と状態に合わせて、UI に触れたり、クリックや再生に反応したりする
- **自律の移動（R5 以降、2026-11-06 決定）**：部屋の中は、NavMesh による経路の探索と、Steering（巡回・追う・逃げる・うろつく・離れ合う・障害物を避ける）によるその場の回避を組み合わせる。NavMesh は Blender で歩ける床を別の形として作り、作品の素材として持つ。計算は `src/world/` の決定的な関数にする。UI の近くの経路は、下の「UI の領域情報」から作る。経路の探索の方法とライブラリは R5 で決める。FABRIK（手を伸ばす IK）は、必要になった段階で検討する。Google の Three-Live 本体は採用しない（独自の描画を持ち three.js と別に WebGL を作る、Alpha、作者向けの部分が new Function を使うため）。Steering の考え方は参考にする（Apache-2.0。コードを写すなら著作権の表示を残す）
- **一緒に見る（シアターモード・全画面）**：部屋を歩いていても、シアターモードになると手前に来て、画面の前に座り、後ろ姿で一緒に見る。部屋の明かりは映画館のように落ち、動画の光がキャラの背中と部屋を照らす。座るのはプレーヤーの中の層（操作バーより奥）なので、バーが出てもバーがキャラの上に描かれる。動画を隠す量は、座る位置（下の角か、下の真ん中か）と大きさを作品が決め、見る人は YouTube の中のスライダーで小さくできる。シアターモードを抜けると、部屋に戻る。奥から手前へ移るときは、操作部品のない所を通って層を乗り換える（R5 のモードと一緒に作る）

### 移動の役割の分け方（2026-11-06 決定）

| 役割            | 担当                   | 中身                                                             |
| --------------- | ---------------------- | ---------------------------------------------------------------- |
| 3D の部屋の経路 | Blender で作る NavMesh | 家具や壁を迂回する                                               |
| UI の近くの経路 | UI の領域情報（下）    | DOM の位置と大きさから通れる所を計算し、大事な UI を避ける       |
| その場の動き    | Steering               | 経路に沿った自然な移動、キャラどうしの回避、その場の障害物の回避 |

Steering だけでは大事な UI を確実に避けられないので、避ける場所は経路の段階で外す。

### UI の領域情報：読みやすさと移動を同じ情報で決める

ページの部品ごとに「領域」を持ち、その重要度から、**保護の板**と**キャラの移動の制約**を一緒に決める。たとえば検索バーを保護の対象にすると、そこに半透明の保護の板が載り、同時に、UI の手前にいるキャラはその前を横切らなくなる。奥の部屋を歩くキャラには、その制約を掛けない。

| 重要度     | 例                                   | 保護の板                   | 手前のキャラ               | 奥のキャラ                            |
| ---------- | ------------------------------------ | -------------------------- | -------------------------- | ------------------------------------- |
| 操作（G1） | ボタン・シークバー・検索の入力       | あり                       | 横切らない（経路から外す） | 制約なし（UI がいつも手前に描かれる） |
| 読む       | 動画のタイトル・説明・コメント・字幕 | あり（濃さは重要度で調整） | 横切らない。通るなら短く   | 制約なし（板の後ろで薄く見える）      |
| 自由       | 飾り・余白                           | なし                       | 自由                       | 自由                                  |

- 既定の重要度は、アダプターが部品の種類ごとに渡す。作者は「読む」と「自由」の間で上げ下げできるが、「操作」を下げることはできない（操作性の3段階：破綻はエンジンが起こさせない）
- 領域情報は、今の G1 の操作部品の一覧を広げたものにする。別の仕組みを作らない
- **経路で避けるのは振る舞いであって、守りではない**。操作部品を隠さない保証は、今どおり重なり順（奥）と切り抜き（手前）が持つ。経路の計算が外れても、操作は壊れない
- **ガードは手前の物だけ（2026-11-07 決定）**：描く物の既定の奥行きは「UI の奥」にする（部屋・画像や動画のレイヤー・ふだんのキャラ）。奥の物はブラウザの重なり順で必ず UI の下になるので、ガードの重い仕組み（読み取りの保留・近さの判定・止める・切り抜く）は掛けない。「UI の手前」に出られるのは、キャラ・フレーム・板に触れた跡などの小さな飾りだけで、ガードはそれだけに掛ける。守る力は弱めず、ガードの仕事と重さ（起動・遷移の上乗せを含む）を減らす。ガードそのものは消さない
- 今は移動の仕組みを作り込まない。先に、部屋・DOM・キャラの奥行きの関係（どの奥行きにいるか、どの層で描くか、領域情報）を成り立たせる土台を優先する。経路の探索の方法とライブラリの選定は R5 で決める

### 描画

- 目標は UE5 のようなライティングと空気感。Blender で作った部屋を three.js で描く方針は変えない
- **焼いた光で軽くする（2026-11-06 決定）**：動かない部屋は本物の3Dの形として持ち、Cycles で光と影を焼き込む（ライトマップ）。カメラと投影が動いても破綻せず、長期のロードマップ G2 の空間技法（パース・消失点・特殊な投影）が部屋にも効く。ツヤや映り込みが要る所は、反射のプローブで足す。部屋を「Cycles で描いた絵＋奥行き」で持つ方式は、カメラも投影も動かせないので採らない。窓の外の遠景のように、パースが変わっても困らない所だけは描いた絵でよい
- キャラと動く物はその場の照明で描き、部屋の焼き込みと同じ光（部屋の位置で撮った環境の光）を当てて馴染ませる。キャラの影は、部屋の簡単な形（床・机など）に落とす
- 動画の光は、焼き込んだ光の層を動画の明るさで混ぜる形で表す
- WebGPU やポストプロセスも使うが、YouTube がふつうに使える性能を最優先する（「描画と性能」の物差しを守る）
- ウィンドウの縦横の比が変わっても破綻しないよう、部屋は見える範囲より広く作る
- **空気感の動き**：窓から差す光の筋、光の中を舞う埃、雲や葉の影が床を渡る、カーテンの揺れ、時間帯で光が移り変わる。どれもエンジンが持つ決まった効果の種類として用意し、作品は数値（強さ・速さ・色・場所）だけを持つ（作品データにシェーダーを入れない）。太陽の光は焼き込みを別の層にして、動く影の模様を掛ける。時間帯は、朝・昼・夕・夜の焼き込みを時刻で混ぜる。タブが見えないときは止め、動きを減らす設定（reduced-motion）では弱める
- **HTML-in-Canvas（Chrome 157、2026-11-06 決定）**：`content="drawable"` の canvas の中の HTML を、本物の DOM のまま WebGL・WebGPU の絵として描ける（three.js は実験的に `HTMLTexture`）。取り込めるのは canvas の中の要素だけで、別のドメインの画像・iframe、字幕と動画の操作バーは描かれない。そのため **YouTube など他人のページでは使わず、今の方式（本物の DOM・ガラスの板・重なりの層・G1）を続ける**。**自分たちのページ（Playground・制作アプリ）と WWT 自身の UI（部屋の中のモニター・看板・設定の部品）で併用する**。使えるかを確かめ、使えないブラウザでは今の方式に戻す（`src/browser/` に閉じ込める）。描いた UI にも本物のクリックが届くので、キャラが操作部品を隠さないこと（G1）は、描く側の WWT が守る。コンテストの Playground の豪華版に使う（2026-11-06。「コンテストまでの計画」の「Playground の豪華版」）

## 最初の作品：生活空間の部屋

**2026-11-06 決定**：「機械の部屋」は廃止。最初の作品は、上の「空間の設計思想」に沿った**生活感のある高品質な部屋**にし、12/5 のコンテスト（デモ動画）に入れる。部屋の方向は下の「部屋の方向」に決めた。キャラの暮らし方とデモの台本はこれから決める。

部屋・キャラの動き・光の当て方は翔太の作品に属し、WWT に足すのは、それを動かす仕組みだけ。

### 部屋の方向（2026-11-06 決定）

**夜の、本と音楽の生活空間。** 絵柄はアニメの美術背景の塗りで、形と塗りはアニメ、光と空気は写実寄りにする。翔太が作った参考の絵は雰囲気の参考で、そのまま写さない（天井の面の分かれ方など、絵ならではの崩れは3Dで組めば自然に直る）。

- **絵柄**：平たい色で塗り、輪郭線は基本なし（色の境目で形を見せる）。光は焼いたやわらかい光、ランプの光のたまり、壁に落ちる影、光の筋、埃で見せる。写実の細かいツヤや材質は狙わない
- **色**：窓の青（sun\_night）、ランプのオレンジ（室内照明）、部屋全体の紫がかった灰色の3つ。動画の光が4つ目の色になる
- **置く物**：ベッド、ビーズクッションとスツール、丸いローテーブルとろうそく、本棚、壁の棚、テレビ台、ギター数本・アンプ・鍵盤、観葉植物、L字デスク（デスクランプ・モニター・キーボード・椅子）、ブラインドとカーテンの窓、アーチ型のフロアランプ、吊り下げのランプ
- **室内照明はランプごとに分けて焼く**：吊り下げのランプ・フロアランプ・デスクランプ・ろうそく・棚の間接照明などを、それぞれ別の層（room\_pendant・room\_floor・room\_desk など）にする。シアターモードで1つずつ落とせるようにするため
- **部屋のモニター**：見ている動画を部屋のモニターにも映す（エンジンの決まった効果）。画面の面は dyn\_monitor\_screen として別のオブジェクトにし、モニターが照らす光は screen\_monitor の層として焼く
- **飾り**：ポスター・ステッカー・フィギュアは自作か架空の物（deco\_）。ギターは少し崩したオリジナルの形にし、特定のメーカーの形やロゴにしない

**構図とプレーヤー（いちばん大事）**：既定の動画ページでは、左上の大きな四角（プレーヤー）は不透明で、部屋が一切見えない。右の3分の1（おすすめ欄越し）と下のほう（タイトル・コメント欄越し）は、薄い板越しに見える。

- 主役の窓と光、キャラがよくいる場所は、右の3分の1と下のほうに置く。本棚やベッドのように隠れてもよい物は左上に回す。カメラの向きか家具の配置で合わせ、YouTube のスクリーンショットを camera\_main の画角に重ねて確かめる
- 電球やモニターのような明るい光源を、読む部品（おすすめ欄・コメント欄）の真後ろに置くと、その部分の板が濃くなり部屋が見えにくくなる。強い光源はプレーヤーの真後ろか、UI の少ない所に置く

**作り込みの順番**：1. 余白と板越しによく見える物、キャラの居場所 → 2. 板越しに見える物（形と光が分かればよい）→ 3. カメラが寄ったときだけ見える細部。

**床の照り返し**：見る角度で変わる光なので、ライトマップには焼けない。反射のプローブで出す（2026-11-07、測って決めた）。

**キャラの暮らし方**：これから決める。居場所の候補は、ビーズクッション、ベッド、デスクの椅子、窓辺、ローテーブルの前。

素材を作品として分けるのは、売り方の候補に「作る道具を売る」があるため。デモは「WWTでここまで作れる」の証明になるので、動かす仕組みはWWTの機能として作る。

### 部屋の素材の約束（2026-11-06）

素材を作る側（Blender・Tripo）とエンジンの間の決まり。部屋の素材を作るときは、この節だけを見れば足りるようにする。11/14 の比べで決まる所は、そう書いてある。

**全体**

- 1つの部屋を1つの glTF（.glb）にまとめる。単位はメートル、向きは Blender の glTF 書き出しの既定のまま
- 家具は実寸で作る（机の高さ約0.7m など）。キャラは実寸の人型として部屋に立つ
- 元ファイル（.blend・Tripo の出力・テクスチャ）は、リポジトリの外かつ OneDrive の外に置く。トルーシェもリポジトリに入れない
- 実在の製品のロゴは作らない。他人の作品（アニメ・漫画・ゲーム・アルバムのジャケットなど）の絵やロゴも、外に見せる版（コンテスト・Playground・クラファン・配る作品）には入れない。飾りは自作か架空の物にする。翔太が自分だけで使う手元の版では、飾りを好きな物に差し替えてよい（その版のスクショや動画は外に出さない）。Tripo で作った物は、作ったときのプランの利用条件を確かめる
- 絵柄は作品が決める。エンジンは特別なシェーダーを前提にしない

**カメラと画角**

- 基準の視点として、.blend に camera\_main を置く。カメラは演出で寄る・ずれる・画角が変わるので、camera\_main から少し動いても、部屋の外や作っていない裏側が見えないようにする。テストの部屋では camera\_main から左右 ±0.2m・上下 ±0.4m・前 0.3m・後ろ 1.0m・ドリーズーム 1.5m まで外が見えなかった（2026-11-07）。空間技法でもっと大きく動かしたいなら、その分だけ部屋を広く作る。窓の外の面は窓より 1m 以上大きくする
- 基準の画面は 16:9（1920×1080）。ウィンドウが 21:9 まで横に広がっても、16:10 まで縦に伸びても部屋の外が見えないよう、部屋を見える範囲より広く作る
- 横長の PC 画面で YouTube の動画ページを開いたときの UI 配置を基準にする。中央のプレーヤーと上の検索バーのあたりは保護の板で見えにくいので、見せたい物（窓・光の差す所・目を引く家具）やキャラがよくいる場所は、プレーヤーまわりの余白・左右の端・下のほうに置く。迷ったら、スクリーンショットを camera\_main の画角に重ねて確かめる
- シアターモードでは、キャラが手前に来て画面の前に座り、部屋の明かりが落ちる。部屋の側で足す物はない（室内照明の層を分けておけば足りる）

### 読みやすさの板

コメント・説明・動画のタイトルなど、読む部品の下にだけ半透明の板を挟む。部屋を文字の裏に置いても読めるようにするため。

- 板は読む部品の背景色として当てる。部品と一緒に動くので、スクロールしてもずれない。部品の位置はアダプターが知っている
- 濃さは計算で決める。白い文字を 4.5:1 で読めるように、板の後ろが一番明るいときでも足りる濃さを下限にする。部屋の一番明るい所が中くらいの灰色（相対輝度 0.2）程度なら、1割の濃さで足りる（後ろが真っ白なら8割以上）
- 動画のフラッシュで部屋が明るくなる瞬間だけ、同じ光のシグナルで板を濃くする

## 描画と性能

**部屋とキャラは GPU で描き、1枚の canvas にまとめる。** 描画器は three.js の `WebGPURenderer` で、WebGPU が使えない環境では WebGL2 に切り替わる。

- WebGPU は、描く物が多いときのメインスレッドの命令のコストが小さい。空気感の動き（埃・光の筋など）は compute shader で回せる
- 今の 3D は、描いた結果を 2D の canvas にコピーしてページに載せている（`docs/spatial-design.md` 6節）。全画面の部屋ではこのコピーが重いので、1枚の canvas に直接描く
- 今の VRM の描き方（`WebGLRenderer`、`powerPreference: 'low-power'`）は急いで書き換えない。部屋の描画器で先に使い、キャラを移す時期は測って決める

合否は次の3つで決める。

| 物差し                             | 見るもの                                                          | 基準                         |
| ---------------------------------- | ----------------------------------------------------------------- | ---------------------------- |
| 拡張の CPU 時間（1フレームあたり） | YouTube 自身の処理との取り合い（操作の引っかかり）                | 中央値 +0.5ms、p95 +1ms 以内 |
| GPU の描画時間                     | 部屋とキャラの重さ（WebGPU の timestamp query）                   | 部屋を入れるときに決める     |
| 動画のフレーム落ち                 | GPU を動画の再生と取り合っていないか（`getVideoPlaybackQuality`） | 拡張なしと比べて増えない     |

画質の段階切り替え、解像度の自動調整、タブが裏のときの停止は最初から入れる。動画の明るさは、小さい canvas で間引いて読む。

## 音

**音に合わせて、光と世界が脈打ち、キャラが楽しそうにする。** 動画の音を解析して、シグナルとして作者に開く。

| シグナル（案）   | 中身                         | 使い道の例                                |
| ---------------- | ---------------------------- | ----------------------------------------- |
| 音量             | 今の音の大きさ               | 部屋の光の強さ                            |
| 低音・中音・高音 | 帯域ごとの強さ               | 低音で部屋の光が脈打つ                    |
| 拍               | 音が立ち上がった瞬間の出来事 | 拍ごとに光が跳ねる、キャラがうなずく      |
| 盛り上がり       | 数秒の平均でゆっくり変わる値 | キャラの「楽しい」が上がり、踊る（dance） |

感情に「楽しい」を足す。盛り上がりと拍で上がり、リズムに乗る・踊る。怖い場面（恐怖が高い）では楽しいより恐怖を優先する。

### 音の取り方

1. **まず `video.captureStream()` を試す。** 動画の音を分岐して読むだけで、YouTube の音の経路は変えない。権限も要らない。拡張が更新・停止しても音は消えない
2. 取れない場面があれば、`chrome.tabCapture`（＋ offscreen document）を足す。権限を足すこと自体は問題にしない。ただし、取り込んだ音を再生し直さないとタブの音が消えること、取り込みの開始に利用者の操作が要ることを確かめてから決める
3. `createMediaElementSource` で動画を Web Audio につなぐ形は使わない。YouTube の音が拡張の中を通るので、拡張が止まると動画の音が消える

取れないとき（DRM の動画、広告の切り替わり）は、音を「無音」として扱わず、「取れない」として作品に渡す（動画の光と同じ扱い）。

### 守ること

- 光の明滅は1秒に3回までに抑える（光過敏への配慮、WCAG 2.3.1）。作品からは外せない
- 「動きを減らす」の設定（reduced-motion）では、脈打ちを弱める
- 読みやすさの板は、音で部屋が明るくなる瞬間も文字が読める濃さを保つ

## デモ動画の前に満たす水準

**デモ動画は急がない。** 次の5つを満たしてから出す。

1. 台本の6場面が、本物の YouTube で撮り直しなしに通る（その場面に合わせて仕込まない）
2. 30分ふつうに使っても（見る・検索・コメントを読む・シーク・全画面）、操作の破綻も、読めない文字も出ない
3. 上の性能の物差しの基準を守る
4. 画面遷移・ウィンドウの大きさ変更・ダークとライト・広告の場面でも崩れない
5. 翔太が絵（構図・色・線）を見て「出していい」と思える

台本は新しい作品（生活空間の部屋）で書き直す。機械の部屋の台本は使わない。

**Playground（応募するサイト）**：YouTube のページは持ってこられず、埋め込みの YouTube プレーヤーには上に何も重ねてはいけない決まりがある（[Required Minimum Functionality](https://developers.google.com/youtube/terms/required-minimum-functionality)）。そこで、翔太が作る簡単な動画サイト（自前の動画・プレーヤー・シークバー、YouTube に似せない）の上で、WWT のエンジンを拡張なしで動かす。「WWT を適用」ボタンで、ただの動画サイトが別の世界に切り替わるのが見せ場。キャラは再配布できる VRM を自律行動で動かし、トルーシェは使わない。本物の YouTube での姿は、前後比較の動画で見せる。余裕があれば、拡張を Chrome ウェブストアに限定公開して「あなたの YouTube で試す」入口を足す。

**Playground の豪華版（HTML-in-Canvas、2026-11-06 計画に入れる）**：Playground は自前のページなので、動画サイトの UI をまるごと HTML-in-Canvas で3Dの部屋の中に描ける。空間の設計思想の「UI はガラスの板」を、本当に3Dの板として見せる。

- **2段構え**：今の方式の Playground（基本版、どのブラウザでも動く）を必ず出す。HTML-in-Canvas が使える Chrome では、豪華版に自動で切り替わる。豪華版が間に合わなくても、応募は基本版で成り立つ
- **見せ場の候補**（重さと時間を見て絞る）：
  1. 「WWT を適用」で、平らな動画サイトが奥へ傾いて、部屋の中に浮かぶガラスの板になる（カメラのドリーズーム）。デモ動画の冒頭にも使う。いちばんの見せ場
  2. 板が本物の3D になる：部屋のランプの光が板に映り、板の後ろの部屋がぼける。キャラが板の前後を本当の奥行きで行き来し、板に影を落とす
  3. 板に触れる：キャラが板の縁に座る・手をつく。スクロールで板が少したわむ（シグナル）
  4. 部屋のモニターにも同じ動画が映る
- **守ること**：板が傾いても本物のクリックとキーボードが届く（G1。描く側の WWT が板の位置を渡して合わせる）。文字が読める角度と大きさに留める。移行の動きは短く、移行の間は操作を受けない。reduced-motion では移行を弱める。光の明滅は1秒3回まで
- **技術**：three.js（HTMLTexture か WebGL の直接の呼び出し）。API は Chrome の版で名前と形が変わってきたので、機能があるかを確かめて呼び分け、`src/browser/` に閉じ込める。Chrome の安定版 157 は、フラグもトークンもなしで使えた。傾けた板のボタンのクリック、Tab での移動と入力、日本語の読みやすさも確かめた（2026-11-07、Codex、docs/html-in-canvas-probe.md）。Playwright の Chromium 153 はフラグが要る。使えないブラウザ（古い Chrome・Firefox・Safari）では基本版に戻る。動画は板とは別に動画のテクスチャとして描く（動画の光にも使う）。板の描き直しは UI が変わったときだけにし、ノート PC で測る
- **順番**：部屋とキャラ（デモ動画）＞ Playground の基本版 ＞ 豪華版。豪華版のために部屋とキャラを遅らせない
- **予定**：11/15〜18 に試作（カード1枚 → 動画サイトの全体、クリック・読みやすさ・重さ）→ **11/20 にやるかどうかを決める** → 11/21〜28 に作る → 12/1〜3 の撮影に入れる

**自律行動（Playground の形は決定）**：性格・感情・欲求・記憶の状態から、行動と体の動きをその場で作る。Playground では、BOOTH の「オリジナル3Dモデル ミルド - mirdo」（2026-11-07 決定。規約で営利・非営利を問わず、ソフトへの組み込みと改変したデータの配布が許可されている。トルーシェの作者には問い合わせない）を、CC0 の動作セット（Quaternius の Universal Animation Library）＋計算の動き＋翔太が作る姿勢で動かす（2026-11-07、CC0 の動作を足した。モデルに組み込んでも、ファイルのまま置いてもよい）。トルーシェと Mixamo 由来の動作は Playground に入れない。LLM は使わず、状態機械・Utility AI などで考える（docs/autonomy-plan.md・docs/playground-plan.md）。11/26ごろに自然さを見て、届かなければ 2D の描き出しの連番をシグナルで動かす形に切り替える。

**進め方**：1回の作業は、R の段階のまとまった塊にする。塊の中は小さなコミットに分け、Codex の検証は塊の終わりに1回。作品データの版上げは1回に1段まで。「同じ問題への挑戦は3回まで」は塊の中の個々の不具合ごとに数える。性能の計測で、背景の CPU 負荷は組を外す条件にせず、参考値として記録する。

**年内（v1）に入れないもの（案）**：FBX の取り込み（R7）、制作アプリ（R8 の大部分）。v1 の範囲は 11/5〜11/11 に翔太が決める。
