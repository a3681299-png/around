# WWT 製品設計：キャラが住むYouTube

Nov 3, 2026 · @翔太

## 核

**いつものYouTubeに、あなたのキャラが住む。** UIが変わらなくても、日常のページにキャラが暮らしているだけで、見た瞬間に「何これ」となる。UIの着せ替えは、世界観を大事にしたい人のための付属の機能として残す。

デスクトップペット（しめじ・伺か・Bongo Catなど）との違いは、WWTが**ページの中身を分かっている**こと。これが、デスクトップアプリではなく拡張機能で作る理由になる。

- **部品が分かる**：動画カードに座る、プレーヤーの縁を歩く、再生ボタンの近くではよける
- **動画が分かる**：曲に合わせて踊る、動画が止まったら振り向く
- **操作を壊さない**：キャラがどこにいても、YouTubeのボタンは押せる（G1）

デスクトップのほかのアプリには、DOMのような中身の手がかりがない。上の3つは、Webページだからできる。

## キャラの形式

キャラは3DのVRM、動作は名前の決まった標準セット（.vrma）。人型の骨の名前が決まっているので、同じ動作がどのモデルにも使える。

- **モデル**：VRM（人型）。WWTはもうVRMとGLBを読める
- **動作**：VRM Animation（.vrma）。最初のセットは翔太が作り、それがWWTの標準になる
- **足りない動作**：近いもので代わりに出す（「走る」がなければ「歩く」を速く）。最初は待つ・歩く・座るの3つから始められる

標準の動作の名前（案）

| 名前  | 動作     | 代わり                     |
| ----- | -------- | -------------------------- |
| idle  | 待つ     | —（必須）                  |
| walk  | 歩く     | —（必須）                  |
| sit   | 座る     | —（必須）                  |
| run   | 走る     | walk を速く                |
| jump  | 跳ぶ     | なし（段差を歩いて下りる） |
| sleep | 寝る     | sit                        |
| peek  | 覗き込む | idle                       |
| happy | 喜ぶ     | idle                       |
| dodge | よける   | walk                       |
| dance | 踊る     | idle                       |

**モデルの権利**：販売されているモデルは、利用規約で再配布が禁止されていることが多い。作品を配るときは、作品にモデルを含めず、「モデルは各自が入れる」形にする。動作（.vrma）と性格・行動の設定だけを配る。

最初のキャラは「Trusie トルーシェ」（もち山金魚さん）。宣伝のために使うことは、作者から了承を得ている。製品に埋め込んで売ることはしない。リポジトリにはコミットしない（`WW_VRM_FILE` で指定）。

### 取り込める形式：VRM と FBX

**エンジンの中では、骨の対応・表情・揺れもの・材質を「中の形」として持つ。** VRM はそのまま中の形になり、FBX は取り込むときに変換する。動きの仕組みは1つで済ませ、R3 で骨の扱いを VRM に縛られない形で作る。VRChat のアバターの多くは FBX と unitypackage で配布されているので、FBX の取り込みは買う理由になる。

| FBX に足りないもの | 取り込みでやること                                                                                   |
| ------------------ | ---------------------------------------------------------------------------------------------------- |
| 骨の対応           | よくある名前の辞書（VRChat・Unity・VRoid・Mixamo）で自動で対応付け、骨の図で確かめて直せる画面を出す |
| 材質               | テクスチャを読み込んでトゥーン調の材質にする（lilToon の見た目そのままは無理）                       |
| 表情               | VRChat の口の形とまばたきは名前で対応付ける。喜怒哀楽は、あれば選んでもらい、なければ表情なしで動く  |
| 揺れもの           | 「Hair」「Skirt」などの名前の骨に、簡単な揺れを自動で付ける（あとで調整できる）                      |

unitypackage の中身（FBX とテクスチャ）を直接取り出せれば、「BOOTH で買ったファイルをそのまま落とすだけ」にできる。取り込むときに、「アバターの規約で、ほかのアプリでの使用が許されているか確かめてください」と案内を出す。順番は、VRM で動きが綺麗に動くのを確かめてから（R7）。

### 動きの3段階：体型に左右されるかで線を引く

アバターは頭身も足の長さもばらばらで、同じ歩く動作を当てても崩れる。線は「体型に左右される動きか」で引く。

| 段階                | 対象         | 動き                                                                                                        |
| ------------------- | ------------ | ----------------------------------------------------------------------------------------------------------- |
| 1. 読み込むだけ     | どの人型でも | 視線と顔の向き、まばたき、呼吸、揺れもの、表情、横に揺れる、跳ねる、震える、瞬間移動、計算で作る座り方      |
| 2. 標準の動作・姿勢 | 普通の体型   | 翔太が作る標準の .vrma と姿勢に、自動の補正（腰の高さ、足の接地、足の長さに合わせた速さ、腕の開き）をかける |
| 3. 作者の動作       | 作者が作る   | トルーシェのように、そのキャラ専用に作った動作                                                              |

- **体型を測って自動で決める**：読み込んだときに、頭の大きさと身長の比、足と腕の長さを測る。標準の動作が崩れる体型なら段階1の動きに切り替え、使う人にそのことを表示する。手で変えることもできる
- **歩かずに移る**：遠い所へは瞬間移動（ノイズが走って消え、別の部品に現れる）、近い所へは跳ねて移る。移る先はランダムではなく、きっかけ（カーソル、新しいコメント、動画の停止、怖いもの）で選ぶ。部品の上を横切らないので G1 とも合う
- **姿勢の反映**：翔太が作る姿勢は、1コマの .vrma（人型の骨ごとの角度）と、「どこが何に触れるか」の印（お尻は縁、両手はひざ、足は床など）。使う人のキャラには同じ角度を当て、触れる所はエンジンが IK で合わせ、体にめり込む所は少し押し出す。届かない所はあきらめるか、より単純な姿勢に切り替える
- **座り方は下に何があるかで分ける**：操作部品に重なった絵は切り抜かれるので、動画カードやボタンの上では体育座り・横座り・寝転ぶ（縁より下に何も出さない）。プレーヤーの上の縁（下は動画）やページの余白では、足を下ろしてぶらぶらさせる

## 動きの設計の段階

誰もがタイムラインを作るわけではないので、手間の違う段階を用意する。上の段階ほど簡単で、下の段階ほど作者の思いどおりになる。どの段階も重ねて使える（性格で暮らしつつ、サビだけ踊る、など）。

| 段階                  | 作者がやること                                                               | キャラの動き                                               | エンジン           |
| --------------------- | ---------------------------------------------------------------------------- | ---------------------------------------------------------- | ------------------ |
| 0. 性格を選ぶ（後で） | 「怖がり」「飽きっぽい」などを選ぶだけ。中身は感情の上がり方・下がり方の数値 | 同じ動作セットでも、感情の動き方が変わって暮らし方が変わる | 新しく作る         |
| 1. 場所と動作         | 部品やページの場所に「ここでは座る」を指定する                               | 指定した場所の間を、歩く・走る・跳ぶを自動で選んで移動する | 新しく作る         |
| 2. きっかけと反応     | 「動画が止まったら振り向く」「サビで踊る」を並べる                           | シグナル（再生・停止・音・スクロール・マウス）に反応する   | シグナルがある     |
| 3. 演技で記録         | ページの上でキャラをドラッグして動かし、そのまま記録する                     | 記録した動きをそのまま再生する                             | テイクの記録がある |
| 4. タイムライン       | 時間の上で細かく作る                                                         | 作者の思いどおり                                           | タイムラインがある |

新しく作るのは1と、感情の仕組み（R4）が中心。性格（0）は、標準の動作セットに感情ごとの動作がそろってから（R6のあと）、感情の癖として定義し直す。動作が少ないうちに性格を変えても、見た目がほとんど変わらないため。実際に動くものを見てから決める。2・3・4は今ある仕組みを、キャラにつなぐ。

**間の自動補完**：場所AからBへの移動は、距離と高さの差から動作を選ぶ。近ければ歩く、遠ければ走る、段差があれば跳ぶ。ページの部品の上の縁を「床」として扱い、床から床へ移る。

## 部品の「できること」

ページの部品が、「ここではこれができる」を最初から持っている。作者が場所を置かなくても、キャラは近くの部品から次の行動を選べる（ゲーム「シムズ」の、冷蔵庫が「食べる」を持つのと同じ考え方）。YouTubeの配置が変わっても、キャラは部品についていく。部品を見分けるのは、今あるサイトアダプター（`src/sites/`）の仕事。

最初の一覧（案）

| 部品               | できること                             | 使う動作         |
| ------------------ | -------------------------------------- | ---------------- |
| 動画カード         | 上に座る、寝転ぶ、サムネイルを覗き込む | sit・sleep・peek |
| プレーヤーの上の縁 | 腰かけて動画を一緒に見る               | sit              |
| ページの下の端     | 歩く床                                 | walk・run        |
| 検索欄             | 入力中の文字を覗き込む                 | peek             |
| 高評価ボタン       | 押されると喜ぶ                         | happy            |
| コメント欄         | 新しいコメントを読みに行く             | walk・peek       |

- 作者は部品ごとに「この部品では必ずこれ」を上書きできる（段階1）
- 部品だけでなく、ページの任意の場所にも「できること」を置ける
- YouTube以外のサイトでも、アダプターを足せば同じ形で広げられる

## リアルタイム編集の原則

どの段階も、本物のYouTubeの上で、その場で結果が見える。「編集」と「再生」を分けない。

- 場所を置いた瞬間に、キャラがそこへ歩いていく
- きっかけを足した瞬間に、反応が変わる。その場できっかけを起こして試せる（動画を止めてみる、など）
- 性格を切り替えた瞬間に、暮らし方が変わる
- 今ページのクリックが何をするのかを、常にページの上に出す（キャラを動かすのか、場所を置くのか、YouTubeを操作するのか）。今のエディターで分かりにくかった一番の点

エディター（サイドパネル）の最初の画面は「キャラを住まわせる」にする。レイヤー・着せ替え・タイムラインは、その後ろに置く。

## 拡張と制作アプリの役割

拡張は見る人の道具で、制作アプリとのつなぎ役。編集はすべて制作アプリでする。拡張だけでは編集できない（2026-11-04、翔太の決定）。今の編集の画面（サイドパネル・別ウィンドウの Studio）は、制作アプリができるまで開発用として残す。

- **拡張のアイコンを押すと開く窓**：案内・困ったとき・応援（FANBOX やクラファンへのリンク）・設定の書き出しと読み込み・プライバシー。ボタンはどれも「押すと1つの決まった動作」（制作アプリとつなぐ、作品を止める、作品を切り替える など）
- **YouTube の中のアイコンとスライダー**：プレーヤーの操作バーにアイコンを置き、押すとスライダーが出る。変えられるのは、作者が作品の中で「見る人が変えてよい」と決めた項目だけ（キャラの大きさ、光の強さ、音への反応の強さ など）。見る人の値は作品データではなく見る人の設定に保存し、作品を更新しても消えない。置き場所はサイトのアダプターが持ち、見つからなければ置かない。YouTube のボタンをずらしたり隠したりしない（G1）
- **制作アプリ**：翔太が普段使う Chrome とつなぐ（方式B）。アプリの中にブラウザを開く方式や、アプリが別の Chrome を起動する方式は、Google のログインで詰まる可能性が高く、ログインしていない YouTube は「よそのYouTube」になるので採らない。作者が編集する画面と、見る人が体験する画面がずれないことを優先する
- **クラッシュ報告など外へ送る仕組み**は、入れるならプライバシーの方針と、すべて切れる選択肢を最初から用意する

### 方式Bの仕組み

- **要素の位置・シグナル・編集データ**：nativeMessaging（JSON。アプリから拡張へは1件 1MB まで）。インストーラーが接続の設定も入れる。拡張の ID はウェブストアの ID に固定する
- **タブの映像**：拡張のオフスクリーンドキュメントで tabCapture し、WebRTC でアプリへ送る。接続の手続きは nativeMessaging でする。tabCapture は使う人が拡張を押したタブにしか許されないので、「このタブを制作アプリとつなぐ」を1つのボタンにする
- **映像の上のクリック**：アプリは「映像のこの位置」を送り、要素 ID への変換は拡張のコンテンツスクリプトが今の画面で行う。映像は少し前の画面なので、アプリの手元の情報で決めるとスクロール中にずれる。拡大率・画面の倍率も拡張がまとめて扱う
- **ページを動かす操作**：スクロールや再生・一時停止は、コンテンツスクリプトからページの API で動かす。マウスを乗せたときの見た目は WWT の側で「乗せた状態」を再現して見せる。メニューを開くような本物の操作は、使う人が Chrome で直接する。debugger の権限は使わない（警告が強い）
- **制作アプリの中身**：Electron が素直（WebRTC が入っていて、TypeScript のまま書ける）
- **権限**：nativeMessaging を足す。権限なしの方法（アプリが PC の中にサーバーを立て、拡張が WebSocket でつなぐ）には、どの Web サイトからも話しかけられる・ポートがぶつかる・ファイアウォールの警告が出る、という弱点がある。nativeMessaging は決めた拡張とアプリの間でしかつながらないので、こちらを選ぶ。ウェブストアでの見え方は、試作のときに確かめて書き足す
- **作品データの検証は拡張の側に残す**：制作アプリから届くデータも、今と同じ安全の検証を通す（アプリにはほかの人の作品も入るため）
- **最初の試作で確かめること**：Chrome がアプリの後ろに隠れたとき・最小化したときも映像を取り続けられるか、映像の遅れ、CPU の負担、映像の上のクリックが正しい要素に変わるか

### ほかのサイト・ほかのブラウザに耐える3本の線

最終的には YouTube 以外のサイトと、Chrome 以外のブラウザに広げる。今はほかに向けて作らず、境界だけを守る。

1. **アプリと拡張のやり取りに、YouTube と Chrome の言葉を入れない**：セマンティックレイヤーの言葉（カード・ボタン・見出し・動画の枠 など）だけで話す。通信に版番号をつけ、古い版とも話せるようにする
2. **サイトごとの違いは `src/sites/` のアダプターに閉じ込める**：設定のアイコンもアダプターが持つ「置き場所」の1つ。置き場所がないサイトでは、操作面にかからない隅に小さく出すか、ツールバーのアイコンだけにする
3. **ブラウザごとの違いは `src/browser/` に閉じ込める**：Chrome にしかない機能（サイドパネル・オフスクリーンドキュメント・tabCapture）を、コードのあちこちで直接呼ばない。manifest もブラウザごとにビルドで作り分ける。検証のときに、Chrome 固有の呼び出しがこの外に出ていないかを確かめる

映像の取り方はブラウザによって違う（Chrome・Edge は tabCapture、Firefox は拡張から映像を流し続ける機能がない、Safari は制限が多い）ので、差し替えられる形にする。どのブラウザでも使える最後の手段は、制作アプリが OS の機能でブラウザの窓を直接映すこと。クリックを要素に変える処理は、この場合も拡張がする。

### 今からやっておくこと

R3 以降、編集の画面に手を入れるときは、編集の操作を「画面」ではなく「作品データへの命令」として切り分ける。制作アプリに移すときに、命令をそのまま使える。R8 の前に「調べて計画」で小さな試作を作り、上の「最初の試作で確かめること」を測ってから本番に入る。

## G1とキャラ

操作を壊さないこと（G1）が、そのままキャラの「よける」動きになる。カードの上に座っているキャラにマウスを近づけると、ひょいとよける。守るための仕組みが、性格のように見える。

- **G1.2が土台**：今のG1は、操作部品に近づくとページ全体の効果を止める。キャラが歩き回るなら、止める範囲を「近づいた部品に重なるものだけ」に絞る必要がある
- **止めるのではなく、よける**：キャラは絵と違って動けるので、重なりそうになったら、消える代わりに dodge で横へ移る。よけきれないときは、今までどおり消える（守る力は弱めない）
- **動いているキャラの当たり判定**：キャラはクリックを受けない（本物のボタンが押せる）。触って反応するやり取りを入れるときは、G1の設計と一緒に決める
- **性能**：3Dのキャラが常に動くので、「描画と性能」の3つの物差し（拡張のCPU時間・GPUの描画時間・動画のフレーム落ち）の基準を、キャラがいる状態でも守る。見えていないとき（タブが裏、画面外）は止める

## 今ある機能との関係

作ってきたものは捨てず、キャラを中心に並べ直す。新しく作るのは、性格と部品の「できること」、場所の間の移動が中心。

| 今あるもの                               | 新しい中心での役割                                           | 扱い                     |
| ---------------------------------------- | ------------------------------------------------------------ | ------------------------ |
| G1（操作を壊さない）                     | キャラがボタンの上に来ても操作を邪魔しない。よける動きの土台 | G1.2で止める範囲を絞る   |
| サイトアダプター                         | キャラが歩ける地形と、部品の「できること」                   | 広げる                   |
| 3Dモデル・VRM                            | キャラ本体                                                   | 中心にする               |
| シグナル                                 | きっかけと反応（段階2）                                      | キャラにつなぐ           |
| テイクの記録                             | 演技で記録（段階3）                                          | キャラにつなぐ           |
| タイムライン                             | 細かく作る人のため（段階4）                                  | そのまま                 |
| 画像・動画のレイヤー                     | キャラの周りの小物や背景                                     | そのまま                 |
| UIの着せ替え                             | 世界観を大事にしたい人のための付属の機能                     | 残す。これ以上は広げない |
| エディター（サイドパネル・別ウィンドウ） | 最初の画面を「キャラを住まわせる」に                         | UX1で組み直す            |

着せ替えに「絵として置く」モードを足す案は、取りやめる。キャラを飾りたい人は、キャラを住まわせればよい。

## 最初の作品：機械の部屋

**YouTubeの裏には、機械とケーブルだらけの部屋がある。トルーシェはUIの縁で暮らしながら、その奥にいる「何か」に怯えている。** これは翔太の個人作品で、部屋・影・ケーブル・キャラの動きはすべて作品に属する。WWTに足すのは、それを動かす仕組みだけ。

正体は見せず、気配と影とキャラの反応で怖さを伝える。絵柄は線画の手描き調（漫画的な輪郭線、少ない色数、くすんだ青緑）。写実は狙わず、粗さを不気味さにする。

|        | 作品（翔太・リポジトリの外）                                                     | WWTの仕組み                                                |
| ------ | -------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| 空間   | 部屋・棚・CRT・ケーブルの glTF（Blender で作る）                                 | UIの裏に置く層、glTF の再生、揺れ                          |
| キャラ | トルーシェ（VRM）、動作、怯え方の演技                                            | 縁に座る・バーの上に立つ、感情の値で振る舞いを変える       |
| 光     | 部屋の色・光の当て方                                                             | 動画の明るさ・色のシグナル（`docs/spatial-design.md` 5節） |
| 時間   | 影が蠢く・ケーブルがざわめく演出                                                 | モード（操作中・鑑賞中・シアター）、`user.idle.duration`   |
| 音     | 低音で部屋の光とケーブルが脈打つ、盛り上がるとトルーシェが楽しそうにリズムに乗る | 音のシグナル（下の「音」の節）、感情の「楽しい」           |

素材を作品として分けるのは、売り方の候補に「作る道具を売る」があるため。デモは「WWTでここまで作れる」の証明になるので、動かす仕組みはWWTの機能として作る。

### 重ね順（奥から）

1. 部屋（ページの一番下）
2. YouTubeの背景（透明にする）
3. 読みやすさの板（読む部品の下だけ）
4. 文字とUI（そのまま）
5. フレーム（縁を這うケーブル、カーソルの懐中電灯）とキャラ

### 読みやすさの板

コメント・説明・動画のタイトルなど、読む部品の下にだけ半透明の板を挟む。部屋を文字の裏に置いても読めるようにするため。

- 板は読む部品の背景色として当てる。部品と一緒に動くので、スクロールしてもずれない。部品の位置はアダプターが知っている
- 濃さは計算で決める。白い文字を 4.5:1 で読めるように、板の後ろが一番明るいときでも足りる濃さを下限にする。部屋の一番明るい所が中くらいの灰色（相対輝度 0.2）程度なら、1割の濃さで足りる（後ろが真っ白なら8割以上）
- 動画のフラッシュで部屋が明るくなる瞬間だけ、同じ光のシグナルで板を濃くする

### 決まり

- **操作部品の上には重ねない（G1）。** 動画の上は場面を選んでよい
- シークバーは保護範囲で切り抜かれるので、「乗って運ばれる」は「バーのすぐ上に立って運ばれる」。ポインターが近づくと G1.2 で止まるので、そこで「よける」を使う
- 動作に Mixamo を使うのは、この作品の中だけ。Mixamo は生のアニメーションファイルを配ることを禁止しているので、WWTの標準セット（.vrma）には入れない（[Mixamo FAQ](https://community.adobe.com/questions-696/mixamo-faq-licensing-royalties-ownership-eula-and-tos-589400)）
- フル規模の「音に共鳴する電脳空間」はWeb版ではやらない。デスクトップ版か、別の作品に取っておく

## 描画と性能

**部屋とキャラは GPU で描き、1枚の canvas にまとめる。** 描画器は three.js の `WebGPURenderer` で、WebGPU が使えない環境では WebGL2 に切り替わる。

- WebGPU は、描く物が多いときのメインスレッドの命令のコストが小さい。ケーブルを大量に描く部屋に向く。ケーブルの揺れや影の動きは compute shader で回す
- 今の 3D は、描いた結果を 2D の canvas にコピーしてページに載せている（`docs/spatial-design.md` 6節）。全画面の部屋ではこのコピーが重いので、1枚の canvas に直接描く
- 今の VRM の描き方（`WebGLRenderer`、`powerPreference: 'low-power'`）は急いで書き換えない。部屋の描画器で先に使い、キャラを移す時期は測って決める

合否は次の3つで決める。

| 物差し                             | 見るもの                                                          | 基準                         |
| ---------------------------------- | ----------------------------------------------------------------- | ---------------------------- |
| 拡張の CPU 時間（1フレームあたり） | YouTube 自身の処理との取り合い（操作の引っかかり）                | 中央値 +0.5ms、p95 +1ms 以内 |
| GPU の描画時間                     | 部屋とキャラの重さ（WebGPU の timestamp query）                   | 部屋を入れるときに決める     |
| 動画のフレーム落ち                 | GPU を動画の再生と取り合っていないか（`getVideoPlaybackQuality`） | 拡張なしと比べて増えない     |

画質の段階切り替え、解像度の自動調整、タブが裏のときの停止は最初から入れる。動画の明るさは、小さい canvas で間引いて読む。

## 音

**音に合わせて、光と世界が脈打ち、キャラが楽しそうにする。** 動画の音を解析して、シグナルとして作者に開く。

| シグナル（案）   | 中身                         | 使い道の例                                    |
| ---------------- | ---------------------------- | --------------------------------------------- |
| 音量             | 今の音の大きさ               | 部屋の光の強さ                                |
| 低音・中音・高音 | 帯域ごとの強さ               | 低音でケーブルが脈打つ                        |
| 拍               | 音が立ち上がった瞬間の出来事 | 拍ごとに光が跳ねる、キャラがうなずく          |
| 盛り上がり       | 数秒の平均でゆっくり変わる値 | トルーシェの「楽しい」が上がり、踊る（dance） |

感情に「楽しい」を足す。盛り上がりと拍で上がり、リズムに乗る・踊る。怖い場面（恐怖が高い）では楽しいより恐怖を優先する。

### 音の取り方

1. **まず `video.captureStream()` を試す。** 動画の音を分岐して読むだけで、YouTube の音の経路は変えない。権限も要らない。拡張が更新・停止しても音は消えない
2. 取れない場面があれば、`chrome.tabCapture`（＋ offscreen document）を足す。権限を足すこと自体は問題にしない。ただし、取り込んだ音を再生し直さないとタブの音が消えること、取り込みの開始に利用者の操作が要ることを確かめてから決める
3. `createMediaElementSource` で動画を Web Audio につなぐ形は使わない。YouTube の音が拡張の中を通るので、拡張が止まると動画の音が消える

取れないとき（DRM の動画、広告の切り替わり）は、音を「無音」として扱わず、「取れない」として作品に渡す（動画の光と同じ扱い）。

### 守ること

- 光の明滅は1秒に3回までに抑える（光過敏への配慮、WCAG 2.3.1）。作品からは外せない
- 「動きを減らす」の設定（reduced-motion）では、脈打ちを弱める
- 読みやすさの板は、音で部屋が明るくなる瞬間も文字が読める濃さを保つ

## デモ動画の前に満たす水準

**デモ動画は急がない。** 次の5つを満たしてから出す。

1. 台本の6場面が、本物の YouTube で撮り直しなしに通る（その場面に合わせて仕込まない）
2. 30分ふつうに使っても（見る・検索・コメントを読む・シーク・全画面）、操作の破綻も、読めない文字も出ない
3. 上の性能の物差しの基準を守る
4. 画面遷移・ウィンドウの大きさ変更・ダークとライト・広告の場面でも崩れない
5. 翔太が絵（構図・色・線）を見て「出していい」と思える

台本（30〜60秒）：縁に座るトルーシェ → 再生するとバーの上で運ばれる → 暗い場面で奥のケーブルが揺れ、振り向いて固まる → フラッシュで奥に影が一瞬見え、枠の陰に隠れる → カーソルを近づけると恐る恐る寄ってくる → シアターモードで部屋が開き、画面の前で一緒に見る後ろ姿。

### コンテストまでの計画（2026-11-05 決定）

WWT を最後まで作り、年内の完成を最優先にする。別の収益化アプリは作らない。ロリポップ!「デプロイナウコンテスト2026」（12/8 締切）に、12/5 を目標に応募する。未踏は当面見送る。クラファンは続けて検討し、世界観を作り込んでから出す。機能を足し続けるより、仕上げることを優先する。

**デモ動画**：「デモ動画の前に満たす水準」の5つは下げない。台本の6場面に要るのは R3（縁・バー）、R4（怖い・安心・隠れる）、R5 の一部（UIの裏の層・読みやすさの板・動画の光・モード）と部屋の絵だけ。音への反応・WebGPU・FBX・制作アプリ・性格はデモに要らない。

| 確認日    | 確かめること                                                          |
| --------- | --------------------------------------------------------------------- |
| 11/15ごろ | R3（縁に座る・バーの上）が本物の YouTube で動いているか               |
| 11/25ごろ | 6場面が一度通しで動くか。そろわなければ場面を減らす（水準は下げない） |
| 12/5      | 動画と Playground で応募                                              |

**部屋の絵**：翔太が Blender で作る。エンジンは仮の箱で先に進め、絵はできたものから差し替える。最初に CRT 1台とケーブル1本の試作を書き出し、読み込めるかを確かめてから本格的に作る。約束：glTF（.glb）、特別なシェーダーを前提にしない、輪郭線はメッシュ（インバーテッドハル）、三角形5万〜10万程度・テクスチャ2048px以下、揺らす物は別のオブジェクトに名前を付ける、影や隠れ場所には目印の Empty、実在の製品のロゴは作らない、元ファイルはリポジトリの外。

**Playground（応募するサイト）**：YouTube のページは持ってこられず、埋め込みの YouTube プレーヤーには上に何も重ねてはいけない決まりがある（[Required Minimum Functionality](https://developers.google.com/youtube/terms/required-minimum-functionality)）。そこで、翔太が作る簡単な動画サイト（自前の動画・プレーヤー・シークバー、YouTube に似せない）の上で、WWT のエンジンを拡張なしで動かす。「WWT を適用」ボタンで、ただの動画サイトが別の世界に切り替わるのが見せ場。キャラは再配布できる VRM を自律行動で動かし、トルーシェは使わない。本物の YouTube での姿は、前後比較の動画で見せる。余裕があれば、拡張を Chrome ウェブストアに限定公開して「あなたの YouTube で試す」入口を足す。

**自律行動（調べ中）**：性格・感情・欲求・記憶の状態から、行動と体の動きをその場で作る。体の動きは「計算の動き＋翔太が作る姿勢（1コマの .vrma）＋IK」を基本にし、Mixamo のデータを配る物に使わない。LLM は使わず、状態機械・Utility AI などで考える。R3-2・R4 とどう重ねるかと、Playground に間に合う一番小さな形を、Claude Code が調べる（docs/autonomy-plan.md・docs/playground-plan.md）。12月の頭までに見せられる自然さに届かなければ、2D の描き出しの連番をシグナルで動かす形に切り替える。

**進め方**：1回の作業は、R の段階のまとまった塊にする。塊の中は小さなコミットに分け、Codex の検証は塊の終わりに1回。作品データの版上げは1回に1段まで。「同じ問題への挑戦は3回まで」は塊の中の個々の不具合ごとに数える。性能の計測で、背景の CPU 負荷は組を外す条件にせず、参考値として記録する。

**年内（v1）に入れないもの（案）**：FBX の取り込み（R7）、制作アプリ（R8 の大部分）、機械の部屋の作り込みの残り（R6）。v1 の範囲は 11/5〜11/11 に翔太が決める。
