# 奥行きの土台・空間図法・ガラスの板

2026-11-07、Claude Code。ブランチ `codex/depth-foundation`（`codex/creator-editor-spike` の `263579c` から）。設計は [設計書のスナップショット](product-design-snapshot.md)（rev 99）の「空間の設計思想」「部屋の素材の約束」「描画と性能」「エンジンの順番」の 1・2。部屋の測定は `codex/room-bake` の `docs/room-bake-plan.md`。

**中核を触った**：`src/design/schema.ts`・`src/design/migrations.ts`・`src/world/`・`src/host/`（`page-controller.ts` を含む）・`src/sites/`・`scripts/build.mjs`・`playwright.config.ts`。**作品データを v17 に上げた**（ミルドの v16 の上に1段。初めは v16 で作り、ミルドを作業ブランチに取り込んだあと載せ直した）。Codex の検証では e2e 全件（Windows）が要る。

## 0. 見せられる成果

本物の YouTube の動画ページの奥にテスト用の部屋（`codex/room-bake` の部屋）があり、YouTube の背景が透明になって部屋が見える。UI の領域（プレーヤー・おすすめ欄・タイトルとコメント・ヘッダー）の下に、部屋をぼかしたガラスの板が浮かぶ。マウスを動かすと部屋だけが左右上下にずれ、ページを下へスクロールすると部屋がドリーズームで奥へ引く。板は部屋に影を落とし、動画の色の光がプレーヤーのまわりの部屋と板の縁を照らす。

スクリーンショットと録画は `.work/space-live`（コミットしない）。

## 1. 仕組みの分け方

| 役割                 | 置き場所                                                  | 中身                                                                                                                                                                                                                          |
| -------------------- | --------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 空間座標→カメラ→投影 | `src/world/space.ts`（純粋な関数）                        | `cameraTarget`（シグナル→カメラが行きたい所）、`stepCamera`（時間で追う。コマ数によらない）、`projectCamera`（ドリーズームの画角）。板の位置（`glassPlates`）、読みやすさの濃さ（`plateAlpha`）、動画の光（`stepVideoLight`） |
| ページを読む         | `src/host/space.ts`                                       | ポインター・スクロール・reduced-motion・タブの可視・全画面・UI の領域・動画の色を読み、world の関数に通して描画に渡す。動いた時だけ描く                                                                                       |
| 描く                 | `src/renderers/three/room.ts`                             | 1枚の canvas（ページの中身の下）。部屋を光の層を混ぜたライトマップで描き、1回のパスで板（ぼかし・縁の屈折・縁のハイライト・色味・読みやすさの濃さ）と、板の影・動画の光を部屋に足す                                           |
| サイトの事情         | `src/sites/youtube-backdrop.ts`（`SiteAdapter.backdrop`） | YouTube 自身の背景（`html`・`body`・`ytd-app`）だけを透明にし、部屋の置き場所（`body` の子、`z-index:-1`）を渡す。UI の領域（いくつかの決まった入れ物と重要度）と動画の要素を渡す                                             |
| 作品データ           | `src/design/space.ts`・v17                                | 部屋の素材・光の層の重み・カメラ・板の見た目・動画の光の数値だけ。シェーダー・選択子・CSS は入れない                                                                                                                          |

### 重なり順（奥から）

1. 部屋の canvas（`body` の子、`z-index:-1`、`body` の先頭）
2. 奥の作品（`depth: 'room'` だけの作品のとき。部屋の canvas のすぐ後、同じ `z-index:-1`）
3. YouTube の中身（背景を透明にした `ytd-app` 以下）。ヘッダーやボタンなど、自分の背景を持つ部品はそのまま
4. 手前の作品（今までどおり、ガードの下）

板は canvas の中に描くので、DOM には何も足さない（`backdrop-filter` も使わない。ぼかしは部屋の描画のミップマップから取る）。

## 2. 自分で決めたこと

| 決めたこと                                                                                                                                                                                               | 理由                                                                                                                                                                                                                                                                                                                                                           |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 部屋は1つの .glb（光の層を PNG にして埋め込む）。`scripts/room/pack-room.mjs` で EXR からまとめる                                                                                                        | 設計書の「1つの部屋を1つの glTF にまとめる」。部屋がふつうの3D素材（GLB）として、今の取り込み・検証（`inspectGlb`）・保存・バックアップをそのまま通る。EXR の読み込み器を拡張に足さない                                                                                                                                                                        |
| 光の層の符号化は「平方根＋層ごとの倍率」の 8bit                                                                                                                                                          | PNG は 16bit を 8bit で読まれる。平方根で暗い所の段差を減らした。倍率は層の 99.9 パーセンタイル（ランプの電球など数点は飽和させる）                                                                                                                                                                                                                            |
| 描画器は `WebGLRenderer`（`low-power`）                                                                                                                                                                  | 部屋の測定と同じ描き方。WebGPU は次の塊以降（設計書「描画と性能」の WebGPU は未着手）                                                                                                                                                                                                                                                                          |
| 部屋は画面の 0.75 倍で描き、合成は等倍                                                                                                                                                                   | 部屋はほとんど板越しのぼかしで見える。GPU の画素の数を減らす（room-bake の測定で重さを決めるのは画素）                                                                                                                                                                                                                                                         |
| 板の文字の色は、YouTube の灰色の補助の文字（ダーク `#aaaaaa`、ライト `#606060`）を 4.5:1 で守る                                                                                                          | 設計書の決まりは「白い文字が 4.5:1」。灰色の文字はそれより暗く、白だけを守ると読めない。白い文字はこれで 8:1 以上になる                                                                                                                                                                                                                                        |
| 板の濃さは画素ごとに、その画素に見えている部屋（ぼかし後）から決める                                                                                                                                     | 板の後ろが明るい所だけ濃くなる（設計書の「明るい光源の真後ろの板は濃くなる」）。動画のフラッシュで部屋が明るくなる瞬間も、同じ計算で板が濃くなる                                                                                                                                                                                                               |
| 濃さの限界に 8bit の余白（ダークは 0.9 倍、ライトは +0.02）                                                                                                                                              | 余白なしでは本物の YouTube で 4.47:1 になった（出力を 1 バイトに丸める分）                                                                                                                                                                                                                                                                                     |
| 板の最低の濃さ：操作 0.32・読む 0.2                                                                                                                                                                      | 暗い部屋の上でも、板がガラスとして見えるように                                                                                                                                                                                                                                                                                                                 |
| 屈折は縁の 20px だけ、ハイライトは縁の 3px だけ                                                                                                                                                          | 文字は縁から 12px 以上内側にある（板は領域より 12px 外へ出す）。文字のある中央は静か                                                                                                                                                                                                                                                                           |
| 板の領域は「入れ物」単位：ヘッダー・プレーヤー・おすすめ欄・タイトルとコメント・チャット・ホームと検索の一覧・ミニガイド・ミニプレーヤー                                                                 | 毎フレーム読めるのは数個の箱だけ。カードごとの板（カードの間から部屋が見える）は次に試す                                                                                                                                                                                                                                                                       |
| ヘッダーにも操作の板                                                                                                                                                                                     | 動画ページのヘッダーは YouTube 自身が背景を持たず（ページの背景が透けている）、部屋の窓の光がログインボタンの後ろに来た                                                                                                                                                                                                                                        |
| UI の領域情報は `SiteBackdrop.regions()` に置いた                                                                                                                                                        | 設計書は「G1 の操作部品の一覧を広げる。別の仕組みを作らない」。G1 の一覧（`OperationSource`）は守りのための細かい読み取りで、奥の作品だけのときは動かさない（ガードは手前の物だけ）。そこで、同じアダプターの中に「操作部品の入れ物」を重要度つきで返す口を足し、操作の重要度の入れ物はその操作部品の一覧の外枠になるようにした。G1 の守りはこの情報に任せない |
| 部屋の置き場所は `body` の子・`z-index:-1`                                                                                                                                                               | `ytd-app` は位置づけされているが自分の重なりの文脈を作らないので、負の重なりの子はその下に描かれる。本物の YouTube で確かめた（canvas を指すクリックは0）                                                                                                                                                                                                      |
| 奥の作品は「すべての根が `depth: 'room'` のとき」だけ奥に描く                                                                                                                                            | 1つでも手前の物があればガードは要り、今のガードの道は1つの層の中の重なりを前提にしている。混ざった作品は今までどおり全部を手前（ガードあり）で描く。分けて描くのは次の塊（キャラが部屋を歩くとき）                                                                                                                                                             |
| `depth` の省略は「手前」                                                                                                                                                                                 | 設計書は「既定の奥行きは UI の奥」。ただし古い作品の見た目を変えないため、省略を手前のままにした（移行で値を足さない）。新しい作品を作る側（制作アプリ・エディター）が `room` を既定にする。エディターの既定はまだ変えていない                                                                                                                                 |
| 部屋がないとき（`space` がない・読み込み中・全画面）は、奥の作品も手前に描く                                                                                                                             | 奥に描く場所がない。ガードの下に戻る                                                                                                                                                                                                                                                                                                                           |
| カメラ：ポインターで左右 0.2m・上下 0.2m、スクロールで下がる 0.1m とドリーズーム最大 1.5m × `dolly`                                                                                                      | room-bake の「外が見えなかった幅」の中。上下は部屋の範囲の半分にして床と天井を残した                                                                                                                                                                                                                                                                           |
| 動画の光は 500ms ごとに GPU で 8×5 に平均した色を読み（待たずに数フレーム後に受け取る）、1秒に輝度 0.5 までしか変えない                                                                                  | 10% の明滅に 0.2 秒かかるので、1秒に 2.5 回まで（設計書の 3 回以内）。読めない動画（DRM など）は黒にせず、同じ速さで消える                                                                                                                                                                                                                                     |
| 再描画は「カメラ・板・光のどれかが動いたとき」だけ。光だけの変化は 30fps まで                                                                                                                            | 部屋は止まっていれば描き直さない                                                                                                                                                                                                                                                                                                                               |
| 読みやすさとガードの「わざと壊したビルド」：`WW_SPACE_BREAK=density`（板の濃さを外す）・`stacking`（奥の作品を UI の上に出す）                                                                           | 守りがテストで捕まることを確かめるため（`.work` にだけ出せる）                                                                                                                                                                                                                                                                                                 |
| テストの覗き口：`WW_SPACE_PROBE=1`（`.work` だけ）で、部屋の状態（`data-ww-room-frame`）・ガードの状態（`data-ww-guard`）・描いた画素（`data-ww-room-sample` に点を書くと `data-ww-room-pixels` に返る） | 実サイトで、描いた板の色を読んで文字のコントラストを測るため                                                                                                                                                                                                                                                                                                   |

### 設計書と違う判断

- **YouTube のアンビエント（映画のような光）** は止めていない。動画ページでプレーヤーのまわりが暗い色で塗られ、部屋が見えにくい所がある。YouTube の部品の見た目は作り替えない決まりに従った
- **夜の映り込み**（余裕があれば）は入れていない
- **キャラが板に触れた跡**は、キャラが部屋を歩く次の塊に回した（今回のキャラはプレーヤーの縁のまま）

## 5. 性能

ノート PC（i7-13650HX、Chromium は内蔵 GPU を選ぶ）、Chromium 153.0.8010.12、144Hz、画面の外の表示あり、1920×1080。**仮説を確かめる段階の短い計測（各2組）**で、合否の交互計測（8組）はしていない（Codex）。要約は [benchmarks/depth-foundation-2026-11-07.json](benchmarks/depth-foundation-2026-11-07.json)。

### ガードは手前の物だけ：起動と検索 SPA の上乗せ

`scripts/g11/run.mjs` に `G11_DEPTH=room`（場面の32レイヤー・16グループをすべて `depth: 'room'` にし、テスト用の部屋を置く）を足し、同じビルドの中で「ガードあり／ガードを外した」を交互に測った。差（6秒の拡張の CPU 合計）がガードの上乗せ。

| 場面     | 作品                                         | ガードの上乗せ（ms/6秒、組ごと） | ガードの読み取り（回） | 動画の落ち（ガードあり） |
| -------- | -------------------------------------------- | -------------------------------- | ---------------------- | ------------------------ |
| 起動     | 手前（今まで）                               | +144.4、+35.6                    | 14、12                 | 2、8                     |
| 起動     | 奥（直す前：部屋の読み込み中は手前でガード） | +38.1、+92.9                     | 4、6                   | 2、0                     |
| 起動     | 奥（部屋を待つ）                             | −85.2、−51.6                     | 1、1                   | 0、0                     |
| 検索 SPA | 手前（今まで）                               | +249.0、+184.4                   | 14、15                 | 3、0                     |
| 検索 SPA | 奥（直す前）                                 | +444.4、−33.9                    | 0、0                   | 1、0                     |
| 検索 SPA | 奥（部屋を待つ）                             | +28.3、−17.4                     | 0、0                   | 6、2                     |

- 奥の作品では、起動と検索 SPA のガードの上乗せが**組の振れの中（±100ms）**に消えた。ガードの読み取りは、起動の最初の1回（設定を読む前の1回）だけ
- 直す前の版は、部屋の読み込みを待つ間、奥の作品を手前に描いてガードを掛けていた。そこで「部屋のある奥の作品は、部屋ができるまで描かない（全画面でも描かない）」にした（`place()` の `'pending'`）
- 検索 SPA の奥（直す前）の1組目 +444ms は、両方の側で部屋を描いていて、ガードの読み取りが0回なので、振れと見ている（2組目は −33.9）。プロファイルは取っていない
- 動画の落ちは、奥（部屋を待つ）の検索 SPA の1組目で 6 枚。ガードを外した側でも 1・3 枚あり、2組では傾向は言えない

### 部屋そのものの重さ

- 部屋ありの場面は、ガードを外した側でも拡張の CPU 合計が手前（部屋なし）より 6秒で約 +100〜300ms 多い（1フレーム約 +0.1〜0.35ms）。WebGL の呼び出し（GPU への命令）が拡張の時間に数えられるため。ただしこの数値は、動画の色を canvas の `getImageData` で読んでいた版のもの
- **CPU プロファイル（検索 SPA、部屋あり）で一番重い自分の処理は `getImageData`（6秒で 143ms、1回 約 4.7ms）だった**。GPU の処理を待つ読み戻し。動画の色を WebGL で読み、ピクセルバッファとフェンスで数フレーム後に受け取る形に変えた（`sampleVideo`）。変えた後のプロファイルでは消え、拡張の下の時間は 754 → 573〜615ms。残る自分の処理は `getBufferSubData`（GPU プロセスとの往復、1回 約 0.6ms）で、読む間隔を 200 → 500ms にした
- 部屋の描画の JS の自己時間（`tick`・`draw`・`remix`・`sampleVideo`）は 6秒で合計 3ms ほど。残りの大きい項目（`getPropertyValue`・画像レイヤーの `draw`・`applyLayout`）は場面の32レイヤーの今までの処理
- 部屋は止まっていれば描き直さない。動画の再生中は光の変化で 30fps まで描く
- GPU の時間・定常の交互計測・動画のフレーム落ちの拡張なしとの比較は測っていない（Codex の 8 組で）

## 7. 気になる所・引き継ぎ

- **部屋がほとんど板に隠れる**：板は入れ物（列）単位なので、部屋が見えるのはヘッダー・列の間・板越しのぼかしだけ。カード1枚ずつの板（カードの間から部屋が見える）が次の候補。読む領域を細かくすると読み取りの箱が増える
- **YouTube のアンビエント**（プレーヤーのまわりを動画の色で暗く塗る）が、部屋の見え方を変える。止めていない
- 板の位置はスクロールの1フレーム後を追う（設計書で許容）。板は領域より 12px 大きいので、文字が板の外に出ることは見ていないが、速いスクロールで数えてはいない
- 奥と手前が混ざった作品は、今は全部を手前（ガードあり）で描く。キャラが部屋を歩く次の塊で、奥の層と手前の層を分けて描く
- エディターで新しく作るレイヤーの既定の奥行きは、まだ手前のまま（設計書の既定は奥）
- 部屋の素材の約束の名前（`static_`・`dyn_`・`navmesh_` など）は、名前で描き方を分けているだけ。`marker_` の読み取り・反射のプローブ・キャラの影はまだ
- 光の層の 8bit の符号化は、暗い所のグラデーションに段差が出るかを本番の部屋で見ていない
- `WebGLRenderer` のまま。WebGPU は未着手
- 夜の映り込み・キャラが板に触れた跡は入れていない
- 利用者が実際に保存した過去の作品データでの確認はしていない

- 文字の箱を測る（文字の並びごとの Range）のが重かった。部品の箱の大きさが同じ間は「右をどれだけ詰めるか」を覚えて、1秒ごと・ページの変化のたびに測り直す（動いている間は1回に4部品、止まっている間は全部）。詰めるのは右だけなので、古い値が害になるのは行が長くなった所だけで、1秒以内に直る

### 読みやすさの確かめ方を変えた

実サイト `space-live` は、見えている文字の真後ろ（コメント・おすすめの文字・タイトルの文字の並びの中、6×12px の格子）を、描いた画素で読んでコントラストを測る。部品の箱の外に出た文字（省略記号で切れた所）は見えないので数えない。

### 気になる所（2回目）

- 文字に沿う板は「右だけ詰める」。左にインデントがある部品や、縦に余白の多い部品では、板が文字より大きい（読みやすさには安全側）
- YouTube の部品の名前（`yt-lockup-metadata-view-model`・`ytd-comment-view-model #main` など）に頼っている。変わると板が付かない部品が出る（文字は部屋の上に出る）。実サイトのテストで気づける
- シアターで黒い余白を透明にしたので、縦長の動画では映像の左右に部屋が見える（意図どおり）。操作バーのグラデーションは YouTube のまま
- 昼の光の層はテスト用の部屋で焼いただけで、光の強さは目で決めた値
