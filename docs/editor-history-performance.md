# 編集処理とStudio履歴の計測

`npx playwright test --project=unit tests/editor-benchmark.spec.ts --workers=1` で再計測する。
数値は情報として出力し、速度の閾値では失敗させない。JSONもテスト結果に添付する。

32画像、シグナルなし／32ルール×8キー／32ルール×64キー。最初のレイヤーの配置だけを変え、
10回のウォームアップ後の100コマンドの中央値・最大値を測る。
時間にはcoreの更新・履歴記録・snapshot生成を含む。ブラウザーの描画や通信時間は含まない。
Studio送信量は履歴100件時の通常更新メッセージをJSON化したUTF-8バイト数。
符号化時間にはsnapshot/checkpoint生成とJSON化を含む。変更後は実際にhostが使うエンコーダーに
最後のコマンド直前の状態を渡し、そこからの差分を測る。計測対象のコマンド・作品・履歴件数は同じ。

## 変更前（3f16157、2026-10-21）

Windows、Node v24.16.0、1 worker、上記コマンドで計測。
依頼文の計測とは環境・入力が異なるため、以降は同じfixture・コマンドで比較する。

| ルール×キー | 作品 bytes | 配置 中央値 ms | 最大 ms | Studio bytes | 符号化 ms |
| ----------- | ---------: | -------------: | ------: | -----------: | --------: |
| なし        |      9,424 |          0.371 |   1.892 |      991,016 |     4.867 |
| 32×8        |     35,724 |          0.919 |   1.698 |    3,752,499 |    22.538 |
| 32×64       |    163,500 |          4.295 |   8.106 |   17,168,979 |   107.275 |

Studio量は1メッセージ分。要求への返信が同じsnapshotを含む場合の重複は加算していない。
変更前の方式では、作品と履歴件数に比例して増える。

## 変更後（2026-10-21、同じ環境・コマンド）

| ルール×キー | 配置 中央値 ms | 最大 ms | Studio bytes | 符号化 ms | 復旧 bytes |
| ----------- | -------------: | ------: | -----------: | --------: | ---------: |
| なし        |          0.043 |   0.206 |          499 |     0.463 |    100,744 |
| 32×8        |          0.065 |   0.192 |          499 |     0.142 |    144,797 |
| 32×64       |          0.063 |   0.203 |          499 |     0.136 |    329,918 |

最大規模の中央値は約68倍改善した。最大値も2msの目標内だった。
通常更新は変更した数値と履歴の追加・削除だけなので、未変更のキー数を増やしても499bytesで変わらない。
数値はこの環境での観測値であり、速度の保証ではない。

接続時には初期snapshotと共有形式の履歴を送り、以降は順序番号付きの差分を送る。
差分が欠けた場合は再接続して初期状態を取得する。再接続時の復旧要求も共有形式を使う。
保存済みデータが下書きと同じ場合は参照で表す。レイヤーやルールの順序変更はID列で送り、
位置が変わっただけのルールの未変更キーデータを再送しない。32ルール×64キーの1キー編集と
保存でも、この性質をJSON往復のテストで確認する。
保存・復旧という外部入力の境界では全体検証を維持し、通常の編集では変更したノードと参照関係を検証する。
コマンドはJSON変換より先にデータ型を確認し、関数・getter・循環参照・非有限値を拒否する。
列挙値も文字列として検証するため、配列や独自の文字列変換による型のすり抜けを許さない。
履歴は凍結済みの作品を保持し、変更しないレイヤー・設定・キーを共有する。

作品のDesignDocument v11と、展開後のEditorCheckpoint v1は変更していない。
復旧保存の外側だけ共有ノード表のv2を使う。旧v1はそのまま読み込み、coreで従来の全検証を通す。
上限6MiBと履歴100件は維持した。上記の最大規模・配置履歴100件は329,918bytesに収まる。
全ノードを毎回変更する履歴など、共有できないデータが6MiBを超える場合は従来どおり明示的に拒否する。

外部データの読み込み・保存通知時の内容比較と、controllerの画面寸法用の小さな文字列化は残した。
これらは配置コマンドごとの作品全体の再検証・文字列比較ではない。
UIの見た目、作品形式、ページ内編集の素材取り込み経路は変更していない。
