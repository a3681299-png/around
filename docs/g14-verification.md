# G1.4 独立検証

2026-11-04、Codex。対象は `ed03b29c75e7997fa13d1d781350e84751131c1a`、比較元は `20ffdc360df7d6a013cbfde595aa62cc138ca413`。それぞれ `git worktree add --detach` で別フォルダへ固定した。映像上の絵だけ `4d3f39b8707db63de81466d7cba4f833dde979d9` も比較した。製品コード・既存テスト・通常の dist・main は変更していない。

## 判定

**長い待ちへの修正効果は確認できた。G1.4 全体の完了判定は保留。**

長い待ちの実描画は20/20成功し、Windows e2e 全件も268成功・60スキップだった。旧版では同じ長い待ちが今回も失敗した。確定した製品退行は今回の範囲では見つからなかった。

保留の理由は、指定CIに1件の失敗があることと、静止した不透明な絵の性能を同じ条件で4組そろえられなかったこと。CIの失敗は入力前に古いハンドルが切り抜かれた準備条件で、入力を奪った結果ではない。静止画の計測では、DOM上の可視性と実画素が食い違う回を確認した。原因は確定していない。画素が出ない回を軽い性能値として数えていない。

映像上の viewport 絵が切り抜かれる現象は3版とも再現した。これは前からある残件として分け、今回を不合格にする理由にはしない。

### CIの1失敗

[指定run 41772161277](https://github.com/a3681299-png/around/actions/runs/41772161277) はed03b29を実行していた。unit 421成功。e2eは合計267成功・1失敗・60スキップ、別のnative entry 4件は成功。

失敗は `operation-safety.spec.ts:233` の263行。無通知でプレーヤーを動かし2rAF待った後、まだ古い編集ハンドルがヒットする `own:true` を期待したが、falseだった。最初の242行のown:trueは通っている。

CIのtraceを取得して画像も開いた。538269.881msに移動、2rAFの終了は538311.187ms、538317.351msのsnapshotでは既に切り抜きが変わっていた。元の許可領域y=182〜325.5がy=54.25〜197.75へ移り、ハンドル中心(484,253.764)を除外した。停止状態は空で、制作ハンドルのclip制限が記録されている。538334.954msのassertより前の保護更新だった。[抽出時系列](benchmarks/g14-verification/ci-clip-timeline.json)、[元trace](benchmarks/g14-verification/ci-stale-handle-trace.zip)、[失敗画像](screenshots/g14-verification/ci-stale-handle.png)

したがってこのCI失敗を、ハンドルが本物の入力を奪った証拠として扱えない。保護の更新と、意図的に古いハンドルを残したい試験の準備条件が競合した可能性がある。ただし通常ビルドのCI traceでは、更新の呼び出し元がidleタイマーか他の描画更新かまでは分からない。Windowsの同一試験は旧・新各10/10成功した。CI環境で旧版を同じ位相へ固定した対照は未実施なので、G1.4が揺れを増やしたかは未確定。

次担当の案は、この入力時防御の試験だけ予約なしの開発ビルドで古いハンドルを確実に残し、入力拒否・native到達のassertを維持すること。自動再確認は別のG1.4実描画試験で確認する。今回は既存テストを緩めず、CIも成功扱いにしていない。

従来のプローブはdocument_idleの注入から記録を始めるため、従来セットの「遷移6秒まで」には3フレームしかない回もあった。これを性能合格の根拠にしなかった。追加の4組では主世界にdocument_startからフレーム時計だけを置き、拡張の実コールバックを0〜6,000msへ割り当てた。CPUを主世界のページ処理と合算していない。少なくとも120フレーム採れることも試験条件にした。

### 静止した不透明な絵

最初は64×64pxを切り抜きの許す大きな矩形へ置いた。撮影面がStudioによって縮む問題、配置の基準寸法のずれを検証用コードで直した。その後も実画素が白になる準備失敗が出た。64pxの条件は3組まで完了したが、4組目とその再採取は失敗した。この値を正式な4組へ混ぜていない。

最後はプレーヤーと右欄の隙間に8×64pxで表示し、全512画素が不透明な指定色であることを条件にした。1組は前後とも通った。6秒のCPU合計は前0.00ms・後36.80ms、平均は前0.0000ms・後0.0455ms/フレーム。後はsetTimeoutが14回、最後までvisible・opacity=1・停止なしだった。中央値・p95が0でも追加処理は存在する。

次の回は、名前g14-solid.png、visibility=visible、opacity=1、停止・issuesなし、clipが配置を許し、decodedBytes=16,384・inFlight=0なのに、PNGの該当512画素が全て白だった。[状態](benchmarks/g14-verification/static-gap-failure.json)、[独立した画素集計](benchmarks/g14-verification/static-gap-pixel-audit.json)、[画像](screenshots/g14-verification/perf-gap-failed.png)。CSSや統計だけで描画できたと数えなかった。通常ビルドの同一操作との対照が未了なので、計測ビルド固有か、nativeとの重なりか、描画通知の問題かは確定していない。

3つの準備修正でも成立しないため、around-verifyの「同じ不具合を直す試みが3回目でも基準に届かなければ、止めて報告する」に従い、追加の作り直しを止めた。**この静止画性能は4組未達で、合格にしていない。**

## 直していないものと引き継ぎ

- 製品と既存テストは、依頼どおり直していない。検証用のビルド・試験・計測器と報告だけを追加した。
- 次担当はCIのstale handle試験の準備を決定的にし、Linuxでも通ることを確認する。最後のnative入力のassertを緩めない。
- 静止画の白い回は、同じ手順を通常ビルドの旧・新版で比べて分類する。assetの実画素、最終paint、nativeとの重なりを記録し、原因が分かるまで性能合格にしない。
- 起動は文書遷移からの0〜6秒と、実際の拡張起動処理を分けて記録する。今回の0msをcold startの合格として使わない。
- HOLDの単独faultを、HOLDの窓を確実に踏む実描画試験へつなぐ。計画のdirty時の文書差も整理する。
- 翔太が普段のログイン済みプロフィールで確かめる場合は、静止した不透明な作品を置き、無入力のまま操作部品の変化を待つ。シアター切替・広告切替を含む日常条件は今回の独立した実サイト比較では網羅していない。ログイン後のコメント入力も未確認。
