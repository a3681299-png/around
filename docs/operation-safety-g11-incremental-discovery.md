# G1.1 候補探索の差分化と再計測

2026年10月24日。**G1.1の起動直後 +2ms以内は、まだ確認できていない。** 再取得1回のコストは半減した。ただし、この環境ではフレーム全体p95のばらつきが大きく、+2msの合否を判定できなかった。作業先は `codex/creator-editor-spike`。

## 原因と変更

起動直後の再取得は6秒で約58回、中央値6.6〜13.8msだった。その約半分は、操作面の候補を探す `querySelectorAll` で、約9,700要素の文書に7回の走査をしていた。

- 7本のセレクターを1本にまとめた。割り当ては従来と同じ（最初に一致したセレクターが所有し、文書順に番号を振る）。効果はわずかで、単独の対策では足りなかった。
- 候補の列挙を差分化した。`operation-source.ts` が、挿入されたサブツリーと、class・role・href・contenteditable が変わった要素を集めて Adapter へ渡す。Adapter（`youtube-operations.ts`）は文書順の候補一覧を持ち、通常は差分だけを更新する。
- 次の場合は従来どおり文書全体を走査する：最初の読み取り、入力直前の検査（`validate` にイベントがあるとき）、通知が64件を超えたとき、前回の全体走査から1秒以上たったとき、`active(true)` による再開。
- 位置・可視性・合成順の読み取りは、毎回すべての候補に対して新しく行う。画面外の候補も省かない。入力直前の同期再取得、世代確認、ヒット先確認、縦方向の保護帯、安定待ちは変更していない。
- 監視する属性に `href` を足した（`a[href]` に一致するかが変わるため）。再取得の引き金は増やしていない。

## 検証（Windows、Chromium 143.0.7499.4、ヘッドレス、1920×1080）

引継ぎ文書の環境は Chromium 153。今回は別のビルドで、**前回の値と絶対値では比べられない。**

- 再取得1回の中央値（起動直後、検査あり、各実行4組。旧＝`cb23a68`の本体、新＝今回）

- 回数は旧が214〜227回、新が214〜234回（4組・各6秒）。回数はほぼ変わらず、1回の重さが約半分になった。
- フレーム全体p95の増分は、旧が +7.95・-8.98・+2.08ms、新が +18.54・+2.00・-13.35ms と符号も安定しなかった。この時間帯は検査なしのp95自体が88〜110msで、環境の負荷が大きい。**+2ms以内かどうかは、この測定では判定できない。** 午前の最初の測定（検査なしp95 21.8ms）では、旧コードで +9.27msだった。
- 候補一覧をキャッシュする使い捨ての実験では、増分が +2.17msまで下がった。列挙が支配的という見立てと矛盾しない。
- 検査ありのRAF内の拡張CPUは、中央値で検査なしより約2.6ms大きい（5.4ms対2.9ms）。再取得のないフレームにも固定費が残る。次の調査対象。
- 同じ実DOM上の比較（`compare-source.mjs`、基点 `e2ac377`）では、可視操作面と保護領域は全区間で一致した。この比較は入力検査と同じ全体走査を通るため、差分化の速度は表さない。
