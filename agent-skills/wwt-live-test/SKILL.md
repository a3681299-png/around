# WWT の e2e テストと実サイトのテスト

原則は AGENTS.md の「テストを製品の今の挙動に合わせて緩めない」。失敗したら、まず製品側の原因を疑う。

## テストの3つの層

| 層                | どこで動くか                                                  | 実行                                                             |
| ----------------- | ------------------------------------------------------------- | ---------------------------------------------------------------- |
| unit              | Node の中。`playwright.config.ts` の `unitSpecs` に名前を足す | `npm run test:unit`                                              |
| e2e（模擬ページ） | 拡張を読み込んだ Chromium ＋ `tests/fixtures/youtube.html`    | `npm run build` → `npm run test:e2e -- tests/<名前>.spec.ts`     |
| 実サイト          | 本物の YouTube。環境変数で明示したときだけ動く                | `WW_LIVE_<名前>=1 npm run test:e2e -- tests/<名前>-live.spec.ts` |

- CI は unit と e2e を毎回動かす。e2e は `--shard=N/4` で4台に分けて並べる。実サイトは CI では動かさない（ネットワークと YouTube の変化で結果が揺れるため）
- 手元でどこまで回すかは AGENTS.md の「テストの段階分け」に従う。作業の途中は触った部分の spec だけでよい。spec を1つの機能ごとに分けておくと、選びやすい
- 1件ごとに拡張入りの Chromium を起動し直すので、1件あたり数秒かかる。同じ準備で確かめられることは1つのテストにまとめ、似たテストを増やしすぎない
- 新しい実サイトのテストは `test.skip(process.env.WW_LIVE_<名前> !== '1', '理由')` で始め、既存の `*-live.spec.ts` と同じ形にする
- e2e は `workers: 1` で順に動く。ネイティブの Chrome ウィンドウ（サイドパネル・ショートカット）を使うテストは、Linux では `xvfb-run` が要る
- 拡張は `tests/fixtures.ts` の `launchExtension()` で読み込む。読み込む dist は `WW_TEST_EXTENSION_PATH`（既定は `dist`）。e2e の前に `npm run build` を忘れない

## 実サイトのテストを書くときの決まり

- 未ログインの新しいプロファイルで動かす。ログインが要る状態（登録済み・高評価済みなど）はテストにしない。手動で確かめる手順を docs に残す
- YouTube の DOM は変わる。セレクターはテストに直接書かず、`src/sites/` のアダプターが付けた印（`data-ww-*`）や、役割（`getByRole`）で探す
- 座標を固定しない。`tests/helpers/youtube-live.ts` の `clearestPoint()` で、本物の操作部品とプレーヤーの操作帯から一番離れた点を狙う
- いつでも出うるものを先に片付ける
  - プロモーションのダイアログ：`declinePromotion()`。ポインターが動くので、ポインターを使う確認は狙い直す
  - 広告：`waitForAdvertToEnd()`
  - コメント欄が横のパネルに出るレイアウト：`openNativeComments()`
- 失敗の理由を残す：`attachOperationDiagnostics()`（操作面）、`renderDiagnostics`（描画）を使う

## 過去の不安定さの原因（同じ形を疑う）

| 症状                                   | 原因                                                            | 直し方                                                              |
| -------------------------------------- | --------------------------------------------------------------- | ------------------------------------------------------------------- |
| プレーヤーの上のドラッグが効かない     | 動画の要素の z-index（10）が、テストの狙った要素を覆っていた    | 狙う点を `clearestPoint()` で選ぶ。重なりを elementFromPoint で記録 |
| キー操作が届かない                     | フォーカスが `#movie_player` に残っていた                       | 操作の前にフォーカスの位置を確かめ、明示的に移す                    |
| 近づくと戻る動きが、たまに起きる       | G1 の接近の判定（40〜72px）の対象に `player.video` が入っていた | 判定の対象を確かめる。テストの点を接近の範囲の外に置く              |
| 本物の `:hover` が、操作のあとに消える | 合成のドロップなどでポインターの状態が保たれない                | 編集画面の強制プレビュー（「ページ上でこの状態を表示」）で確かめる  |
| 実行ごとにレイアウトが違う             | YouTube のA/Bテスト・ウィンドウの幅・シアターモードの記憶       | 幅を固定し、`enterNativeTheater()` などで状態を明示的に作る         |

新しい原因を見つけたら、この表に1行足す。

## 不安定なテストを調べる手順

1. 同じテストを `--repeat-each=10` で回し、失敗率を数える
2. 失敗した回の trace（`.work/test-results/e2e/` の `trace.zip`）を開き、失敗の直前のスクリーンショットと DOM を見る
3. 原因が製品にあるか、テストにあるかを分ける。製品の不具合なら、まず確実に失敗するテストにしてから直す
4. 待ち時間を延ばす・リトライを足す・判定を緩める、で通すのは禁止。`expect.poll` で状態を待つのはよい（固定の `waitForTimeout` より優先）
5. 直したら、もう一度 `--repeat-each=10` で 0 件の失敗を確かめる

## 見た目を確かめるテスト

テストが通っても、見た目が正しいとは限らない。スクリーンショットを撮ったら、**必ず画像を開いて目で確かめる**。

- 撮影は `docs/screenshots/<段階>/` に置く。何を確かめた画像かをファイル名で分かるようにする
- 確かめること：意図した場所に描かれているか、本物の文字が読めるか、操作部品の上に重なっていないか、おかしな小さな塊が出ていないか
- 数値で確かめられるものは数値にする：要素の大きさと位置（着せ替えの前後で同じ）、`elementFromPoint` の結果、コントラスト（`tests/helpers/native-youtube.ts` の `contrastAt()`）
- テスト用の素材は、結果が分かりやすい形にする（例：角と辺がはっきりした9スライス用の PNG）。実際の作品に近い素材は、別に1枚だけ確かめる

## 報告

AGENTS.md の完了報告に、テスト件数を unit / e2e / 実サイトで分けて書く。実サイトは、どの `WW_LIVE_*` を何回動かしたか、失敗があればその理由も書く。
