# WWT の性能計測と調査

合否の基準と原則は AGENTS.md の「計測」「性能の調査」にある。このスキルは、その進め方の手順。

測るのは、ページの上で動く処理（content script・`src/sites/`・`src/world/`・`src/host/`・描画）を変えた段階だけ。エディターやサイドパネルの見た目だけの段階では測らない。

## 合否の基準（再掲）

- 指標：**拡張の CPU 時間（1フレームあたり）**。拡張のコールバック（rAF・タイマー・Mutation/Resize/IntersectionObserver・イベント・読込時の実行）を、フレームごとに合計した値
- 合格：変更前との比較で、中央値の増分が +0.5ms 以内、p95 の増分が +1ms 以内
- フレーム全体の p95（Chrome trace の AnimationFrame）は参考値。合否に使わない
- 場面を分ける：起動直後（遷移から6秒）・定常・SPA 遷移直後

## 1. 既存のハーネスを先に探す

計測の仕組みは段階ごとに作られてきた。新しく作る前に、近いものを広げる。

| ハーネス                         | 測るもの                                                                       | 使い方                                                                                               |
| -------------------------------- | ------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------- |
| `scripts/g11/`                   | G1/G1.1 の操作性の保護。動画ページ、ガードの有無の交互比較、塗れる面積         | `node scripts/g11/build.mjs` → `node scripts/g11/run.mjs startup\|spa\|steady\|minute\|areas\|smoke` |
| `scripts/ui1/`                   | UI1 の着せ替え。検索結果ページ（部品が多い）、変更前後のビルド、着せ替えの有無 | `node scripts/ui1/build.mjs <source> <.work/out>` → `node scripts/ui1/measure.mjs build\|skin`       |
| `tests/*-benchmark.spec.ts` ほか | 模擬ページでのユニット的な比較                                                 | 仮説の確認にだけ使う。模擬ページの数値で合否を決めない                                               |

- 出力は必ず `.work/` の下。ハーネスは `.work` の外への書き出しを拒否する。この検査を外さない
- 変更前のビルドは、変更前のコミットを `.work/` の下へ取り出して、そのツリーのビルドスクリプトで作る
- プロファイルは毎回、未ログインの新しいもの（`.work/g11-profiles/run-*` など）。手元の Chrome のプロファイルを使わない

## 2. 計測ビルドの作り方

- 製品のソースと通常の dist は変更しない
- 計測用のコードは、content script の前に足すラッパー（`scripts/ui1/build.mjs` の方式）か、開発用のビルドフラグで有効になるフックで入れる
- **ソースの文字列を探して書き換える方式（needle の置換）は使わない**。既存の `tests/helpers/page-change-build.ts` がこの方式で、置き換えの対象になっている
- 計測ビルドを作ったら、通常のビルドに計測コードが入っていないこと（dist の差分なし）を確かめる

## 3. 計測が本当に拾えているかを先に確かめる

数値が 0.00 ばかりのときは、拡張が軽いのか、計測が拾えていないのかが区別できない。本計測の前に1回だけ確かめる。

1. 計測ビルドに、わざと重い処理（例：rAF の中で 2ms のビジーループ）を足した版を作る
2. その版で短く測り、中央値と p95 がおよそ +2ms 増えることを確かめる
3. 増えなければ、計測の方を直す（ラッパーが拡張の isolated world に入っているか、コールバックの種類が漏れていないか）

## 4. 劣化の原因を調べる

推測で直してから測らない。

1. **CPU プロファイルを取る**：`G11_CPUPROFILE=1` を付けて `scripts/g11/run.mjs` を実行すると、`pair-N-*-cpuprofile.json` ができる。プロファイルは負荷が増えるので、その回の数値は合否に使わない。ui1 など別のハーネスで必要なら、同じく CDP の `Profiler.start` / `Profiler.stop` を足す
2. 重い関数を、self time の大きい順に5つ挙げる。拡張のコードかどうかを、ファイル名で区別する
3. 候補が複数あるときは、**機能を1つずつ止めて**切り分ける（例：「小さすぎるとき」を設定しない作品で測る）。この段階は2組か、手元の短い計測でよい
4. 原因を直したら、同じ短い計測で消えたことを確かめる
5. 最後に1回だけ、本物の YouTube でフルの交互計測をする

過去に見つかった原因（同じ形を疑う）：

- ページの変化のたびに文書全体を `querySelectorAll` していた（UI1 の「小さすぎるとき」）→ アダプターが渡す、新しく印を付けた要素だけを見る
- 毎フレームのレイアウト読み取り（`getBoundingClientRect` の連発）→ 結果をフレームの中でキャッシュする（G1.1 の overlaySlot）
- MutationObserver のコールバックが、自分の書き込みで再発火していた → `takeRecords()` で捨てる
- 操作面の候補を、毎回ゼロから探していた → 差分だけ探す（G1.1 の incremental discovery）

## 5. 本計測

- 変更前と変更後を**交互に**、最低4組。起動直後は組ごとのばらつきが大きいので、6組あると安心
- 同じ組の中では、ブラウザー・プロファイル・URL・ウィンドウの大きさ（1920×1080、deviceScaleFactor 1）をそろえる
- YouTube の広告・プロモーションのダイアログで結果が乱れる。乱れた組は捨てずに記録し、理由を書いて除外する
- 起動直後・定常・SPA 遷移直後を、別の表の行にする

## 6. 記録

- 生データの要約を `docs/benchmarks/<段階>-<内容>.json` に置く（コミット・ブラウザーのバージョン・OS・URL・組ごとの値を含める）
- その段階の docs（例：`docs/ui-skin.md` の「性能」）に、次の形の表を置く

| 比較（交互の組数） | 場面 | 拡張CPU/フレーム 中央値 | p95 | 判定 | 参考：全体p95 |
| ------------------ | ---- | ----------------------- | --- | ---- | ------------- |

- 途中で不合格だった版があれば、その数値と原因、直し方も残す。次の担当が同じ形の劣化を見分けられるようにする
- 拡張なしの値を測っていない場合は、そう書く
