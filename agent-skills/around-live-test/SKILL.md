# Around の e2e テストと実サイトのテスト

原則は AGENTS.md の「テストを製品の今の挙動に合わせて緩めない」。失敗したら、まず製品側の原因を疑う。

## 塊ごとの確認（2026-11-07、翔太の決定）

- どの場面で何がどう見えたら完成かを実装前に決める。作り、本物のページで撮り、自分で画像や動画を開いて基準と見比べ、必要な修正を繰り返す。Playground は実際の Playground を使う。数値のテストに加えて、文字と操作部品、動きも目で確かめる
- 基準を満たしたら終了する。目安は1〜2日で、何度か直しても改善しなければ、試したことと足りないことを書いて止める。翔太に聞くのは G1 を守りを弱めずに直せない場合、権利、Chrome の権限、設計書と大きく異なる判断の4つ
- Claude Code はエンジンの中核（world・host・sites・描画・作品データの形）、Codex は Playground・エディター／Studio・素材の処理・計測の道具を担当する。同じファイルを同時に触らず、持ち場の外の変更は最小限にして報告に書く
- 大きな塊の終わりにもう片方がレビューする。中核は Codex が e2e 全件・実サイト・性能まで確かめ、中核以外は Claude Code が完成基準・見た目・触った所のテストを中心に見る

## テストの3つの層

| 層                | どこで動くか                                                  | 実行                                                                 |
| ----------------- | ------------------------------------------------------------- | -------------------------------------------------------------------- |
| unit              | Node の中。`playwright.config.ts` の `unitSpecs` に名前を足す | `npm run test:unit`                                                  |
| e2e（模擬ページ） | 拡張を読み込んだ Chromium ＋ `tests/fixtures/youtube.html`    | `npm run build` → `npm run test:e2e -- tests/<名前>.spec.ts`         |
| 実サイト          | 本物の YouTube。環境変数で明示したときだけ動く                | `AROUND_LIVE_<名前>=1 npm run test:e2e -- tests/<名前>-live.spec.ts` |

- CI は unit と e2e を毎回動かす。e2e は `--shard=N/4` で4台に分けて並べる。実サイトは CI では動かさない（ネットワークと YouTube の変化で結果が揺れるため）
- 手元でどこまで回すかは AGENTS.md の「テストの段階分け」に従う。作業の途中は触った部分の spec だけでよい。spec を1つの機能ごとに分けておくと、選びやすい
- 1件ごとに拡張入りの Chromium を起動し直すので、1件あたり数秒かかる。同じ準備で確かめられることは1つのテストにまとめ、似たテストを増やしすぎない
- 新しい実サイトのテストは `test.skip(process.env.AROUND_LIVE_<名前> !== '1', '理由')` で始め、既存の `*-live.spec.ts` と同じ形にする
- e2e は `workers: 1` で順に動く。ネイティブの Chrome ウィンドウ（サイドパネル・ショートカット）を使うテストは、Linux では `xvfb-run` が要る
- 手元では、表示ありのテストの窓を画面の外に出す（AGENTS.md の「手元でテストの窓を前に出さない」）。`npm run test:e2e` なら自動で `AROUND_TEST_WINDOW_OFFSCREEN=1` が付く。新しいテストで Chrome を自分で起動しない
- 拡張は `tests/fixtures.ts` の `launchExtension()` で読み込む。読み込む dist は `AROUND_TEST_EXTENSION_PATH`（既定は `dist`）。e2e の前に `npm run build` を忘れない

## 実サイトのテストを書くときの決まり

- 未ログインの新しいプロファイルで動かす。ログインが要る状態（登録済み・高評価済みなど）はテストにしない。手動で確かめる手順を docs に残す
- YouTube の DOM は変わる。セレクターはテストに直接書かず、`src/sites/` のアダプターが付けた印（`data-around-*`）や、役割（`getByRole`）で探す
- 座標を固定しない。`tests/helpers/youtube-live.ts` の `clearestPoint()` で、本物の操作部品とプレーヤーの操作帯から一番離れた点を狙う
- いつでも出うるものを先に片付ける
  - プロモーションのダイアログ：`declinePromotion()`。ポインターが動くので、ポインターを使う確認は狙い直す
  - 広告：`waitForAdvertToEnd()`
  - コメント欄が横のパネルに出るレイアウト：`openNativeComments()`
- 失敗の理由を残す：`attachOperationDiagnostics()`（操作面）、`renderDiagnostics`（描画）を使う

## 過去の不安定さの原因（同じ形を疑う）

| 症状                                   | 原因                                                                                                                                           | 直し方                                                                                                                                           |
| -------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| プレーヤーの上のドラッグが効かない     | 動画の要素の z-index（10）が、テストの狙った要素を覆っていた                                                                                   | 狙う点を `clearestPoint()` で選ぶ。重なりを elementFromPoint で記録                                                                              |
| キー操作が届かない                     | フォーカスが `#movie_player` に残っていた                                                                                                      | 操作の前にフォーカスの位置を確かめ、明示的に移す                                                                                                 |
| 近づくと戻る動きが、たまに起きる       | G1 の接近の判定（40〜72px）の対象に `player.video` が入っていた                                                                                | 判定の対象を確かめる。テストの点を接近の範囲の外に置く                                                                                           |
| 本物の `:hover` が、操作のあとに消える | 合成のドロップなどでポインターの状態が保たれない                                                                                               | 編集画面の強制プレビュー（「ページ上でこの状態を表示」）で確かめる                                                                               |
| 実行ごとにレイアウトが違う             | YouTube のA/Bテスト・ウィンドウの幅・シアターモードの記憶                                                                                      | 幅を固定し、`enterNativeTheater()` などで状態を明示的に作る                                                                                      |
| サムネイルのクリックが別の要素に届く   | ポインターが留まると `ytd-video-preview` がカードの外に重なる。押してから離す間に出ると、click は共通の親へ行く                                | プレビューが出るまで待ってから押す（`tests/card-preview-live.spec.ts`）。各入力の宛先を window の capture で記録する                             |
| G1 の止まった表示を見逃す・見間違える  | 自動で戻る停止（3回未満の失敗・動きの間の保留）は、poll の間隔のあいだに消える。停止の文言で待つと、文言を変えたときに待ちが黙って効かなくなる | 止まった表示を `data-around-safety` の MutationObserver で全部記録して確かめる。待つ条件は文言ではなく「止まっていない（`"stopped":""`）」にする |
| G1 の読み直しの窓にテストの操作が入る  | 続けて起きた変化は 200ms（`COALESCE_MS`）の窓でまとめて読まれ、その間は描画を保留する。最初の操作が直前の読み直しの窓に入る                    | 保留が解けてから、窓より長く（250ms）空けて操作する（`operation-safety.spec.ts` の「redraws over unchanged…」）                                  |

新しい原因を見つけたら、この表に1行足す。

## 不安定なテストを調べる手順

1. 同じテストを `--repeat-each=10` で回し、失敗率を数える
2. 失敗した回の trace（`.work/test-results/e2e/` の `trace.zip`）を開き、失敗の直前のスクリーンショットと DOM を見る
3. 原因が製品にあるか、テストにあるかを分ける。製品の不具合なら、まず確実に失敗するテストにしてから直す
4. 待ち時間を延ばす・リトライを足す・判定を緩める、で通すのは禁止。`expect.poll` で状態を待つのはよい（固定の `waitForTimeout` より優先）
5. 直したら、もう一度 `--repeat-each=10` で 0 件の失敗を確かめる

## 見た目を確かめるテスト

テストが通っても、見た目が正しいとは限らない。スクリーンショットを撮ったら、**必ず画像を開いて目で確かめる**。

- 撮影は `docs/screenshots/<段階>/` に置く。何を確かめた画像かをファイル名で分かるようにする
- 撮影は `caret: 'initial'` で撮る。既定（`'hide'`）は入力欄のスタイルを変え、守りがそれに答えて一瞬絵を止めるので、絵の消えた画像になる（2026-11-07、Codex の調べ）。`launchExtension()` で開いたページは既定がそうなっている。自前で Chrome を開く道具は明示する
- 画面基準のモデルを動画の上に置くと、見ている間は操作バーの列ごと切り抜かれて見えない（守りの設計どおり）。動画の上のキャラはプレーヤー基準で置く
- 確かめること：意図した場所に描かれているか、本物の文字が読めるか、操作部品の上に重なっていないか、おかしな小さな塊が出ていないか
- 数値で確かめられるものは数値にする：要素の大きさと位置（着せ替えの前後で同じ）、`elementFromPoint` の結果、コントラスト（`tests/helpers/native-youtube.ts` の `contrastAt()`）
- テスト用の素材は、結果が分かりやすい形にする（例：角と辺がはっきりした9スライス用の PNG）。実際の作品に近い素材は、別に1枚だけ確かめる

## 報告

塊の終わりに1回、基準と見比べた画像・動画、自分で納得した所、まだ物足りない所、もう片方の担当にレビューしてほしい所をまとめる。

AGENTS.md の完了報告に、テスト件数を unit / e2e / 実サイトで分けて書く。実サイトは、どの `AROUND_LIVE_*` を何回動かしたか、失敗があればその理由も書く。
