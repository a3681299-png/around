# Around の世界の評価（World Runtime）

設計の中身は `docs/spatial-design.md` にある。このスキルは写さない。**読む節の案内**と、**置き場所と作品データの判断の仕方**だけを書く。設計書と食い違ったら設計書が正しい。

## 1. 読む節

作業を始める前に、`docs/spatial-design.md` の「0. 土台と責務」を必ず読む（固定条件・責務の表・入口の関数）。そのうえで、触る範囲の節を読む。

| 触る範囲                               | 読む節                                                                             |
| -------------------------------------- | ---------------------------------------------------------------------------------- |
| 座標・奥行き・カメラ・投影             | 1. 空間とカメラ                                                                    |
| 点の参照・面・4隅                      | 2. 点と面                                                                          |
| 操作面・接近・切り抜き・照合・緊急 OFF | 3. 操作性の保証（G1）。実装の記録は `docs/operation-safety.md`・`docs/g12-plan.md` |
| キャラ・姿勢・クリップ・取り込み・接地 | 4. キャラクター                                                                    |
| 光・奥行きの見え方                     | 5. 光と奥行き                                                                      |
| 重ね方・合成・DOM と候補方式の比較     | 6. 描画の重ね方                                                                    |
| その場の状態・記憶・住人               | 7. 世界の状態の3分類                                                               |

## 2. Host と world のどちらに置くか

迷ったら、次の順に問う。最初に「はい」になった所に置く。

1. **ページの DOM・ブラウザーの API・時計を読む／書くか**（`getBoundingClientRect`・`performance.now`・`matchMedia`・Observer・ストレージ）→ Host（`src/host/`・`src/sites/`）。world は読まない
2. **作品から外せない保護か**（操作面を隠さない・入力を横取りしない・緊急 OFF）→ 判定の材料は Host が集めて入力として渡し、保護そのものはエンジン（Host・描画）側に置く。作品データから弱められる形にしない
3. **同じ入力列から同じ結果になるべき計算か**（状態遷移・姿勢・追従・規則の評価・投影）→ world（`src/world/`）。純粋な関数にし、時刻・乱数・品質の段は入力として受け取る
4. **数値の指示を DOM・Canvas・Three へ反映するだけか**（GPU 資源・合成・最終の照合）→ 描画（`src/renderers/`）。世界の判断を描画の隠れた状態で変えない
5. **素材の解析・共有・参照数か** → Asset Runtime。個体の可変状態は持たない

ほかに守ること：

- Host から world へ渡すものは、型の決まった入力（シグナル・出来事・環境）にする。G1.2 の `environment.approach` のように、Host が決めた制限は「作品からも録画からも入らない」ことを、読み込み（`parseWorldInput` など）で確かめる
- world に足した状態は WorldState に入り、録画（テイク）に入るかを決める。Host の制限を録画に入れない（`docs/g12-plan.md` の「録画との互換」）
- ページの変化のたびに文書全体を検索しない（AGENTS.md の「繰り返さない設計」）。Host の読み取りは差分か、snapshot ごとに一度

## 3. 作品データに入れてよいか

作品データ（DesignDocument）に入れてよいのは、**検証できる宣言的な値**だけ。

| 入れてよい                                                                                      | 入れない                                                                                 |
| ----------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| 数値・範囲の決まった数値・列挙・色・ID の参照（登録表にある property ID、レイヤー ID、素材 ID） | JS・任意の式・CSS の文字列・シェーダーのコード・DOM セレクター（実行される形のもの全部） |
| 作者の表現（位置・動き・規則のキー・見た目の段の指定）                                          | 操作性の保護を外す・弱める設定（作品から解除できない）                                   |
| 上限のある配列（`IMAGE_LIMITS` などの上限を守る）                                               | 利用者の許可・記憶・閲覧の記録（作品に暗黙に含めない）                                   |

判断の手順：

1. 値が「実行される」形なら入れない。表現に必要なら、エンジン側に登録表（property ID・型・範囲）を作り、作品はその ID と数値だけを持つ
2. 入れる値は `src/design/schema.ts` で検証し、上限を決める。範囲外は読み込みで拒否する（黙って直さない）
3. 項目を足すなら版を上げる。手順は `around-design-version` スキル（移行チェーンに1段、履歴由来の fixture）
4. エンジンの判断（品質の段・保護の範囲・Host の制限）は作品データに入れない。作品が選べるのは表現まで

外部の Three.js のスキル（`threejs-*`）の例は、CDN の import map から three を読む書き方や、WebGPU と TSL のシェーダーを勧めることがある。Around は three を同梱してビルドし（拡張は外のコードを読めない）、描画は `WebGLRenderer`、シェーダーはエンジンのコードの中だけに置く。作品データからシェーダーは受け取らない。
