# WWT の段階の検証

大きな塊の終わりに、実装した担当と別の担当が完成基準と報告の主張を確かめる（2026-11-07、翔太の決定）。Claude Code はエンジンの中核（world・host・sites・描画・作品データの形）、Codex は Playground・エディター／Studio・素材の処理・計測の道具を担当する。同じファイルを同時に触らず、持ち場の外を触る必要があれば最小限にして報告に書く。中核は Codex が e2e 全件・実サイト・性能まで確認する。中核以外は Claude Code が完成基準・見た目・触った所のテストを中心にレビューする。

実装担当は塊ごとに、どの場面で何がどう見えたら完成かを先に決める。実装し、本物のページ（Playground は実際の Playground）で撮影し、自分で画像や動画を開いて基準と見比べ、必要な修正を繰り返す。基準を満たせば終了する。塊は台本の場面がまとまって動くまでの大きさ（rev 112）で、数回直しても改善しなければ、試したことと足りないことを記録して止める。

## 0. 見る目の柔らかさ（2026-11-08、設計書 rev 112。AGENTS.md の「見る目の柔らかさ」）

使う人が感じるかで判断する。

- **緩めない線は4つだけ**：操作を壊さない（G1）、文字が読める（4.5:1 以上）、作品データの安全（JS・任意の CSS・シェーダー・セレクターを入れない、検証を弱めない）、権利（私用 VRM・Mixamo 由来の動作・私用の素材を入れない）。このどれかが破れたときだけ「取り込む前に直す」にする
- それ以外（見た目の粗、まれな揺れ、少しの重さ、テストの環境の問題）は、取り込みを止めずに「残りの一覧」に書く
- 判定は2つだけで言う：**「取り込んでよい（残りあり）」**／**「取り込む前に直す」**。「不合格」「保留」は使わない
- 数字は目安。少し超えても、体感で分からず直す手が見えていれば先へ進む。2組で傾向が言えないものは、それだけで止めない
- 同じことを何通りも測り直さない。正式な検証は塊の終わりに1回
- 気づきには「こうすると良くなる」を添える

検証で見つけたもののうち、直すか後回しかなどの細かい決定は検証する側が決め、docs に1行残す。翔太に聞くのは AGENTS.md の「止めて聞く」ときだけ（G1 を守りを弱めずに直せない・権利・Chrome の権限・設計書の方針と大きく違う判断）。

## 1. 読むもの

1. 依頼文（検証の範囲と、直してよいもの）
2. その段階の docs（例：`docs/ui-skin.md`）と、完了報告
3. 差分：`git log --oneline <変更前>..<変更後>` と `git diff --stat`。テストとソースの比率、計測の道具の変更、`[skip ci]` のコミットを見ておく
4. スクリーンショット（`docs/screenshots/<段階>/`）。**画像を開いて目で見る**。テストが通っていても、見た目が壊れていることがある

## 2. 主張を一覧にする

完了報告と docs から、確かめられる主張を抜き出して表にする。

| #   | 主張 | 確かめ方 | 結果 |
| --- | ---- | -------- | ---- |

「〜しない」「〜は変わらない」という主張ほど、数値で確かめる（例：要素の大きさ・位置・`elementFromPoint`・フォーカス順が、変更の前後で同じ）。

## 3. いつも確かめる観点

その段階の内容に関係なく、次は毎回見る。

- **見た目**：対象の本物のページで撮り、画像や動画を開いて完成基準と見比べる。YouTube 向けは本物の YouTube、Playground は実際の Playground。描画の位置、文字の読みやすさ、はみ出しを目で確かめる
- **操作性（G1）**：押せない・ずれる・ドラッグが狂う・操作面が隠れる、が起きないか。プレーヤーの操作帯（上 64px・下 112px）。Alt+Shift+Q（緊急OFF）で、その段階の効果がすべて外れるか
- **ページの変化**：SPA 遷移・シアターモード・全画面の出入り・ダーク／ライトで、新しい部品に付き、古いものが残らないか
- **安全**：作品データから実行できる形（JS・任意の CSS・セレクター・URL）が入らないか。悪意のある作品データを作って試す。新しい Chrome 権限が足されていないか（`manifest.json` の差分）
- **互換**：DesignDocument の版を上げたなら、wwt-design-version の手順どおりか（履歴由来の fixture・変更前のコードで取った期待値）
- **性能**：ページの上で動く処理を変えた段階だけ。wwt-perf の手順で、変更前と変更後を交互に測り直す。報告の数値を写さない。計測が本当に拾えているかも確かめる。エディターの見た目だけの段階では測らず、報告にそう書く。本物の YouTube での8組の交互計測は、ページの上の処理を大きく変えた塊の終わりと、作業ブランチに入れる前だけ。起動直後と SPA 遷移直後は、1フレームの p95 ではなく、6秒の拡張の CPU 合計の組差の中央値が同じ版どうしの振れの幅に収まるかで判定し、1〜2組の上振れでは不合格にしない。50ms 以上の長い処理の数と動画のフレーム落ちは、はっきり増える傾向がないかを見る（2026-11-07、翔太の決定。同日に改めた。wwt-perf の「合否の基準」）。同じ PC の中でだけ比べ、PC・Chromium の版・画面の更新の速さを書く
- **テスト**：中核の塊のレビューでは Codex が Windows で e2e 全件を回す。さらに最終の独立検証がある場合は、対象コミットの CI 結果と既に行った全件確認を参照し、追加したテストと実サイトの確認を回す。中核以外は触った所のテストを確認する
- **編集の操作**：Undo / Redo・保存・破棄・再読込で、プレビューなどの一時的な状態が作品や履歴に残らないか
- **私用 VRM**：`PochibyKT_Pochi*` がコミットされていないか（`git log --all --stat` で確かめる）
- **わざと壊して確かめる**：開発用のビルドで、その段階で関わる守りの仕組み（最後の切り抜き、押した瞬間の照合、接近の停止、HOLD など）を1つずつ止め、どれかのテストが必ず落ちることを確かめる。止め方は、そのビルドだけで効く変更にし、製品のソースや通常の dist には残さない。止めても落ちるテストがなければ、そのテストの穴として報告する（どの仕組みを止めて、どのテストを回したか）

## 4. 見つけたものの扱い

見つけた問題は、まず次の2種類に分ける。変更前のビルドと変更後のビルドの両方で、同じ再現を回して決める（片方だけで決めない）。

| 種類           | 決め方                                                             | 扱い                                                                                                                                                          |
| -------------- | ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 退行           | その段階の変更で入ったもの。変更前のビルドで起きず、変更後で起きる | 4つの線（G1・読める・安全・権利）に触れる退行は「取り込む前に直す」。それ以外の退行は「取り込んでよい（残りあり）」として残りの一覧に書き、直し方の案を添える |
| 前からある残件 | 変更前のビルドでも起きる                                           | 取り込みを止める理由にしない。影響×頻度（下の表）と、本物の YouTube で起きるか（確かめていなければ、そう書く）を残りの一覧に書く                              |

そのうえで、直してよいかは次で決める。

| 見つけたもの                                 | 扱い                                                                           |
| -------------------------------------------- | ------------------------------------------------------------------------------ |
| テスト・計測・道具の不備                     | 直してよい                                                                     |
| 原因がはっきりした小さな製品の不具合         | まず失敗するテストを書き、直す。1件1コミット。コミットのメッセージに原因を書く |
| 設計に関わるもの（方式・作品データの形）     | 直さない。再現手順・原因の見立て・直し方の案を報告する                         |
| 確かめられなかったもの（ログインが要るなど） | 推測で「問題なし」にしない。翔太が手動で確かめる手順を書く                     |

見つけた不具合には、AGENTS.md の「影響×頻度」を付ける。

| 影響＼頻度           | いつも         | 条件がそろうと | まれ           |
| -------------------- | -------------- | -------------- | -------------- |
| 操作が破綻する       | その段階で直す | その段階で直す | その段階で直す |
| 少し不便・読みにくい | その段階で直す | その段階で直す | 後回し         |
| 見た目が少しずれる   | その段階で直す | 後回し         | 後回し         |

- 「後回し」は直さず、その段階の docs に1行（症状・起きる条件・見立て・こうすると良くなる）で書く。取り込みを止める理由にしない
- G1 の同じ不具合が3回の試行で解消しなければ、試したことと足りないことを報告する。守りを弱めずに直せない場合は翔太に聞く
- テストを今の挙動に合わせて緩めない。既存のテストが製品の不具合を見逃していたら、テストを強くする
- 原因を推測で書かない。計算済みスタイル・trace・CPU プロファイル・スクリーンショットなど、証拠を添える

## 5. 検証報告（日本語）

塊の終わりに1回、完成基準と比べた画像・動画、納得した所、物足りない所、レビューで見てほしい所をまとめる。独立検証では AGENTS.md の完了報告に次を加える。

- 判定（「取り込んでよい（残りあり）」か「取り込む前に直す」か）と、残りの一覧

- 主張の一覧の表（確かめた・違った・確かめられなかった）
- 見つけた問題を「退行」と「前からある残件」に分けた一覧（変更前・変更後のビルドでの結果、影響×頻度、本物の YouTube で起きるか）
- わざと壊した守りの仕組みと、それで落ちたテスト（落ちなかったものはテストの穴として）
- 直したものと、直していないもの。直していないものは、その理由と直し方の案
- 交互計測の表（組ごとの値も）
- テスト件数（unit / e2e / 実サイト）と CI の結果
- 翔太が手動で確かめること
- 次の段階に向けて気になる点
- 後始末の結果（残したものとその大きさ。下の 6.）

## 6. 検証の後始末

ノート PC の空きが少ないので、終わった検証の生データは残さない（2026-11-07、翔太の決定。AGENTS.md の「検証の後始末」）。

1. **報告を出したら、すぐに消す**：試行ごとのブラウザーのプロファイル（`p-*`・`g-entry-profile-*`・`g-backup-profile-*` など）、検証用のビルド（`test-dist-*`・`g11-*-dist` など）、検証用の worktree の中の `node_modules`（ジャンクションならリンクだけ外す。中をたどらない）、録画の動画
2. **残すのは要約だけ**：`summary.json`・`stacks.json` などの要約の json と、報告から参照している画像。合わせて **1回の検証で 200MB まで**。超えるなら、何を残したかと理由を報告に書く
3. **`docs/benchmarks` に生データを入れない**：trace・CPU プロファイル・プロファイルのフォルダ・動画はコミットしない。`.gz` などに圧縮しても同じ。保管用の zip も作らない（残すのは、翔太が残してと言った物だけ）
4. **段階が閉じたら、検証の worktree を外す**：`node scripts/clean-work.mjs --dry-run` で確かめてから `node scripts/clean-work.mjs`、または `git worktree remove`。フォルダを直接消さない（git の記録が残る）。ブランチを checkout している worktree は外さない
5. 報告に、残したものの一覧と合計の大きさを書く
